# Роли и права доступа Nexus-ARSEO

Статус документа: черновик. Матрица задаёт **целевые права по умолчанию**. Администратор может менять их для роли или для отдельного пользователя (см. «Как администратор ограничивает доступ»).

Техническая основа — уже реализованные таблицы `app_roles`, `permissions`, `role_permissions`, `user_roles`, `profiles`, `audit_log` (миграция [`202609260001_identity_and_access.sql`](../supabase/migrations/202609260001_identity_and_access.sql)) и предлагаемые расширения из [`data-model.md`](./data-model.md).

## Текущее состояние в базе

| Что | Сейчас | Целевое состояние |
|---|---|---|
| Роли | 9 системных ролей созданы | те же 9 + внешние роли (фаза 8) |

| Проверка прав в RLS | по коду роли (`private.has_role`) | по правам (`private.has_permission`, фаза 0) |

## Обозначения

| Код | Значение | Как хранится |
|---|---|---|
| **Р** | разрешено | `role_permissions.granted = true`, `scope` пусто |
| **З** | запрещено | строки нет или `granted = false` |
| **О** | ограничено | `granted = true` + `scope` (пределы указаны под таблицей раздела) |
| **ОР** | по отдельному разрешению | роли право не выдано; администратор выдаёт его пользователю через `user_permission_overrides` (`effect = allow`) |
| — | не применимо | у раздела нет такого действия |

### Склад

Заведующий складом и работники склада участвуют в приёмке, пересчёте, регистрации партий, стикеровке и размещении. На первом этапе они **не являются пользователями Nexus**. Их действия вносит специалист или старший менеджер по логистике от имени ответственного склада:

- в записи хранится, кто внёс данные (`recorded_by` / `changed_by`), и кто физически выполнил работу (`performed_by_name`);
- в `audit_log.metadata` пишется `on_behalf_of` — ФИО исполнителя и склад.

Если сотрудники склада станут пользователями, понадобятся роли, например `warehouse_head` и `warehouse_worker` (**«Требует подтверждения ARSEO»**, вопрос П22): просмотр поставок и остатков своего склада, движения и этапы приёмки своего склада, без финансов.

## Общие правила

1. **Просмотр по умолчанию.** Сотрудники видят основные данные: контрагентов, товары, склады, остатки, поставки, документы, отчёты. Финансы, себестоимость и дебиторская задолженность видят не все.
2. **Ключевые справочники** (клиенты, поставщики, товары, склады, шаблоны, роли, системные настройки) создают и изменяют директор и администратор. Остальным — **ОР**.
3. **Удаление = архивирование.** Физического удаления бизнес-данных нет. Движения, версии документов, курсы, журнал этапов и журнал действий не архивируются — ошибки исправляются сторнирующей записью.
4. **Управление правами.** Дир и Адм — **Р**; ИД получает управление правами только по отдельному разрешению; остальные — **З**. В текущей миграции изменение прав пока доступно только Адм, поэтому доступ Дир добавляется в фазе 0.
5. **Разделение обязанностей.** Целевое предложение: Адм управляет доступом, но не видит финансы без отдельного разрешения директора. Сейчас у роли `administrator` есть `finance.view` и `finance.manage` (исходная миграция) — изменение является неблокирующим вопросом П21.
6. **Внешние пользователи** не получают прав сотрудников ни при каких настройках: права выдаются только внешним ролям и только с `scope = own_counterparty`.

## Как администратор ограничивает доступ

Администратор и Директор могут:

1. **Изменить право роли** — `role_permissions.granted` и `scope` любой ячейки матрицы (например, запретить Маркетологу просмотр остатков).
2. **Ограничить пользователя** — запись `user_permission_overrides` с `effect = deny`. Запрет действует, даже если роль разрешает.
3. **Выдать отдельное разрешение** — `effect = allow`, при необходимости с `scope` и `expires_at`. Так открываются ячейки **ОР** и доступ внешних пользователей.
4. **Отключить роль** — `app_roles.is_enabled = false` (уже реализовано: `private.has_role` не учитывает отключённые роли).
5. **Отключить пользователя** — `profiles.is_active = false` (уже реализовано: неактивный профиль не проходит `private.has_role`) и блокировка в Supabase Auth.

Каждое изменение прав пишется в `audit_log` с `before_data` и `after_data`.

### Как вычисляется итоговое право

1. Пользователь отключён (`is_active = false`) → **запрещено**.
2. Есть действующий `deny` у пользователя → **запрещено**.
3. Есть действующий `allow` у пользователя → **разрешено** в пределах его `scope`.
4. Иначе берётся самое широкое право среди включённых ролей пользователя: без `scope` > со `scope` > нет права. Ячейка **ОР** без выданного разрешения = **запрещено**.
5. Для внешнего пользователя к любому праву добавляется `scope = own_counterparty` + `shared_only`.

Функция `private.has_permission(code)` (фаза 0) реализует это правило для RLS.

### Защитные правила

- Нельзя снять роль с последнего активного администратора и отключить последнего активного директора.
- Права Директора до отдельного решения может менять только сам Директор (неблокирующий вопрос П23).
- Администратор не выдаёт себе доступ к финансам сам — целевое правило, вопрос П21.
- Внешним ролям нельзя выдать `change_status` и права вне раздела «Документы».
- Журнал действий не меняется и не удаляется никем.
