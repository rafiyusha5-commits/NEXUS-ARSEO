Третий полный аудит после [12.10.2026](./audit-2026-10-12.md) и [13.10.2026](./audit-2026-10-13.md).

Документ описывает найденное; исправления — отдельными ветками и Pull Request после решения владельца.

## Основа и границы

**Проверяемое состояние — `main` = `e279449b01f47f68070969497f160eae0e482036`** (merge PR №91, 09.11.2026).

141 файл тестов TypeScript, 136 файлов SQL-тестов, 83 документа.

**Что сделано**

1. Полный прогон обязательных проверок на основе (результаты ниже).
2. Разбор каталога базы после применения всех 126 миграций к отдельному кластеру PostgreSQL 16:
   RLS, политики, права таблиц и функций, `SECURITY DEFINER`, `search_path`, Storage, внешние ключи.
3. Чтение всех 18 маршрутов (`route.ts`), прокси сессии, клиентов Supabase, действий входа и администрирования,
   мест использования серверного ключа; обзор 43 файлов server actions на наличие проверки сессии.
4. Проверка границы Google (области доступа, методы запросов), сервиса OCR, заголовков безопасности.
5. Чтение нового расчёта автозаказа Казахстана (`src/lib/replenishment/calculate.ts`) и входных проверок
   функций последних миграций (ноябрь 2026).
6. Состояние GitHub: защита веток, открытые PR, последний прогон CI на `main`.
7. Поиск секретов в текущем дереве по известным образцам.

**Что не проверялось**

- Production и облако: Supabase, хостинг, бот, переменные окружения, резервные копии, фактическая схема рабочей базы.
- Живая работа внешних сервисов (модель, OCR, Telegram, Drive). Google-источники не открывались.
- Тела всех 258 функций, доступных `authenticated`, построчно не перечитывались: проверены каталог, шаблон
  входной проверки прав и функции последних миграций. Сценарии с воспроизведением, как в аудите 13.10, не повторялись.
- Задания CI `pilot-docker`, `historical-readiness`, `recovery-drill` локально не запускались.
- История Git: копия неглубокая (336 коммитов), поиск секретов выполнен только по текущему дереву.
- Нагрузка, доступность интерфейса, правовые вопросы.

## Итог

Код и база в хорошем состоянии: все обязательные проверки проходят, а защита данных в базе выдержана
на всём объёме, который с октября вырос вдвое. Новых уязвимостей уровня «посторонний читает или портит данные»
не найдено.

**Главные риски сейчас не в коде, а в процессе и эксплуатации:**

- ветка `main` на GitHub не защищена, хотя правила проекта утверждают обратное (К1);
- последний прогон CI на текущем `main` завершён с отказом, и причина не разобрана (К2);
- рабочая база ведётся без реестра миграций (К3, перенос из контекста проекта).

Эти три пункта стоит закрыть раньше любых новых функций.

## Что подтверждено надёжным

- **RLS и права.** RLS включён на всех 121 таблице `public`. У `anon` нет прав ни на таблицы, ни на функции
  приложения. Политик с условием `true` и политик для `anon`/`public` нет. Шесть таблиц без политик
  (`replenishment_*`, `shipment_document_checks`, `telegram_link_codes`) доступны только через функции.
- **Функции.** Все 417 функций `SECURITY DEFINER` имеют пустой `search_path`. Из 233 публичных функций,
  доступных `authenticated`, только три не содержат проверки прав в теле, и все три — тонкие обёртки над
  функциями, которые её выполняют (`add_shipment_transport`, `confirm_shipment_source_extraction`,
  `preview_receivables_import`).
- **Отключённый пользователь.** `private.is_employee()` и `private.is_external_client()` требуют `is_active`,
  поэтому отключение действует в базе, а не только в интерфейсе, включая прямые запросы к API Supabase.
- **Storage.** Загрузка только в папку по шаблону пути и от своего имени; чтение только зарегистрированных
  файлов с правом на документ; удаление только своего незарегистрированного файла в течение часа.
- **Маршруты.** Все 18 маршрутов проверяют сессию; маршруты с расходом денег или серверным ключом требуют
  совпадения `Origin`, ограничивают размер тела и перепроверяют права. Секрет Telegram-воркера сравнивается
  за постоянное время. Все 43 файла server actions проходят через `requireUser` / `requireAccessManager`
  (кроме входа и восстановления пароля, где сессии ещё нет).
- **Google только на чтение.** Области доступа — `drive.readonly` и `spreadsheets.readonly`. Единственные
  запросы `POST` к Google — получение токена и Vision OCR; запросов записи в Drive и Sheets в коде нет.
- **Адреса возврата.** `safeNextPath` и `appOrigin` закрывают находки Н11 и Н12 прошлого аудита.
- **Выгрузки XLSX** пишут текст как `inlineStr`, поэтому значение, начинающееся с `=`, не становится формулой.
- **Секреты.** В дереве найдены только синтетические строки тестов маскирования; `.env*` исключены.
- **CI.** Действия закреплены на хешах коммитов, права `contents: read`, `pull_request_target` не используется.

### К1. Ветка `main` не защищена (высокая)

AGENTS.md: «Запрет закрепляется защитой ветки `main` на GitHub: Pull Request обязателен, force push
и удаление ветки запрещены, обход настроек не разрешён никому». Фактически GitHub API 11.11.2026 возвращает
`protected: false` для `main` и для всех остальных веток. То же отмечено в `project-context.md` на 22.10.2026.

Запрет коммитов и слияний в `main` сейчас держится только на дисциплине участников и агентов. Любая учётная
запись с правом записи может отправить коммит напрямую, переписать историю или удалить ветку.

**Исправление (делает владелец в настройках GitHub):** включить правило для `main` — обязательный PR,
обязательные проверки `app`, `database`, `audit`, `pilot-docker`, `historical-readiness`, `recovery-drill`,
запрет force push и удаления. До включения — исправить формулировку в AGENTS.md, чтобы она не вводила в заблуждение.

### К3. Рабочая база без реестра миграций (высокая, перенос)

По `project-context.md`, в основной базе нет `supabase_migrations.schema_migrations`, SQL применялся вручную.
С тех пор число миграций выросло с 60 до 126. В репозитории нет способа ответить на вопрос «какие миграции
применены в рабочей базе», кроме журнала работ.

Дополнительный признак хрупкости: `scripts/test-db.sh` содержит ручной список примерно из сорока миграций
для повторного применения в строго заданном порядке с пояснениями, какая миграция «возвращает» права после
какой. Поздние миграции переопределяют функции и права ранних, и правильность итогового состояния зависит
от порядка. Тест `security_audit` сверяет итог, и это надёжная страховка для тестового стенда, но не для базы,
где порядок применения не записан.

Аудит рабочую базу не проверял; это вывод по документам и коду.

**Исправление:** отдельно согласованная сверка рабочей схемы на чтение (список функций с хешами тел, политики,
права) с эталоном, собранным из миграций; затем — заполнение реестра по результатам сверки, а не по журналу.

### К4. Админ-действия проверяют роль, а не право (средняя)

`requireAccessManager` (`src/lib/auth/access.ts`) пропускает любого с ролью `administrator` или `director`.
Модель прав проекта при этом строится на `users.manage` / `roles.manage` и приоритете личного запрета.

Для большинства действий расхождение безвредно: дальше идёт запрос с правами пользователя, и RLS его отклонит.
Исключение — `inviteUser` и `inviteExternalClient`: приглашение отправляется серверным ключом **до** первого
запроса под RLS. Директор с личным запретом `users.manage` может отправить приглашение на произвольный адрес
и создать учётную запись Auth. Роль такой записи не назначится, и по `is_employee()` она не станет сотрудником,
поэтому доступа к данным это не даёт. Последствие — письма от имени системы и «висящие» учётные записи.

Та же проверка по коду роли используется в боковом меню и на `/assistant/archive`.

**Исправление:** в `requireAccessManager` и перед вызовом серверного ключа проверять `users.manage`
(и `roles.manage` там, где назначается роль) через `my_permissions`; добавить тест с личным запретом.

### К5. Сервис OCR вне CI (средняя)

`services/ocr` — отдельный сервис на Python (FastAPI, Tesseract), который принимает недоверенные сканы.
У него есть тесты `pytest`, но ни одно из шести заданий CI их не запускает, а `pnpm audit` не видит
`requirements.txt`. Версии закреплены (`fastapi==0.116.1`, `pillow==11.3.0`, `pypdfium2==4.30.0`) и с момента
фиксации не пересматривались; `pillow` и `pypdfium2` разбирают чужие файлы, и именно для них важны обновления.
Dependabot или Renovate в репозитории не настроены.

**Исправление:** задание CI с `pytest` и `pip-audit` для `services/ocr`; ежемесячный пересмотр версий
наравне с правилом для npm-зависимостей.

### К6. Настройки входа не зафиксированы; второго фактора нет (средняя)

В репозитории нет `supabase/config.toml` или иного описания настроек Auth. Отключённая регистрация,
длина пароля, срок сессии и список адресов возврата существуют только в панели Supabase и подтверждены лишь
записью в `security-audit.md` от 03.10.2026. Восстановление проекта или создание нового стенда может тихо
вернуть значения по умолчанию, в том числе открытую регистрацию.

Второй фактор не используется (находка A5 аудита 12.10 не закрыта). Для учётных записей Адм и Дир, которые
управляют ролями и видят закупочные цены, это основной оставшийся риск захвата доступа.

**Исправление:** описать требуемые настройки Auth в репозитории и сверять их при выпуске; запланировать
второй фактор хотя бы для держателей `roles.manage`.

### К8. Плотный неформатированный код (средняя)

В 132 из 397 файлов `src` есть строки длиннее 400 символов, 49 строк длиннее 1500. Целые маршруты и действия
записаны в одну строку (`src/app/api/drive/catalog/sync/route.ts`, `src/app/stickers/actions.ts`,
`src/app/forecasts/actions.ts`); новые миграции — по нескольку операторов в строке. Страницы
`products/[id]`, `sales/[id]`, `shipments/[id]` — по 32–36 КБ каждая. Форматтера в проекте нет.

Это не ошибка, но прямой риск для главного защитного механизма проекта — проверки PR: в такой строке
изменение одного условия прав не видно в diff. Тесты частично компенсируют, но не заменяют чтение.

**Исправление:** подключить Prettier отдельным PR без смысловых правок (и добавить его коммит в
`.git-blame-ignore-revs`); новые миграции писать по одному оператору на строку.

### К11. Веб-слой (низкая)

- `/auth/signout` выполняет выход по `GET`: чужая страница может разлогинить сотрудника ссылкой или картинкой.
  Вреда данным нет. Исправление — `POST` (действие `logout` уже есть).
- `/api/documents/upload` и `/api/shipments/[id]/sources/extract` отклоняют чужой `Origin`, но принимают запрос
  без заголовка; остальные маршруты требуют его. Браузеры отправляют `Origin` при `POST`, и куки Supabase
  имеют `SameSite=Lax`, поэтому практического обхода не видно; стоит выровнять.
- CSP разрешает `script-src 'unsafe-inline'`. Внедрения разметки в коде не найдено (`dangerouslySetInnerHTML`
  не используется), но политика не станет второй линией защиты, пока не переведена на nonce.
