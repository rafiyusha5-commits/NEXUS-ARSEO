## 2. Структура управления

- **ASTRA (главная)** — единый технический руководитель и основной разработчик. Анализирует проект, принимает архитектурные решения, пишет код, ставит и принимает задачи Астры супруги, готовит PR и контролирует интеграцию.
- **АСТРА СУПРУГА** — исполнитель на отдельном аккаунте. Получает конкретные задачи от главной Astra, работает в своей ветке, пишет код и тесты, готовит PR и исправляет замечания. Архитектуру сама не меняет. Найденную архитектурную проблему сначала передаёт главной Astra.
- **Владельцы** одобряют слияние в `main`, изменения production и критические операции.

**Расхождение с политикой репозитория.** [`AGENTS.md`](../../AGENTS.md) пока говорит: «Объединение выполняет владелец после проверки основным Codex». Под новую структуру его должны изменить владельцы (задача A4): проверку выполняет главная Astra, объединение — владелец. До изменения действует текущий текст.

## 3. Архитектура системы

```
Браузер (адаптивный веб, без нативного приложения)
   │  HTTPS, cookies сессии Supabase
   ▼
Next.js 16 App Router (Vercel)  ── src/proxy.ts: обновление сессии
   ├─ Server Components: страницы читают данные от имени пользователя (RLS)
   ├─ Server Actions: формы вызывают RPC от имени пользователя
   ├─ API routes (src/app/api/*): загрузка документов, распознавание, ассистент, Telegram, синхронизация Drive
   └─ серверный ключ Supabase: только приглашения сотрудников и клиентов
   ▼
Supabase
   ├─ PostgreSQL 16: схема public (данные), private (помощники, проверки прав); RLS на всех таблицах public
   │    бизнес-правила — в функциях-RPC (SECURITY DEFINER, search_path=''), а не в приложении
   ├─ Auth: сотрудники и внешние клиенты, приглашения, сброс пароля
   └─ Storage: приватный бакет nexus-documents
Внешние сервисы (только по включению и с подтверждением передачи данных):
   OpenAI (ассистент и агенты) · OCR (Google Vision или своё HTTP-API) · Telegram-бот
   Google Drive/Sheets только на чтение (сервисный аккаунт с правами Viewer) · выгрузки 1С файлами
```

Главный принцип: **база отвечает за правила и права, приложение — за интерфейс.** Почти каждое изменение данных идёт через RPC. Функция сама проверяет право (`private.has_permission`) и состояние объекта, блокирует строки в стабильном порядке и пишет журнал. Прямая запись в таблицы для `authenticated` закрыта. Подробно: [`../data-model.md`](../data-model.md), [`../security-audit.md`](../security-audit.md).

## 6. Технические решения, которые нужно сохранить

1. **Правила — в базе.** Новое изменение данных оформляется как RPC с проверкой права и состояния объекта, а не как прямая запись из приложения. Проверять «в каком состоянии объект», а не только «кто действует» — главный урок аудита 13.10.
2. **Google Drive и Sheets — только чтение** ([`AGENTS.md`](../../AGENTS.md)). Никакой записи, временных файлов или отметок там. Если без записи не обойтись — остановиться и спросить владельцев.
3. **Рабочий день — Казахстан (`Asia/Almaty`).** В SQL используется `private.business_today()` / `private.business_date(ts)` или `(now() at time zone 'Asia/Almaty')::date`, `current_date` запрещён. В приложении — `businessToday()` из `src/lib/dates/business-day.ts` (после #30). Тест `business_date.test.sql` из #30 ловит функции с `current_date` без пояса.
4. **Себестоимость.** В себестоимость входят только фактические расходы, план — для сравнения. Отмена или сторно идут с причиной. Утверждается только расчёт, исходные данные которого не изменились (`inputs_digest`). Расчёт и утверждение сериализуются табличными блокировками. Курс закупки берётся на день прихода (#35). Себестоимость партии — средневзвешенная по приходам (#36). См. [`finance-costing.md`](../finance-costing.md).
5. **Принятое не меняется задним числом.** Принятую позицию поставки нельзя перенести или удалить. Автомобиль после приёмки не возвращается назад. Склад меняется только складскими документами (#32).
6. **Заказ покупателя.** Резерв по FEFO. Подтверждённый заказ при помехах возвращается к подготовке, а не отменяется (модель владельца, #29). Отгрузка проверяет партию, срок годности, ОСГ и гарантийное письмо. Единые правила — `private.customer_order_blockers` (#38/#39).
7. **Права на функции — явный белый список.** Каждая новая функция с `EXECUTE` для `authenticated` вносится в `tests.sec_exec_allow` (`supabase/tests/security_audit.test.sql`), иначе `test:db` падает.
8. **Закупочные цены и себестоимость** закрыты на уровне столбцов и читаются только через функции `my_*` с правом `prices.purchase.view` ([`purchase-price-access.md`](../purchase-price-access.md)).
9. **Внешние сервисы выключены по умолчанию.** Ассистент, OCR и Telegram включаются переменной и отдельным подтверждением передачи данных (`.env.example`).

## 7. База данных

- **Миграции** — `supabase/migrations/<YYYYMMDDHHMM>_<имя>.sql`, номера возрастают. Последняя на `main` — 8100. Номера 8200–9000 заняты открытыми PR. **Следующий свободный — 9100.** Применять в production строго по возрастанию номеров: при `supabase db push` миграция с меньшим номером после большей уже не применится обычным способом. Поэтому PR из раздела 1 сливать и применять в порядке номеров миграций.
- **Схемы.** `public` — данные (RLS включён на всех таблицах, `anon` ничего не получает). `private` — помощники и проверки (`has_permission`, `user_has_permission`, `notify`, `business_today` и т. д.), закрыты от клиентов.
- **Функции.** Изменяющие данные — `SECURITY DEFINER` с `set search_path=''`, права выдаются явно (`revoke all … grant execute … to authenticated`). `CREATE OR REPLACE` сбрасывает настройки функции (в том числе `timezone` из #30): переопределяя функцию, переносите её настройки.
- **Схема данных** — [`../data-model.md`](../data-model.md), соответствие таблиц — [`../database-mapping.md`](../database-mapping.md).
- **Состояние рабочей базы неизвестно** (раздел 1). Перед применением миграций сверить, какие уже применены (таблица `supabase_migrations.schema_migrations`), и сделать резервную копию.

## 8. Авторизация и безопасность

- **Вход** — Supabase Auth (почта и пароль, приглашения, сброс пароля). Сессия в cookies (`@supabase/ssr`), обновляется в `src/proxy.ts`. Страницы требуют `requireUser()` (`src/lib/auth/access.ts`).
- **Права** — роли и коды прав (`role_permissions`) плюс личные разрешения и запреты (`user_permission_overrides`, запрет сильнее роли). Проверка — `private.has_permission(code)`. Матрица — [`../roles-permissions.md`](../roles-permissions.md).
- **Внешние клиенты** — роль `external_client`, отдельные RLS и маршруты `/portal/*` ([`../external-client-portal.md`](../external-client-portal.md)).
- **Серверный ключ Supabase** используется только для приглашений (`src/lib/supabase/admin.ts`).
- **Заголовки** — CSP, `X-Frame-Options: DENY`, HSTS, `Permissions-Policy: camera=(), geolocation=(), microphone=()` (`src/lib/security/headers.ts`). В CSP остаётся `'unsafe-inline'` (A8).
- **API-маршруты** проверяют `Origin`, тип и размер тела, сессию и права.
- **Аудиты безопасности:** [`../security-audit.md`](../security-audit.md) (RLS и функции, матрица доступа), [`../audit-2026-10-12.md`](../audit-2026-10-12.md) (A1–A10). Открыты A2 (секрет воркера Telegram), A4 (резервные копии и мониторинг), A5 (второй фактор), A6 (персональные данные), A8, A9 (ротация ключей), A10 (`pdf-parse`).
- **Секреты** — только в переменных окружения (`.env.example` без значений). В истории репозитория секретов не найдено (аудит 13.10).

## 10. Тестирование и CI

| Уровень | Как запускать | Что важно |
|---|---|---|
| Модульные | `corepack pnpm test` | Node test runner, `tests/**/*.test.ts`, без сети и реальных сервисов |
| Типы и стиль | `corepack pnpm typecheck`, `corepack pnpm lint` | |
| Сборка | `corepack pnpm build` | собирается без переменных окружения |
| SQL | `corepack pnpm test:db` (нужны `initdb` и `pg_ctl` PostgreSQL 16) или `test:db:docker` | одноразовый кластер; все миграции; before-тесты (`supabase/tests/before/<миграция>.sql` воспроизводят дефект до миграции); повторное применение миграций (проверка идемпотентности); SQL-тесты; параллельные тесты (себестоимость, отгрузка, бюджет ассистента, Telegram) |
| Зависимости | `corepack pnpm audit:ci` | любая неразобранная находка блокирует; исключения обоснованы в [`../security-audit.md`](../security-audit.md) |

CI (`.github/workflows/checks.yml`, [`../ci.md`](../ci.md)): задания `app`, `database`, `audit` на каждый push и PR, без секретов, только на синтетических данных. Названия заданий менять нельзя: на них будет ссылаться защита ветки. **Фраза в `AGENTS.md` «Автоматического прогона в репозитории нет» устарела**: `test:db` выполняется в CI.

**Подводные камни `test:db`.** `scripts/test-db.sh` после всех миграций заново применяет часть из них, проверяя идемпотентность.
- Повторное применение `202609272300_database_security_hardening.sql` снимает `EXECUTE` со всех функций вне его списка.
- Повторное применение старых миграций возвращает старые версии функций.

Поэтому новую миграцию, которая переопределяет такие функции или добавляет новые права, нужно тоже применить повторно в нужном месте списка. Порядок важен; комментарии в скрипте объясняют каждую строку. Если два PR вставляют строку после одной и той же строки, при слиянии будет конфликт: ставьте строку туда, где её не трогают соседние PR.

**Практика Opus, рекомендуемая к сохранению:**
- before-тест на каждый исправленный дефект;
- мутационная проверка нового SQL: намеренно ломать правило и убеждаться, что тест падает (скрипты были локальными, в репозиторий не входят);
- для интерфейса — снимки на 1280 и 390 px на локальной заглушке Supabase (синтетические данные).

## 13. Правила работы с Git

Обязательны правила [`AGENTS.md`](../../AGENTS.md):
- в `main` нельзя коммитить, пушить и сливать;
- каждая задача — своя ветка от согласованной основы, результат — Pull Request;
- объединяют владельцы;
- нельзя `rebase` и `push --force` для отправленных веток; обновлять ветку слиянием `main` (merge commit);
- перед PR — `typecheck`, `lint`, `test`, `build`, `test:db`; основа и непрошедшие проверки указываются в описании PR прямо;
- `audit --prod` вокруг обновления зависимостей.

Именование веток: `fix/<суть>`, `feature/<суть>`, `docs/<суть>`; Астра супруга — с префиксом `astra2/`, чтобы было видно исполнителя. Язык PR, документации и сообщений пользователям — русский. Коммиты описывают, что и почему изменилось.
