# NEXUS: мобильная готовность

Проверка от 14.10.2026 на `main` = `5469b6c4476eed47ab2a1605bb4ac2bc670bac5a`. Это часть передачи проекта: см. [`NEXUS_HANDOVER.md`](./NEXUS_HANDOVER.md).

## Как проверялось и чего проверка не покрывает

**Фактическое тестирование интерфейса в браузере:**
- production-сборка `main` (`next build` + `next start`) в Chromium (Playwright) с эмуляцией мобильного устройства (`isMobile`, `hasTouch`) на ширине **375, 390, 768 и 1280 px**;
- 34 экрана, у каждого измерены: переполнение страницы по горизонтали относительно ширины устройства, элементы за правым краем, размер нажимаемых элементов, кегль полей ввода, таблицы без прокручиваемой обёртки, поля загрузки файлов, мета-тег `viewport`, manifest, `theme-color`, `apple-touch-icon`;
- отдельно проверено мобильное меню: открытие, число ссылок, их высота;
- просмотрены снимки экранов на 375 и 768 px.

**Ограничения, которые надо учитывать:**
- **Данные синтетические.** Вместо Supabase работала локальная заглушка API с вымышленными записями: рабочий проект и реальные данные не использовались. Экраны с длинными реальными названиями и большими таблицами могут вести себя хуже.
- **Это эмуляция Chromium, а не реальные устройства.** iOS Safari, Android Chrome и WebView не проверялись. Поведение клавиатуры, автоматическое увеличение при фокусе, выбор файла с камеры и загрузка фото с телефона на реальном устройстве **не проверены** и оценены только по коду.
- Не проверены экраны «Пользователи» (на заглушке страница падает: ей нужен серверный ключ Supabase) и внешний кабинет клиента `/portal/*` (тестовый пользователь — сотрудник, его перенаправляет на главную).

## Что уже адаптировано

- **Раскладка.** В `src/app/globals.css` 48 media-запросов (точки 600–1250 px). Tailwind подключён, но разметка написана на собственных классах, адаптив задан этими запросами. Next.js выводит `<meta name="viewport" content="width=device-width, initial-scale=1">`.
- **Мобильная навигация есть.** На 375 и 768 px боковая панель скрыта, вверху кнопка «Меню». После нажатия появляются все 34 ссылки разделов высотой 40–41 px, сгруппированные по разделам (`src/components/app-sidebar.tsx`, чистый CSS без JavaScript).
- **Переполнения страницы нет на 33 из 34 экранов** при ширине 375, 390 и 768 px. Таблицы (главная, остатки, отчёт поставки, дебиторка, аналитика, ассистент, документы) прокручиваются внутри своих обёрток и не растягивают страницу.
- **Формы на телефоне в одну колонку**: поставки, заказы, финансы, склад, шаблоны, стикеры. Вкладки карточек поставки и заказа — горизонтально прокручиваемая полоса.
- **Вход и восстановление пароля** — поля 16 px (без автоматического увеличения в iOS), переполнения нет.
- **Модальных окон нет**: вместо них используются раскрывающиеся блоки `<details>` (27 мест в разметке), которые на телефоне работают как обычный текст.
- `apple-touch-icon` есть (`src/app/apple-icon.png`), `icon.png` есть.

## Что требует доработки

1. **Вкладка «Документы» поставки — переполнение 492 px на 375 px и 98 px на 768 px.** Причина — заголовок панели агента «Сверка»: метка «Есть ошибки · ошибок 3, предупреждений 2» и кнопка «Проверить сейчас» в одной строке без переноса (`.panel-heading` / `.topbar-actions` / `.doc-check-state`), и вся вкладка растягивается до 867 px. Это ключевой экран логиста (загрузка и сверка документов поставки).
2. **Шрифт полей ввода 12–13 px почти во всех формах** (поставки, товары, задачи, календарь, склад, финансы, шаблоны, стикеры). iOS Safari при фокусе на поле со шрифтом меньше 16 px увеличивает страницу. Это видно на каждой форме. На реальном iPhone не проверено, но такое поведение Safari известно и задокументировано.
3. **Нажимаемые элементы меньше 44 px** (рекомендация Apple; у Android — 48 dp) — большинство кнопок, ссылок в списках, вкладок и раскрывающихся заголовков. Элементов меньше 24 px немного: в основном ссылки внутри текста, номера поставок на главной, ссылки на документы.
4. **Очень длинные экраны.** «Финансы» на 375 px — около 4300 px в высоту (формы курса, расхода, реестр расходов и расчёт себестоимости одной лентой). Карточки поставки и заказа — длинные ленты разделов. Пользоваться можно, но неудобно.
5. **Загрузка документов с телефона.** Поля загрузки принимают `.pdf, .xlsx, .xls, .csv, .docx, .jpg, .jpeg, .png`, атрибута `capture` нет: телефон предложит выбрать файл, галерею или камеру. Ограничения:
   - предел **4 МБ на файл** (`MAX_DOCUMENT_FILE_SIZE_BYTES`, `src/lib/documents/files.ts`; `serverActions.bodySizeLimit` 4,4 МБ в `next.config.ts` из-за предела запроса Vercel). Фото с современного телефона часто больше 4 МБ — такие файлы будут отклонены;
   - формата `.heic` в списке нет. iOS обычно перекодирует снимок в JPEG, если HEIC не указан, но на устройстве это не проверено;
   - сканы и фото читаются только при настроенном OCR (`docs/source-document-extraction.md`).
6. **Десктоп 1280 px:** переполнение у «Остатков и партий» (132 px: колонки форм растягивают выпадающие списки с длинными названиями товаров) и у «Аналитики» (32 px). На мобильной ширине этих экранов переполнения нет.

| Признак | Состояние |
|---|---|
| Web App Manifest (`manifest.json` / `app/manifest.ts`) | **нет** |
| Service worker, офлайн-режим | **нет** |
| `theme-color` | нет |
| Иконки 192/512 для установки | нет (есть только `icon.png` и `apple-icon.png`) |
| Capacitor, Cordova, React Native, Expo | **нет**: ни в `package.json`, ни в коде |
| Push-уведомления | нет (уведомления только внутри приложения и в Telegram) |

**Установить NEXUS как PWA сейчас нельзя.** Без manifest браузер не предлагает установку. На iOS можно только добавить ярлык на домашний экран: он откроет сайт в Safari с панелью браузера.

## Готовность к Capacitor и ограничения для Android/iOS

Архитектура: Next.js 16 App Router, серверный рендеринг, Server Components, Server Actions, API-маршруты (`src/app/api/*`), сессия Supabase в cookies через `@supabase/ssr` и `src/proxy.ts`. Из этого следует:

1. **Статического экспорта нет и не будет без переписывания.** `output: "export"` несовместим с Server Actions, `proxy.ts` и динамическими страницами. Поэтому сборку NEXUS нельзя упаковать внутрь приложения Capacitor. Реалистичен только вариант **«оболочка с удалённым адресом»**: Capacitor `server.url` указывает на рабочий домен, и WebView загружает NEXUS с сервера.
2. **App Store.** Apple отклоняет приложения, которые только показывают сайт (правило 4.2 «Minimum Functionality»). Для iOS понадобятся нативные возможности: push-уведомления, камера или сканер, работа с файлами. Google Play к таким оболочкам мягче.
3. **Камера в WebView.** Заголовок `Permissions-Policy: camera=()` (`src/lib/security/headers.ts`) запрещает странице доступ к камере через `getUserMedia`. Выбор файла с камеры через системное окно это не затрагивает, но сканирование штрихкодов в браузере потребует ослабить заголовок до `camera=(self)`.
4. **Вход по ссылке из письма.** Ссылки сброса пароля и приглашения открываются в браузере, а не в приложении. Для приложения нужны Universal Links / App Links на домен NEXUS, а адрес возврата задаётся `APP_ORIGIN` (PR #31).
5. **CSP** (`frame-ancestors 'none'`, `X-Frame-Options: DENY`) не мешает WebView, который загружает страницу напрямую, но запрещает встраивание NEXUS во фрейм.
6. **Push-уведомлений нет.** Их понадобится сделать заново: FCM/APNs, хранение токенов устройств, отправка с сервера. Сейчас уведомления — строки в `public.notifications` и сообщения бота Telegram.

**Можно ли использовать существующий backend без изменений?**
- Для мобильного веба, PWA и оболочки Capacitor с удалённым адресом — **да**: это тот же сайт, та же сессия и те же права (RLS).
- Для собственного нативного интерфейса — **частично**. Большая часть бизнес-логики уже в функциях PostgreSQL (RPC с проверкой прав и RLS), их можно вызывать из `supabase-js` с токеном пользователя. Но часть операций живёт только в Server Actions и API-маршрутах Next.js: регистрация и загрузка документов, распознавание исходных документов, ассистент, синхронизация каталога Drive, приглашения, генерация DOCX/XLSX/PDF. Их пришлось бы вынести в API.

## Минимальный объём работ

**Шаг 1. Мобильный веб (несколько дней одного разработчика).** Задачи M1–M4 в [`NEXUS_HANDOVER.md`](./NEXUS_HANDOVER.md):
- поля 16 px на узких экранах;
- перенос заголовка «Сверки»;
- нажимаемые элементы от 44 px на узких экранах;
- переполнение «Остатков» и «Аналитики» на десктопе;
- автоматическая проверка ширины на 375/390/768.

**Шаг 2. PWA (1–2 дня).** Задача M5:
- `src/app/manifest.ts` (имя, `start_url`, `display: standalone`, `theme_color`) и иконки 192/512, в том числе маскируемая;
- service worker на первом этапе не нужен: Chrome на Android и десктопе не требует его для установки;
- кэшировать данные авторизованного пользователя офлайн **нельзя без отдельного решения о безопасности**.

**Шаг 3. Оболочка Capacitor (решение владельцев, после шагов 1–2).**
- проект Capacitor с `server.url` на рабочий домен;
- Universal/App Links для писем;
- push-уведомления (FCM/APNs и серверная отправка);
- при необходимости сканера — `Permissions-Policy` и плагин камеры;
- проверка на реальных устройствах и решение по правилу App Store 4.2.

Это новый объём работ: он требует решения владельцев и в этой передаче не начат.
