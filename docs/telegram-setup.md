# Личный Telegram-чат ассистента: локальный пилот

Ветка `feature/agent-telegram`, поверх проверенного веб-ассистента Terra.
Сейчас поддерживаются текстовые вопросы, `/help`, `/limit`, `/unlink`. Голос, файлы и отправка отчётов в этот пилот не входят.

## Подключение

1. Создать бота у BotFather. Токен хранить только на сервере, не в переписке и не в Git.
2. Применить `202609275300_agent_telegram.sql` после миграции 5200. Миграция не меняет бизнес-данные и месячный бюджет.
3. Задать `TELEGRAM_ENABLED=true`, `TELEGRAM_AUTH_ACKNOWLEDGED=true`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и случайный `TELEGRAM_WORKER_SECRET` (64 шестнадцатеричных символа). Подтверждение Auth необходимо отдельно: сервер выполняет административный вызов создания временной сессии.
4. Запустить Nexus на порту 3000 и `node scripts/telegram-poll.mjs` из каталога репозитория. Этот режим работает только пока компьютер и оба процесса включены. Публичный туннель не нужен. При существующем webhook воркер отказывается запускаться и не удаляет его.
5. В Nexus открыть `/assistant/telegram`, создать ссылку, открыть бота и нажать «Начать». Вернуться в Nexus, обновить страницу и подтвердить свой чат.

Ссылка одноразовая, действует 10 минут. В базе сохраняется только SHA-256 кода. После `/start` доступ ещё не предоставлен: требуется подтверждение в авторизованном Nexus. Одна активная привязка на сотрудника и на чат. Новая ссылка отменяет старые неподтверждённые запросы. Снятие права `agent.use` или деактивация профиля немедленно блокирует получение ответов.

## Права и сессия

Владелец выбрал временную сессию через Supabase Auth (`generateLink` → `verifyOtp`). Административный ключ используется только для Auth, служебных RPC Telegram и существующих RPC учёта. Бизнес-данные читаются клиентом с сессией привязанного сотрудника: RLS, персональные запреты и права проверяются как в вебе.

Сессия создаётся для одного сообщения и завершается `signOut({scope: "local"})`, чтобы не завершать браузерные сессии сотрудника. Пароли, access/refresh-токены не сохраняются в базе и журналах Nexus. Учётная запись с подтверждённым MFA не поддерживается этим способом: сервер отказывает вместо обхода второго фактора. Supabase Auth регистрирует вход, а аварийное завершение процесса может помешать очистке созданной сессии.

Права проверяются при получении сообщения, перед каждым инструментом и перед отправкой ответа. Привязка повторно проверяется перед отправкой. В Telegram фиксированный список девяти инструментов; новые веб-инструменты автоматически не включаются. Финансовых инструментов, данных водителей и исходных файлов нет. Ответ дополнительно маскирует персональные данные и суммы. Лимит 20 вопросов и месячный бюджет общий с веб-чатом.

## Доставка и ограничения

`getUpdates` забирает сообщения, локальный воркер передаёт только разрешённые поля внутреннему `/api/telegram/process`. Маршрут проверяет отдельный серверный секрет; исключение из cookie-прокси действует только для этого точного пути. Telegram-токен не отправляется браузеру. Группы, каналы, боты и изменённые сообщения игнорируются.

Уникальный `update_id` сохраняется до запуска модели. Повторы не обрабатываются. Перед отправкой выставляется `delivery_started`. Если процесс завершится после захвата или во время отправки, ответ может потеряться: автоматического повторного запуска и повторной отправки нет, сотрудник задаёт вопрос снова. Такой выбор предотвращает дубли и повторный расход. В таблице обновлений нет вопросов и ответов. Привязки и отключения записываются в `audit_log` без одноразовых кодов и сессий.

Истории диалога нет: каждый вопрос самостоятельный. Ответ отправляется простым текстом без интерпретации HTML/Markdown от модели, до 3900 UTF-16 единиц; длинные ответы сокращаются. Ссылки на localhost не отправляются, поскольку они не открывают компьютер сотрудника с телефона.

## Проверка

Node-тесты проверяют личные чаты, маскирование, временную сессию и отказ при MFA, безопасные ошибки Bot API и правила каналов. SQL-тесты проверяют одноразовую ссылку, подтверждение, RLS чужой привязки, отзыв доступа и дедупликацию. Все внешние вызовы в автоматических тестах подменены. Живой сценарий требует применённой миграции и привязки владельца; успешный `getMe` сам по себе не подтверждает работу Auth или ответы по бизнес-данным.

Круглосуточный облачный режим с webhook, очередью и восстановлением заданий — отдельный этап. Текущий внутренний маршрут не является webhook Telegram.
