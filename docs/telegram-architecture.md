# Telegram-канал ассистента: архитектурное решение (следующий этап)

Статус: решение, реализация не начата.

Telegram — второй канал того же `runAgent` (`src/lib/agent/runner.ts`) с той же логикой:
- инструменты;
- маскирование;
- проверка фактов (факты собирает код; пояснения модели отправляются отдельным блоком с пометкой «не проверено»);
- общий дневной лимит (`agent_runs.channel = 'telegram'`).

Канал отличается только способом получения сессии, очередью заданий и доставкой ответа.

## 1. Запросы с правами связанного пользователя

Требования: бизнес-данные читаются с сессией связанного сотрудника, так что RLS и `has_permission` работают как в вебе. Пароль сотрудника и широкое чтение через `service_role` не используются. Совместимость способов ниже с текущей конфигурацией Supabase этого проекта **не проверена**. Перед реализацией нужен отдельный технический прототип на тестовом проекте Supabase. До его результата ни один вариант не считается готовым решением.

**Вариант A (предпочтительный, если подтвердится): короткоживущий пользовательский JWT, подписанный ключом Nexus.**

Как работает:
- Сервер выпускает токен:
  - `sub` = `user_id` активной привязки;
  - `role` = `authenticated`, `aud` = `authenticated`;
  - `exp` ≤ 5 минут.
- Supabase-клиент вызывается с publishable-ключом и заголовком `Authorization: Bearer <токен>`.

Что проверить в прототипе:
1. Позволяет ли проект Supabase принимать JWT, подписанный ключом, закрытая часть которого есть у Nexus. Варианты:
   - импорт собственного асимметричного ключа в JWT Signing Keys;
   - использование legacy JWT-секрета проекта.

   Ключи, которые генерирует сам Supabase, закрытую часть не отдают, и подписать ими токен на сервере Nexus нельзя.
2. Принимают ли PostgREST и Storage такой токен без сессии Auth (`auth.uid()`, RLS, `my_permissions`). Не ломает ли его отсутствие утверждения `session_id` / `aal` в существующих политиках.
3. Как поведут себя отзыв и ротация ключа: выпущенный токен нельзя отозвать до истечения срока.

Ограничения:
- Компрометация ключа подписи позволяет действовать от имени любого сотрудника. Ключ хранится только на сервере, отдельно от прочих секретов, с регулярной ротацией.
- Legacy JWT-секрет одновременно подписывает и `service_role`-токены, поэтому его утечка опаснее.

**Вариант B (запасной): одноразовая серверная сессия через Supabase Auth.**

Как работает:
- Сервер вызывает `auth.admin.generateLink({ type: "magiclink" })` для связанного пользователя и сразу обменивает токен на сессию (`verifyOtp`) в памяти.
- Сессия используется для одного задания и не сохраняется.

Плюсы:
- Настоящая сессия Auth: RLS и все проверки работают без изменений.
- Ключ подписи не нужен.

Ограничения:
- Нужен секретный ключ для одного административного вызова Auth. Бизнес-данные им не читаются, но сам ключ остаётся мощным. Это требует явного согласия владельца, так как отходит от правила «без `service_role`».
- Каждое задание создаёт запись входа в журнале Auth.
- Совместимость с текущими настройками Auth (запрет самостоятельной регистрации, MFA) нужно проверить.

**Служебные операции воркера** при любом варианте:
- очередь, поиск привязки по `chat_id`, захват задания, отметка отправки;
- выполняются функциями `telegram_*` / `agent_job_*`, у которых нет доступа к бизнес-таблицам.

Под какой ролью их вызывать — отдельная роль PostgreSQL с членством `authenticator` или узкий серверный ключ — тоже определяет прототип. Ограничения ролей PostgREST в Supabase могут не позволить собственную роль.

## 2. Подтверждение привязки в авторизованном Nexus

Привязка подтверждается двусторонне:
1. Сотрудник в Nexus («Ассистент → Telegram», сессия Nexus, право `agent.use`) нажимает «Привязать». RPC с его сессией создаёт одноразовый код: 128 бит, в базе хранится только хэш, срок жизни 10 минут, не больше 3 активных кодов. Nexus показывает ссылку `t.me/<бот>?start=<код>`.
2. Бот получает `/start <код>`. Принимаются только личные чаты (`chat.type = private`, `chat.id = from.id`). Воркер проверяет код (хэш, срок, неиспользованность) и создаёт **ожидающую** привязку: `user_id`, `telegram_user_id`, `chat_id`, отображаемое имя.
3. Сотрудник снова в Nexus видит «Чат @имя (ID …) просит доступ» и подтверждает своей сессией. Только после этого привязка активна. Перехват кода без входа в Nexus ничего не даёт.
4. Отвязать чат можно в Nexus в любой момент. Администратор может отозвать привязку.

Привязка неактивна, если:
- профиль неактивен;
- `user_type <> 'employee'`;
- нет права `agent.use`.

Ограничения:
- Один Telegram-аккаунт на сотрудника.
- Групповые чаты не поддерживаются.
- Смена телефона в Telegram не влияет: привязка идёт по `telegram_user_id`.

## 3. Устойчивая обработка вебхуков на Vercel

- **Приём.** `POST /api/telegram/webhook`:
  - проверка `X-Telegram-Bot-Api-Secret-Token` сравнением за постоянное время;
  - тело ≤ 64 КБ;
  - принимаются только сообщения из личных чатов;
  - сохранение задания в `agent_jobs` с уникальным `telegram_update_id` — повтор вебхука не создаёт дубль;
  - ответ 200 сразу.

  Текст сообщения маскируется **до** сохранения. Исходный текст не хранится; если очистка невозможна, задание отклоняется с подсказкой.
- **Обработка.** После ответа вебхуку обработка запускается через `after()` того же вызова (`maxDuration` 60 секунд). Независимо от этого Vercel Cron раз в минуту вызывает `/api/telegram/worker` (защита `CRON_SECRET`) и забирает:
  - задания в очереди;
  - зависшие задания (`status = 'running'` и истёкший `lease_until`).

  Захват заданий:
  ```sql
  update agent_jobs set status = 'running', lease_until = now() + interval '90 seconds', attempts = attempts + 1
  where id = (select id from agent_jobs where (status = 'queued' and next_attempt_at <= now())
                 or (status = 'running' and lease_until < now())
              order by created_at for update skip locked limit 1)
    and attempts < 3
  returning *;
  ```
- **Повторы:** 3 попытки с паузой 30 секунд и 2 минуты. Затем статус `failed`, сотруднику одно сообщение «не удалось, повторите», запрос возвращается в дневной лимит.
- **Защита от дублей ответа.** У Telegram Bot API нет ключа идемпотентности для `sendMessage`, поэтому гарантировать «ровно один раз» нельзя. Выбранная политика — повторно не отправлять:
  - перед `sendMessage` ставится `reply_started_at`, после успешного ответа API — `reply_sent_at`;
  - если повторная обработка видит `reply_started_at` без `reply_sent_at`, ответ не отправляется, задание закрывается как `delivery_unknown`, а сотрудник видит в Nexus, что ответ мог не дойти.

  Остающиеся риски:
  - **Дубль возможен.** Если сетевой сбой случился после того, как Telegram принял сообщение, но до записи `reply_started_at` в базу, повторная обработка отправит ответ ещё раз. Так бывает, например, когда отметка не сохранилась из-за обрыва соединения с базой. То же возможно, если администратор вручную перезапустит задание.
  - **Потеря возможна.** Если сбой случился после записи `reply_started_at`, а сообщение не дошло, ответ не будет отправлен повторно автоматически: сотрудник задаёт вопрос снова.
  - Дубль входящего сообщения исключён уникальностью `telegram_update_id`. Сотрудник при этом может отправить тот же текст дважды — это два разных вопроса, и оба засчитываются в лимит.

Ограничения:
- Cron раз в минуту требует тарифа Vercel Pro. На Hobby нужен внешний планировщик, например GitHub Actions по расписанию с тем же секретом.
- Задержка восстановления зависшего задания — до 1–2 минут.

## 4. Проверка прав при обработке и перед отправкой

Права проверяются трижды:
1. **При захвате задания:** привязка активна, профиль активен, `agent.use` (через `my_permissions` с JWT пользователя).
2. **Перед каждым вызовом инструмента:** как в вебе (`runAgent`).
3. **Непосредственно перед `sendMessage`:** привязка и `agent.use` проверяются заново. Если доступ потерян за время обработки, ответ не отправляется, задание закрывается `rejected`.

## 5. Закупочные цены и себестоимость, в том числе через файлы и OCR

Политика канала строже веба: в Telegram закупочные цены и себестоимость не выводятся никогда, даже держателям `prices.purchase.view`. Как это обеспечивается:
- Финансовых инструментов нет. Набор инструментов канала — разрешённый список из `AGENT_TOOLS` без финансовых. Добавление нового инструмента в Telegram — отдельное решение.
- Вложения от пользователя не обрабатываются: документы, фото и файлы отклоняются с подсказкой загрузить их в Nexus. OCR из Telegram не запускается.
- Ответ — только текст. Файлы, выгрузки и ссылки на скачивание не отправляются; ссылки ведут на карточки Nexus, где снова действуют права.
- Перед отправкой весь текст проходит `maskDataText`, который скрывает суммы с валютой, и общее маскирование персональных данных.
- Данные из распознавания идут только через `EXTRACTION_ALLOWED_FIELDS`: без позиций и цен ЭСФ, условий оплаты и реквизитов.

## 6. Отдельный бюджет распознавания речи

Голос выключен, пока не заданы `STT_ENABLED` и `STT_ACKNOWLEDGE_DATA_TRANSFER`.

Порядок обработки голосового сообщения:
- До скачивания проверяется `message.voice.duration` (≤ 60 секунд) и размер (≤ 1 МБ).
- Аудио скачивается в память и не сохраняется.
- Расшифровка — это вопрос пользователя: маскируется, в трассу попадает только выдержка.

Отдельный учёт речи:
- Лимит секунд в сутки на сотрудника: `agent_settings.stt_daily_seconds_limit`, по умолчанию 300.
- Месячный денежный бюджет речи: `stt_monthly_budget_usd_micros`. Расход хранится в `agent_budget_months` в отдельных столбцах `stt_spent_usd_micros` и `stt_seconds`.
- Резерв по заявленной длительности делается атомарно, как для вопросов.
- Расшифровка тоже расходует один вопрос из общего дневного лимита.

Ограничения:
- Длительность сообщает Telegram; фактическую списываем по ответу провайдера.
- Бюджет речи — лимит Nexus, а не предел счёта провайдера.
