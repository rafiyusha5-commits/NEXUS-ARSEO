# Атомарная отгрузка заказа

Основа: `integration/nexus-ui-agents-20261012`, `ca194e8165350f2d53d583d6826fa370043ea992`.
Ветка реализации: `feature/customer-order-fulfillment`. Не зависит от тестового PR №9.

## Использование

После применения миграции `202609276600_customer_order_fulfillment.sql` владельцем
вкладка «Отгрузка» подтверждённого заказа показывает кнопку «Отгрузить заказ полностью».
Она вызывает `fulfill_customer_order(p_sale_id uuid)` через клиент текущего сотрудника.
Миграция в рабочей БД при разработке **не применялась**.

Нужны оба существующих разрешения: `sales.manage` **и** `inventory.move`.
Новых прав ролям не добавлено; индивидуальный deny сохраняется. UI проверяет те же
разрешения через `my_permissions`, но окончательная защита находится в RPC.
`anon`, `PUBLIC` и `service_role` не имеют EXECUTE. Прямые клиентские записи по-прежнему запрещены.

## Контракт операции

Одна транзакция:

1. Проверяет сотрудника и права; блокирует заказ `FOR UPDATE`.
2. При уже выполненной этой операцией отгрузке возвращает тот же ID без изменений.
   Иначе допускает только `confirmed`, непустой заказ и точный активный резерв каждой строки.
3. Блокирует позиции, резервы, остатки, партии и гарантийные письма; проверяет соответствие
   товара, склада, партии и единицы измерения (единица резерва совпадает с единицей остатка; при заказе в других
   единицах — см. пересчёт через упаковку в [`customer-orders-fefo.md`](./customer-orders-fefo.md)). Сумма активных резервов всех заказов на остатке
   должна совпадать с `quantity_reserved`.
4. Отказывает заблокированным/карантинным/просроченным партиям (как исправить такой заказ без отмены — см. «Если после подтверждения что-то изменилось» в [`customer-orders-fefo.md`](./customer-orders-fefo.md)). Пересчитывает ОСГ на более
   позднюю из текущей UTC-даты (после ожидания блокировок) и плановой даты. При низком ОСГ
   требует действующее письмо на те же партии, количества и требования; ухудшившийся
   относительно согласованного письма ОСГ не принимает. Дату от клиента RPC не принимает.
5. Списывает **именно зарезервированные** партии: уменьшает одновременно физический остаток
   и резерв, создаёт `issue` для каждого резерва, помечает резерв `fulfilled`.
6. Обнулившиеся во всех местах партии переводит в `depleted`; заказ — в `shipped`,
   сохраняет `shipped_at` и `shipped_by`. Штатные audit-триггеры остаются включены.

У движения есть FK `sale_id`, `sale_item_id`, `inventory_reservation_id`; уникальный
индекс по последнему полю дополнительно запрещает второе движение для того же резерва.
Номер заказа сохранён в `reference` журнала. Любая ошибка откатывает все изменения,
включая движения и audit-записи. Никакого нового FEFO-подбора на этапе отгрузки нет.

Два запроса одного заказа сериализуются на строке заказа: второй возвращает уже выполненный
результат. Отмена использует ту же блокировку: выигрывает либо отмена (резерв освобождён,
списания нет), либо отгрузка (отмена отклонена). Если связь потеряна после commit, повтор
того же RPC безопасен. Старый `shipped` без `shipped_at` не считается доказанной отгрузкой
новой операции и автоматически не исправляется.

## Проверки и запуск

Требуются зависимости из lockfile, Node 24, Docker/Linux containers с локальным `postgres:16`.
Runner не загружает образ автоматически (`--pull=never`), не читает `.env`, не принимает URL БД,
не публикует порты. Контейнер `nexus-fulfillment-<UUID>` имеет `--network=none`, tmpfs PGDATA;
после теста удаляется только этот контейнер. При принудительном завершении процесса нужно
проверить оставшиеся контейнеры с этим префиксом и удалить только контейнер своего запуска.

```sh
corepack pnpm install --frozen-lockfile --ignore-scripts
corepack pnpm typecheck
corepack pnpm lint
corepack pnpm test
corepack pnpm build
corepack pnpm test:db:docker
```

Последняя команда запускает штатный `scripts/test-db.sh` в PostgreSQL 16, включая
security audit, повторное применение миграций и конкурентные тесты. На Linux с PostgreSQL 16
можно использовать непосредственно `corepack pnpm test:db`. Для обычного `pnpm test`
не задавайте `NEXUS_OCR_TEST_URL`/`NEXUS_OCR_TEST_TOKEN`: реальные OCR-вызовы не нужны.

Новые проверки используют исключительно вымышленные данные (`example.invalid`, `SYNTH-*`):

- Две партии, 300 штук на складе; заказ A резервирует 150 (100 + 50), заказ B — 50.
  После отгрузки A: физически 150, резерв B 50, два движения на 150, резервы A fulfilled.
- Повтор не меняет движения, остатки, исполнителя или время отгрузки; уникальный индекс
  отклоняет попытку дубля. Отмена уже отгруженного заказа запрещена.
- Личные запреты каждого из двух необходимых прав; ACL функции и отсутствие прямой записи.
- Неподтверждённый заказ, неполный резерв, несогласованный общий резерв, неверные
  единица/партия/склад, блокировка, просрочка, отменённое и устаревшее гарантийное письмо.
- Искусственная ошибка на **втором** движении после первого списания: ни одного
  частичного движения/списания/погашенного резерва после отката.
- Десять параллельных RPC одного заказа: одна отгрузка. Параллельные отгрузка и отмена
  второго заказа: один победитель и согласованные остатки/резервы/журнал.
- Server Action с подменными auth/RPC: один вызов от сотрудника, проверка UUID,
  обновление кэша только после успеха, отсутствие сырых SQL-ошибок и вызова без входа.

Бизнес-даты фикстуры фиксированы (2098/2099); при наступлении 2099-01-01 тест требует их
явного пересмотра. Clock PostgreSQL не подменяется; реальный RPC всегда проверяет текущую дату.
Проверки повреждения данных и инъекции ошибки выполняются только владельцем одноразовой
тестовой БД в откатываемых savepoint, не через обход защиты в рабочей операции.

## Ограничения

- Только полная отгрузка, без частичной отгрузки, возврата и отмены выполненного расхода.
- При устаревшем/отозванном письме подтверждённый заказ блокируется. Существующий workflow
  не обновляет письмо в confirmed; нужно отменить заказ и заново согласовать новый,
  а не менять данные прямым SQL. Workflow пересогласования — отдельная задача.
- Права намеренно не расширены: сотруднику с одним только управлением продажами или
  одним только складским движением отгрузка недоступна.
- Произвольные конкурентные складские операции могут привести к обнаруженному PostgreSQL
  deadlock/serialization failure: транзакция откатится, операцию можно безопасно повторить.
  Автоматического повторения всех ошибок нет. Проверены конкретно дубли и гонка с отменой,
  а не все возможные сочетания складских операций.
- Проверено SQL/RPC и server action с подменным транспортом; браузерный E2E и реальная
  Supabase/PostgREST-интеграция не запускались. Google, Telegram, реальные документы,
  рабочая БД и платные сервисы не использовались.
- D1 (этап закрытия поставки) и D2 (комплектность CMR в итоговом отчёте) из PR №9
  не исправляются этим изменением. Финансовое закрытие и печатные документы не входят в задачу.

Миграция аддитивна и проверяется повторным применением. Для выпуска сначала применяется
миграция, затем приложение. После реальной отгрузки нельзя просто удалять новые поля или
индекс: они сохраняют связь неизменяемых движений с заказом и защиту от дублей.
