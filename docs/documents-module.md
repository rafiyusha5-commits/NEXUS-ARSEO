# Модуль «Документы»

Основа документооборота Nexus-ARSEO: реестр документов, версии файлов, связи с поставками и другими объектами, обязательные документы и закрытое хранилище файлов.

## Что реализовано

| Часть | Где |
|---|---|
| Таблицы, права, RLS, bucket и политики Storage | `supabase/migrations/202609271001_document_management.sql` |
| Правила файлов (тип, размер, имя, путь) | `src/lib/documents/files.ts` |
| Сроки действия, требования, поиск, проверка реквизитов | `src/lib/documents/rules.ts` |
| Серверные операции (регистрация, версия, архив, скачивание) | `src/lib/documents/operations.ts`, `supabase-gateway.ts` |
| Реестр `/documents` и регистрация документа | `src/app/documents/page.tsx`, `actions.ts` |
| Карточка `/documents/[id]` | `src/app/documents/[id]/page.tsx` |
| Скачивание по временной ссылке | `src/app/documents/[id]/download/route.ts` |
| Блок «Документы поставки» | `src/components/documents/shipment-documents-panel.tsx` |
| Тесты | `tests/documents/*.test.ts`, `supabase/tests/documents_rls.test.sql` |

## 1. Как применить миграцию

Миграция применяется после `202609270004_service_role_grants.sql`. Она идемпотентна: повторный запуск ничего не ломает и не перезаписывает изменения, которые администратор сделал в интерфейсе (права ролей, типы документов, требования).

**Через SQL Editor Supabase:** откройте файл `supabase/migrations/202609271001_document_management.sql`, вставьте его целиком в SQL Editor и выполните.

**Через Supabase CLI:**

```bash
supabase db push
```

После применения проверьте:

```sql
select code from public.permissions where module = 'documents' order by code;
-- documents.archive, documents.create, documents.manage, documents.manage_requirements,
-- documents.manage_types, documents.update, documents.view

select count(*) from public.document_types;          -- 15 типов
select id, public, file_size_limit from storage.buckets where id = 'nexus-documents';
-- nexus-documents | false | 4194304
```

## 2. Storage bucket `nexus-documents`

Миграция сама создаёт **приватный** bucket `nexus-documents` и политики доступа к файлам, если в базе есть схема `storage` (в Supabase она есть всегда). Если схемы нет, миграция выводит уведомление и продолжает работу — тогда bucket нужно создать вручную.

### Проверка

```sql
select id, public, file_size_limit, allowed_mime_types
from storage.buckets where id = 'nexus-documents';

select policyname, cmd from pg_policies
where schemaname = 'storage' and tablename = 'objects' and policyname like 'nexus documents:%';
-- read registered files (SELECT), upload into document folder (INSERT),
-- remove own unregistered upload (DELETE)
```

### Ручное создание (если bucket отсутствует)

1. Supabase → **Storage** → **New bucket**.
2. Name: `nexus-documents`. **Public bucket: выключено.**
3. Additional configuration: File size limit — `4 MB`; Allowed MIME types:
   `application/pdf`, `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `application/vnd.ms-excel`, `text/csv`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `image/jpeg`, `image/png`.
4. Выполните миграцию ещё раз — она создаст политики доступа к файлам (раздел 9 миграции) и не изменит остальное.

Bucket нельзя делать публичным: файлы выдаются только по временной подписанной ссылке.

Если bucket отсутствует, при загрузке пользователь видит сообщение: «Хранилище документов не настроено… Администратору: примените миграцию… или создайте bucket вручную».

## 3. Переменные окружения

Новых переменных нет. Модулю нужны уже существующие:

| Переменная | Где используется |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | подключение к Supabase |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | подключение от имени вошедшего пользователя |

`SUPABASE_SECRET_KEY` / `SUPABASE_SERVICE_ROLE_KEY` модулем документов **не используются**: все операции выполняются от имени вошедшего сотрудника и проверяются RLS. У роли `service_role` нет прав на таблицы документов.

## 4. Ограничения файлов

| Правило | Значение | Где задано |
|---|---|---|
| Максимальный размер | **4 МБ** (4 194 304 байта) | `MAX_DOCUMENT_FILE_SIZE_BYTES` в `src/lib/documents/files.ts`; лимит bucket; `CHECK` в `document_versions.file_size_bytes` |
| Размер запроса Server Action | 4 400 000 байт | `next.config.ts` → `experimental.serverActions.bodySizeLimit` |
| Форматы | PDF, XLSX, XLS, CSV, DOCX, JPG/JPEG, PNG | `DOCUMENT_FILE_KINDS` в `files.ts`; `allowed_mime_types` bucket; `CHECK` в `document_versions.mime_type` |

Почему 4 МБ: файлы загружаются только через серверный код, а Vercel не принимает тело запроса к серверной функции больше ~4,5 МБ. Чтобы увеличить лимит, нужно изменить все три места и перейти на загрузку по одноразовой подписанной ссылке Storage (см. «Известные ограничения»).

Проверки при загрузке (на сервере):

1. право `documents.create` (новый документ) или `documents.update` (новая версия) — до чтения файла;
2. расширение из списка и соответствие заявленного браузером типа расширению;
3. размер по фактически полученным байтам;
4. сигнатура содержимого (PDF — `%PDF-`, PNG, JPEG, ZIP для XLSX/DOCX, OLE для XLS, отсутствие нулевых байтов для CSV) — переименованный файл другого типа отклоняется;
5. SHA-256: тот же файл нельзя зарегистрировать повторно — пользователь получает ссылку на уже существующий документ.

Имя файла нормализуется (транслитерация кириллицы, только `A-Z a-z 0-9 . _ -`, без каталогов, до 120 символов). Путь всегда строит сервер: `documents/<id документа>/<32 случайных hex>-<имя>`. Пользователь не может передать свой путь: база проверяет формат пути, принадлежность папке документа и то, что файл загрузил тот же пользователь. Исходное имя файла хранится в базе для отображения.

## 5. Как проверить загрузку

1. Войдите сотрудником с ролью, у которой есть `documents.create` (например, `logistics_specialist`).
2. Откройте **Документы** → «Зарегистрировать документ». Выберите тип «Инвойс», введите название, выберите поставку в поле «Основной связанный объект», приложите PDF до 4 МБ.
3. После сохранения откроется карточка: версия 1, автор, связь с поставкой. Нажмите «Скачать» — файл откроется по ссылке, действующей 60 секунд.
4. Загрузите исправленный файл как новую версию — версия 2 станет актуальной, версия 1 останется в истории.
5. Откройте поставку — в блоке «Документы поставки» виден инвойс, статус, обязательность и список недостающих обязательных документов.
6. Попробуйте загрузить `.exe`, файл больше 4 МБ или PNG, переименованный в `.pdf`, — загрузка будет отклонена с понятным сообщением.
7. Войдите пользователем без `documents.view` (например, `marketer`) — реестр покажет сообщение об отсутствии доступа, а прямые запросы к таблицам вернут пустой результат.
8. В **Журнале действий** видны записи о регистрации, версиях, связях, архивировании и скачивании.

Автоматические проверки:

```bash
pnpm test      # правила файлов, путей, прав, архивирования и версий (Node test runner)
pnpm test:db   # все миграции + RLS на локальном PostgreSQL 15+ (нужны initdb и pg_ctl)
```

`pnpm test:db` поднимает временный кластер PostgreSQL, применяет упрощённую замену Supabase (`supabase/tests/supabase_stub.sql`, только для тестов), все миграции, повторно применяет миграцию документов (проверка идемпотентности) и выполняет `supabase/tests/documents_rls.test.sql`.

## 6. Права доступа

| Право | Что разрешает | Роли по умолчанию |
|---|---|---|
| `documents.view` | реестр, карточки, связи, версии, скачивание | все роли, кроме `marketer` |
| `documents.create` | регистрация документа с первым файлом и начальными связями | все роли, кроме `marketer` |
| `documents.update` | реквизиты, статус, новые версии, добавление и снятие связей | все роли, кроме `marketer` |
| `documents.archive` | перенос в архив (без удаления) | `director`, `administrator` |
| `documents.manage_types` | справочник типов документов | `director`, `administrator` |
| `documents.manage_requirements` | обязательные документы для процессов и этапов | `director`, `administrator`, `logistics_director` |

Права выдаются и отзываются в **Роли и права** или индивидуально (разрешение или запрет пользователю). Повторный запуск миграции не возвращает отозванные права.

Как это работает:

- все проверки выполняет база: `private.has_permission()` учитывает роли, отключённые роли, срок назначения роли, индивидуальные разрешения и запреты, активность профиля и тип пользователя (внешний пользователь не получает доступ, даже если ему выдано право);
- у `authenticated` есть только нужные столбцы: пользователь не может изменить путь файла, номер версии, автора или поля архивирования;
- удаления нет ни у кого: документы архивируются функцией `archive_document()` с обязательной причиной, связи снимаются с отметкой, кто и когда это сделал;
- версии неизменяемы;
- `documents.create` без `documents.view` позволяет зарегистрировать документ, но не видеть реестр — так можно дать право загрузки без доступа к чужим документам;
- `documents.manage` из первой миграции сохранён для совместимости, но правилами модуля не используется;
- все изменения пишутся в `audit_log` триггером базы, скачивания — сервером.

### Политики Storage (`storage.objects`, bucket `nexus-documents`)

| Действие | Условие |
|---|---|
| Чтение | `documents.view` и файл зарегистрирован как версия документа; либо свой ещё не зарегистрированный файл |
| Загрузка | `documents.create` или `documents.update`, путь `documents/<uuid>/<32 hex>-<безопасное имя>`, владелец — текущий пользователь |
| Удаление | только свой **незарегистрированный** файл младше часа (очистка после неудачной регистрации) |
| Изменение | запрещено |

## 7. Связи с объектами

`document_links` хранит `entity_type`, `entity_id`, назначение связи (`primary`, `related`, `supporting`). Допустимые типы: `shipment`, `shipment_transport`, `supplier`, `customer`, `product`, `warehouse`, `contract`, `customer_return`.

Обычный внешний ключ здесь невозможен: один столбец ссылается на разные таблицы. Поэтому:

1. список типов ограничен `CHECK`;
2. триггер `private.validate_document_link_target()` сопоставляет каждому типу одну фиксированную таблицу (имя таблицы не берётся из пользовательского ввода) и проверяет, что запись существует;
3. триггер работает с правами пользователя, поэтому связать документ можно только с объектом, который пользователь видит;
4. для `supplier` и `customer` проверяется роль контрагента;
5. `customer_return` принимается только после появления таблицы возвратов (сейчас возвращается понятная ошибка).

Бизнес-объекты не удаляются физически, поэтому «висячих» связей в обычной работе не возникает. Проверка на всякий случай:

```sql
select l.* from public.document_links l
where l.removed_at is null and (
  (l.entity_type = 'shipment' and not exists (select 1 from public.shipments s where s.id = l.entity_id)) or
  (l.entity_type = 'shipment_transport' and not exists (select 1 from public.shipment_transports t where t.id = l.entity_id)) or
  (l.entity_type in ('supplier', 'customer') and not exists (select 1 from public.counterparties c where c.id = l.entity_id)) or
  (l.entity_type = 'product' and not exists (select 1 from public.products p where p.id = l.entity_id)) or
  (l.entity_type = 'warehouse' and not exists (select 1 from public.warehouses w where w.id = l.entity_id)) or
  (l.entity_type = 'contract' and not exists (select 1 from public.contracts c where c.id = l.entity_id))
);
```

## 8. Обязательные документы

`document_requirements` задаёт, какой тип документа нужен: для поставок или перевозок, с фильтрами по типу поставки, шаблону процесса, этапу и маршруту, признак обязательности, срок в днях от начала этапа или текстом, дополнительные условия в `conditions` (пока справочно, не вычисляются).

Миграция добавляет предварительные требования для шаблона `import_eu_kz`: инвойс и упаковочный лист (обязательны, этап проверки документов), спецификация и сертификат (необязательны), CMR (обязателен, отгрузка), таможенный документ (необязателен). Перечень **требует подтверждения ARSEO** (вопрос М4 в `open-questions.md`); менять его могут пользователи с `documents.manage_requirements` (экран настройки требований — в следующей итерации, пока через SQL Editor).

## 9. Как откатить только код

Откат кода не удаляет пользовательские документы: таблицы, файлы в bucket и журнал остаются в Supabase.

1. Откатите коммиты модуля (`git revert` коммитов «Add documents registry…» и «Add server-side document file rules…») или разверните на Vercel предыдущий деплой.
2. **Не удаляйте** таблицы `document_*`, bucket `nexus-documents` и политики Storage — это уничтожит документы и историю.
3. Чтобы временно закрыть доступ без отката кода, отзовите `documents.view` у ролей в **Роли и права**: данные сохранятся, а RLS перестанет их показывать.
4. После возврата кода модуль продолжит работу с теми же данными — повторно применять миграцию не нужно.

Полное удаление модуля из базы (таблиц, функций, bucket) этой инструкцией не предусмотрено: это необратимая операция, решение принимает ARSEO, перед ней нужна выгрузка документов.

## 10. Известные ограничения

- **Размер файла — 4 МБ** из-за лимита Vercel на тело запроса. Для крупных сканов нужен переход на одноразовые ссылки загрузки Storage (`createSignedUploadUrl`), при котором путь и проверки по-прежнему задаёт сервер.
- **Загрузка только через наш сервер не может быть навязана базой полностью.** Сервер работает с сессией пользователя, поэтому тот же пользователь технически может загрузить файл в Storage напрямую через API. Такой файл ограничен политиками (путь, размер, типы), не становится документом без проверок базы и может быть удалён только пока не зарегистрирован. Строгий вариант — загрузка сервисным ключом на сервере — отклонён, чтобы не расширять использование `service_role`.
- **Ограниченный доступ («О» в матрице прав)** пока не применяется: функция `private.has_permission()` не учитывает `scope`. Например, маркетологу нельзя открыть только сертификаты — поэтому по умолчанию он не видит документы.
- Статусы документа меняет любой пользователь с `documents.update`; отдельного права на согласование документов пока нет.
- Повторная регистрация одного файла блокируется по SHA-256 только среди документов, которые пользователь видит.
- `conditions` в требованиях пока не вычисляются; экрана настройки типов и требований нет.
- Распознавание содержимого PDF и сверка с поставкой не реализованы.
- Связь с возвратами заработает после появления таблицы `customer_returns`.
