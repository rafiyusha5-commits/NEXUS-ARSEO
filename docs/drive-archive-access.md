# Исправления доступа к архиву (база 73cd99a)

## Серверная граница и развёртывание

Миграция `202609276200_drive_archive_access.sql` добавляет restrictive RLS к
`drive_catalog_files` и `drive_catalog_text`. Пользовательский JWT без дополнительного
серверного заголовка не читает строки напрямую, через полнотекстовый RPC, REST или
GraphQL. Прежние проверки ролей, личных запретов, активности и закупочных цен сохраняются.
`service_role` не получает новых прав чтения таблиц или RPC. Импорт/OCR остаются на
существующем узком `drive_catalog_sync_step`.

Серверный `catalogGateway` использует publishable key и JWT текущего сотрудника,
добавляя отдельный секрет только к запросам каталога. Он не принимает заголовки от
браузера и не возвращает свой клиент или сырые результаты RPC наружу. `catalog-access`
проверяет текущих родителей и версию Drive, повторно проверяет права после чтения,
фильтрует результаты поиска и пересчитывает счётчики. Исчезновение миграции или ошибка
шлюза не переводят чтение на незащищённый запасной путь.

Перед вводом в эксплуатацию (не выполнено разработчиком):

1. Остановить запросы архива/ассистента и локальный Telegram worker, дождаться завершения
   запросов. Развернуть новый код и миграцию согласованно, перезапустить процессы для
   очистки кратковременной памяти диалогов.
2. Создать случайный секрет из 32 байт, представленный 64 строчными hex-символами.
   Хранить его только в серверном `DRIVE_CATALOG_GATEWAY_SECRET`, без `NEXT_PUBLIC_`.
3. Через доверенное соединение владельца БД записать SHA-256 **UTF-8 hex-строки секрета**
   в `private.drive_gateway_config(id,secret_sha256)` с `id=true` (upsert). Не хранить
   исходный секрет в SQL-файлах, логах или репозитории. При ротации заменить обе стороны.
4. Проверить прямое чтение с пользовательским JWT: ноль строк текста/метаданных.
   Проверить разрешённое чтение через Nexus и отказ при личном запрете.
5. Через интерфейс выполнить обычное обновление каталога, затем OCR-пакеты при
   необходимости. Настройка OCR и существующая модель ролей не меняются.

Без настроенного секрета/хэша шлюз закрыт. Это намеренное условие, а не автоматическая
выдача доступа. Секреты и рабочая конфигурация при разработке не использовались.

## Очистка и трассы

Миграция однократно удаляет ранее извлечённый текст и его поисковый индекс, отменяет
активные квитанции импорта/OCR и ставит документы на повторную обработку. Метаданные,
оригиналы Drive, роли и настройки OCR сохраняются. OCR-текст надо распознать заново;
его счётчик попыток обнуляется. Повторное применение миграции не удаляет новый текст.
Удалённый производный текст восстанавливается повторным чтением источника, не откатом
небезопасной копии. Старые резервные копии БД требуют отдельной политики хранения.

В существующих и будущих `agent_runs` удаляются выдержки вопросов и все значения
параметров инструментов. Сохраняются имя инструмента, число строк, длительность,
ошибки, токены и финансовый учёт самого провайдера. Триггер БД обрабатывает также
поздние записи старых процессов; клиентский код тоже не передаёт свободный текст в ledger.

## Ограничения

Проверка Drive и отправка OpenAI/Telegram не образуют распределённую транзакцию:
остаётся минимальное окно между последней проверкой и фактической передачей.
Повторная проверка выполняется перед каждым обращением модели и после подготовки
доставки Telegram; уже отправленные данные отозвать невозможно.

Поиск ограничен 1000 кандидатами, временем запроса и текущими лимитами Drive; неполный
результат отмечается, скрытые/устаревшие кандидаты не входят в выдаваемое количество.
Дополнительные живые проверки увеличивают число GET-запросов. Маскирование не является
полной анонимизацией: допустимость передачи ФИО/email требует отдельной политики.
Подмена инструкций ограничивается существующими read-only инструментами и проверками
прав; вероятностное поведение реальной модели не оценивается локальными mock-тестами.

## Проверки (11 октября 2026)

- `pnpm typecheck`, `pnpm lint` — успешно.
- 531 локальный тест — успешно, включая 13 новых сценариев F1–F6. Из-за Windows
  `spawn EPERM` использован Node `--test-isolation=none`; три оболочки, запускающие
  дочерний Node, исключены, а их проверки выполнены отдельно и успешно.
- Серверные проверки: `archivist-server.check.ts`, `date-search-server.check.ts`,
  `drive-gateway.check.ts` в `tests/agent`. Последняя проверяет JWT сотрудника,
  отсутствие service-role ключа, запрет посторонних таблиц и отсутствие редиректов.
- `scripts/test-db-embedded.mjs`: 55 миграций в чистом PostgreSQL/WASM (PGlite),
  7 SQL-наборов (доступ, каталог, OCR, ассистент/учёт, инструменты и роли), повторное
  применение исправления, очистка старых текстов/трасс/квитанций, сохранность нового
  текста при повторном применении — успешно. Только синтетические данные в памяти.
- Production build остановлен окружением на `spawn EPERM`; сборку необходимо
  повторить в CI. Настоящие Supabase/PostgREST, Google, OCR, LLM и Telegram не вызывались.

Воспроизведение в Windows при ограничении дочерних процессов:

```powershell
$env:NEXUS_OCR_TEST_URL=''; $env:NEXUS_OCR_TEST_TOKEN=''
node --test --test-reporter=spec --test-isolation=none --test-skip-pattern='archivist reads only safe columns|date search uses ready/arrival|drive gateway uses employee JWT' --disable-warning=MODULE_TYPELESS_PACKAGE_JSON "tests/**/*.test.ts"
node --conditions=react-server --import ./tests/agent/server-condition.mjs tests/agent/archivist-server.check.ts
node --conditions=react-server --import ./tests/agent/server-condition.mjs tests/agent/date-search-server.check.ts
node --conditions=react-server --import ./tests/agent/server-condition.mjs tests/agent/drive-gateway.check.ts
```

Для SQL установить `@electric-sql/pglite` в отдельный временный каталог, задать
`PGLITE_MODULE` абсолютным путём к его `dist/index.js` и выполнить
`node scripts/test-db-embedded.mjs`. Скрипт не принимает строку подключения и не
использует рабочую БД. В обычном PostgreSQL-окружении остаётся `pnpm test:db`;
полный нативный SQL-набор и PostgREST-интеграция здесь не запускались.
