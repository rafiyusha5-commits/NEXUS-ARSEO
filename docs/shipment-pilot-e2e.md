# Изолированный пилот поставки

Основа: `4ab9c251c3f5dc3680f72860ecd7dd874a8e6f24`. Ветка: `test/shipment-pilot-e2e`.
Бизнес-код, миграции и права не изменены. Это интеграционный SQL/RPC-пилот с настоящим
загрузчиком отчёта через подменный транспорт, **не браузерный E2E и не подтверждение
готовности полного цикла**. Два известных дефекта воспроизводятся явно; зелёный exit code
означает соответствие зафиксированному результату, а не отсутствие дефектов.

## Запуск

Требуются Node.js 24 (проверено 24.13.0), Corepack/pnpm из package.json, Docker с Linux
containers и заранее доступный образ PostgreSQL 16. Не создавайте `.env` и не передавайте ключи.

```sh
corepack pnpm install --frozen-lockfile --ignore-scripts
# Только если postgres:16 ещё нет; это загрузка публичного образа, не обращение к БД.
docker pull postgres:16
corepack pnpm test:shipment-pilot
# Весь существующий SQL-набор плюс пилот; работает и на Windows:
corepack pnpm test:db:docker
```

`test:db:docker` запускает **тот же** `scripts/test-db.sh`, что и `corepack pnpm test:db`,
внутри PostgreSQL 16, включая before-migration, повторное применение миграций и конкурентные
тесты. Дополнительно запускается пилот два раза на свежей схеме без повторного применения.
На Linux с локальными бинарниками PostgreSQL 16 можно отдельно использовать `corepack pnpm test:db`.

Runner не принимает URL БД, не читает `.env`, не использует Supabase SDK для сети.
Он создаёт контейнер с `--network=none`, без опубликованных портов, с PGDATA на tmpfs
и именем `nexus-pilot-<UUID>`. Trust-аутентификация действует только внутри этого контейнера.
В режиме полного SQL-набора копируются только SQL, штатный runner и публичный demo JSON из репозитория.
В `finally` удаляется исключительно созданный контейнер. При аварийном завершении процесса
проверьте `docker ps -a --filter name=nexus-pilot-` и удалите только контейнер конкретного запуска.
Никаких вызовов Drive/Sheets, Telegram, OCR-провайдера или рабочей Supabase нет.

## Сценарий и контрольные числа

Все новые данные вымышлены: `Synthetic…`, `PILOT-E2E-*`, `example.invalid`.
Публичные RPC выполняются под `authenticated` с тестовым пользователем роли `director`.
Владелец локальной БД создаёт только начальные справочники/права/требование CMR,
вызывает чистую функцию проверки срока на фиксированную дату и выгружает снимок для отчёта.
RLS и защитные триггеры в пилоте не отключаются, `service_role` не используется.

| Участок | Что действительно проверяется |
| --- | --- |
| Импорт справочников | `import_reference_data`: dry run ничего не пишет; повторный apply оставляет два товара |
| Закупка | Прогноз 100 A + 50 B → submit/review/approve → план закупки → submit/review/approve → `create_purchase_plan_shipment`; обе строки связаны с поставкой; повторное создание отклонено |
| Автомобили | A: 60 на первом + 40 на втором, B: 50 на втором; итог 150, нераспределённого груза нет; цены 2/3 EUR через штатное обновление позиции |
| Документ | `register_document`, CMR привязан только к первому автомобилю; повтор того же ID отклонён, одна карточка и одна версия |
| Подменное OCR | begin/finish создают предложение; до review водитель не меняется; review подтверждает исправленные значения только первого автомобиля; повтор OCR возвращает reuse |
| «Сверка» | Находит намеренно неверный вес 999 вместо 60, отсутствие CMR второго автомобиля и просрочку; повтор ручной проверки не дублирует уведомления |
| Перевозка/таможня | Штатные этапы и переходы автомобилей in_transit → arrived; выполненные таможенные этапы фиксируются в БД |
| Приёмка | Первый автомобиль: 57 принято, 1 повреждено, 2 не хватает; второй: 90 принято. Две приёмки, три партии, приход и физический остаток **147**; received в позициях **148**, включая повреждение |
| Повторы | Повтор приёмки каждого автомобиля отклонён; приход не удваивается. Повтор резервирования заменяет резерв, не увеличивая его до 140 |
| Продажа/ОСГ | Заказ A70; FEFO резервирует 57 из ранней партии и 13 из поздней. На 2099-01-20 у ранней партии ОСГ **26,50%** при требовании 60%; без гарантийного письма подтверждение запрещено, после approved — confirmed |
| Остаток | Физически 147, резерв 70, доступно 77. Продажа **не отгружена**, расход по ней не проведён |
| Отчёт | Настоящий `loadShipmentReport`: 150 заказано / 147 принято, расхождение −3, партии = приход = 147, два авто и две приёмки. Без разрешения закупочные цены null, ценовой RPC не вызывается |
| Закрытие | Воспроизводится преждевременный статус closed при незавершённом этапе closed — см. D1 |

SQL обёрнут в транзакцию с rollback. Два полных запуска сравнивают нормализованные
итоги; после них проверяется отсутствие товаров пилота. Повторы операций проверяются
**также внутри одной транзакции до rollback**, на уже созданных документах и приходах.

Даты поставки 2099-01-01/10, продажи 2099-01-20, партий 2098-04-01 → 2099-05-06
и 2098-11-01 → 2099-12-06 фиксированы. Срок CMR проверяется на 2099-01-10
через `private.document_check_findings`. Часы PostgreSQL не подменяются: audit timestamps,
номера и служебные уведомления используют текущую дату. До 2099-01-01 fixture валиден;
после этой даты тест намеренно требует явного пересмотра дат. Это не тест всех граничных
дат всей системы.

## Подтверждённые дефекты

### D1. Нельзя завершить последний этап поставки

- Источник: `supabase/migrations/202609272300_database_security_hardening.sql:466`;
  блокирующий триггер `supabase/migrations/202609272100_shipment_execution.sql:127`.
- Воспроизведение: через `change_shipment_stage_status` завершить этапы до «Закрытие
  поставки», затем попытаться завершить последний этап. Статус поставки уже `closed`,
  последний этап ещё `pending`; RPC получает «Поставка в статусе closed недоступна для изменений».
- Причина: статус вычисляется из категории следующего незавершённого этапа, у которого
  категория уже `closed`. Триггер запрещает дальнейшее изменение дочерних записей.
- Последствие: незавершённый процесс выглядит закрытым, финальная отметка недостижима.
- Предложение (не реализовано): присваивать closed только после успешного завершения
  обязательных этапов, атомарно с последним переходом; сохранить защиту закрытых поставок.

### D2. Отчёт не замечает отсутствующий документ второго автомобиля

- Источник: `src/lib/shipment-report.ts:58` и `src/lib/shipment-report.ts:84`.
- Воспроизведение: обязательный CMR для каждого автомобиля, два автомобиля, один CMR
  связан только с первым. «Сверка» возвращает `document_missing` для второго;
  `loadShipmentReport().missingDocuments` не содержит CMR.
- Причина: запрос требований теряет `applies_to`, а наличие типа документа проверяется
  общим множеством всей поставки без привязки к конкретному автомобилю.
- Последствие: неполный комплект документов может выглядеть достаточным в отчёте.
- Предложение (не реализовано): считать требования по области и entity_id, сохраняя
  документ → автомобиль; переиспользовать одинаковые правила со «Сверкой».

Оба дефекта зафиксированы assertions как известное поведение и печатаются в результате.
После исправления эти assertions следует заменить проверками правильного поведения,
а не просто удалить.

## Не реализовано / не доказано этим пилотом

- В проверенной основе не найдена отдельная операция исполнения подтверждённого заказа:
  атомарно погасить резерв, списать соответствующие партии и отметить продажу shipped.
  `src/app/sales/actions.ts` заканчивается confirm/cancel;
  `202609272500_customer_orders_fefo.sql` предоставляет резервирование, гарантии и подтверждение.
  Общее `issue_inventory_fifo` и складские документы расходуют свободный остаток, а не
  исполняют резерв конкретного заказа. Ручной SQL-подмены этой отсутствующей операции нет.
- Таможня проверена как внутренний workflow, не как реальная декларация, расчёт/уплата
  пошлин или обмен с таможней. Расчёты себестоимости, платежи и финансовое закрытие в этот
  связанный сценарий не включены; существующие отдельные finance SQL-тесты проходят.
- OCR проверен на уровне его существующих SQL-операций; provider/HTTP, бинарное
  распознавание и генерация PDF/XLSX в пилоте не выполняются. Storage — только метаданные
  локального Supabase stub, не настоящее объектное хранилище.
- Отчёт получает реальный снимок тестовой БД через локальный PostgREST-shaped adapter.
  Это проверка вычислений и скрытия цен загрузчика, не проверка HTTP, SSR, JWT, браузера,
  полной матрицы RLS или PostgREST-вложений. Отдельные штатные security/RLS-тесты выполнены.
- Новые повторные операции последовательны; гонки именно приёмки/регистрации документов
  не проверены. Повтор с новым document_id/изменённым содержимым — не тот же запрос и здесь
  не проверяется. Тест не утверждает глобальную дедупликацию произвольных загрузок.
- Основной бизнес-сценарий проходит одним директором: разделение согласующих сотрудников
  не является предметом этого пилота.
