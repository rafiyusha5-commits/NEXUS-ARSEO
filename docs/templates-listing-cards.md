# Шаблоны документов и карты ввода/вывода товара

Вторая часть Фазы 3 (`docs/mvp-implementation-plan.md`): каталог шаблонов документов с версиями файлов и клиентские карты ввода и вывода товара с версиями и позициями.

## Что реализовано

| Часть | Где |
|---|---|
| Таблицы, права, RLS, триггеры, функции, политики Storage | `supabase/migrations/202609271600_document_templates_listing_cards.sql` |
| Правила шаблонов (поля, путь файла, утверждение) | `src/lib/templates/rules.ts` |
| Операции с файлами шаблонов (создание, версия, скачивание) | `src/lib/templates/operations.ts`, `supabase-gateway.ts` |
| Правила карт (статусы, версии, позиции) | `src/lib/listing-cards/rules.ts` |
| Каталог `/templates` и карточка `/templates/[id]` | `src/app/templates/` |
| Скачивание шаблона по временной ссылке | `src/app/templates/[id]/download/route.ts` |
| Реестр `/listing-cards` и карточка `/listing-cards/[id]` | `src/app/listing-cards/` |
| Модульные тесты | `tests/templates/`, `tests/listing-cards/` |
| SQL-тесты RLS и статусов | `supabase/tests/templates_listing_cards.test.sql` |

## 1. Установка

### Порядок миграций

Миграция `202609271600_document_templates_listing_cards.sql` применяется **после** всех предыдущих, в том числе после `202609271001_document_management.sql` (использует `document_types`, `documents`, bucket `nexus-documents`, функции `private.has_permission` и `private.write_access_audit`).

```
202609260001_identity_and_access.sql
202609270001_phase0_access_control.sql
202609270002_phase1_reference_data.sql
202609270003_phase2_shipments.sql
202609270004_service_role_grants.sql
202609271001_document_management.sql
202609271200_inventory_fifo.sql
202609271400_inventory_movements.sql
202609271600_document_templates_listing_cards.sql   ← новая
```

Миграция идемпотентна: повторный запуск не ломает данные и не возвращает права, отозванные администратором.

**Важно:** эта миграция пересоздаёт две политики Storage из `202609271001` («nexus documents: read registered files» и «nexus documents: remove own unregistered upload»), ограничивая их папкой `documents/`. Если по какой-то причине `202609271001` будет выполнена повторно, после неё нужно снова выполнить `202609271600`.

### Применение

- SQL Editor Supabase: вставить файл миграции целиком и выполнить;
- или Supabase CLI: `supabase db push`.

### Проверка после применения

```sql
select code from public.permissions where module in ('templates', 'listing_cards') order by code;
-- 14 кодов

select tablename, rowsecurity from pg_tables
where schemaname = 'public' and tablename in
  ('document_templates', 'document_template_versions', 'product_listing_cards', 'product_listing_card_items');
-- rowsecurity = true у всех четырёх

select policyname from pg_policies
where schemaname = 'storage' and tablename = 'objects' and policyname like 'nexus templates:%';
-- read registered files, upload into template folder, remove own unregistered upload
```

### Хранилище файлов

Файлы шаблонов хранятся в существующем приватном bucket `nexus-documents` в отдельной папке `templates/<id шаблона>/<случайная часть>-<безопасное имя>`. Отдельный bucket не нужен: те же лимит (4 МБ), список форматов и приватность. Доступ к папкам разграничен политиками: права на документы не дают доступа к файлам шаблонов и наоборот. Если bucket ещё не создан, выполните инструкцию из `docs/documents-module.md`, раздел 2.

### Переменные окружения

Новых нет. Используются `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; секретный ключ Supabase не нужен.

## 2. Модель данных

### Шаблоны

| Таблица | Назначение |
|---|---|
| `document_templates` | каталог: тип документа (`document_types`), название, язык (`ru`, `kk`, `en`), назначение, контрагент (для шаблонов клиента), поля для подстановки (`variables_schema` = `{"fields": [{"key", "label"}]}`), статус, признак включения, номер текущей версии, кто и когда утвердил, архив |
| `document_template_versions` | версии файла: номер, путь, имя, размер, MIME-тип, SHA-256, комментарий, кто и когда загрузил, признак актуальной версии. Только добавление — версии не изменяются и не удаляются |

Статусы шаблона: `draft` → `approved` → (`draft` снова после новой версии или изменения типа, языка или полей) → `archived`. Включение и отключение (`is_active`) не зависит от статуса; архивный шаблон всегда отключён. Уникальность: тип + название + язык + контрагент среди неархивных шаблонов.

### Карты ввода и вывода

| Таблица | Назначение |
|---|---|
| `product_listing_cards` | карта: номер (`LC-ГГГГ-NNNNN`, присваивает база), версия, ссылка на предыдущую версию и на первую версию цепочки, тип (`input` — ввод, `output` — вывод), клиент, шаблон формы клиента, документ заполненной карты, название, дата вступления в силу, примечание, статус, кто и когда отправил, решил, отменил |
| `product_listing_card_items` | позиция: товар, **требуемое количество** и единица (шт., короб, слой, паллета), артикул клиента, цена для клиента и валюта, комментарий. Один товар — одна позиция в карте |

GTIN, штрихкоды, артикул поставщика и срок годности не копируются в карту: они показываются из карточки товара, чтобы у данных был один источник.

Статусы карты:

```
draft ──► submitted ──► approved_by_customer ──► superseded
  │            │  └───► rejected_by_customer
  └──► cancelled ◄──┘
```

- Редактировать шапку и позиции можно **только в черновике**. Проверка стоит в базе (триггеры и RLS): прямой запрос к API тоже будет отклонён.
- Отправленная, утверждённая, отклонённая, отменённая или заменённая карта не меняется. Изменение — через **новую версию**: база копирует шапку и позиции в новый черновик с номером версии +1 и ссылкой на предыдущую.
- Новую версию можно создать только из последней версии цепочки в статусе «утверждена», «отклонена» или «отменена». В цепочке одновременно может быть только одна открытая (черновик или отправленная) и только одна утверждённая версия. Когда клиент утверждает новую версию, предыдущая утверждённая получает статус `superseded`.
- При отказе клиента комментарий обязателен.
- Шаблон формы клиента можно привязать, только если он утверждён и включён.

Отличия от `docs/data-model.md`: добавлены версии, статус `superseded` и требуемое количество в позиции (по требованиям задачи); `document_templates` ссылается на `document_types`, а файлы вынесены в отдельную таблицу версий.

## 3. Права и RLS

Выданы строго по `docs/roles-permissions.md`: «Р» — выдано ролью, «ОР» — выдаётся администратором конкретному пользователю («Роли и права» → отдельное разрешение), «О» — не выдано, потому что ограничения по `scope` пока не применяются.

**Шаблоны — раздел 12, модуль `templates`:**

| Право | Роли |
|---|---|
| `templates.view` | все 9 ролей |
| `templates.export` (скачивание файла) | все, кроме специалиста по логистике («О») |
| `templates.create`, `templates.update`, `templates.upload`, `templates.archive` | директор, администратор |
| `templates.approve` | директор, исполнительный директор |
| `templates.change_status` (включение и отключение) | директор, администратор |

**Карты ввода и вывода — раздел 3, отдельный модуль `listing_cards`** (чтобы не смешивать с правами на справочник клиентов `customers.*`):

| Право | Роли |
|---|---|
| `listing_cards.view` | все 9 ролей |
| `listing_cards.create` (карта и новые версии) | директор, администратор |
| `listing_cards.update` (черновик и позиции) | директор, администратор |
| `listing_cards.archive` (отмена) | директор, администратор |
| `listing_cards.approve` (решение клиента) | директор, исполнительный директор, коммерческий директор |
| `listing_cards.change_status` (отправка клиенту) | директор, исполнительный, коммерческий директор, администратор |

Как устроена защита:

- RLS включён на всех четырёх таблицах. У `anon` и `service_role` прав на них нет.
- У `authenticated` есть только разрешённые столбцы. Установить `created_by`, `uploaded_by`, `approved_by`, `decided_by`, `status`, номер версии, ссылку на предыдущую версию, номер карты и поля архива или отмены пользователь не может: их заполняют триггеры и функции.
- Удаление запрещено для шаблонов, версий и карт. Удалять можно только позиции черновика.
- Смена статуса — только через функции `approve_document_template`, `set_document_template_active`, `archive_document_template`, `submit_listing_card`, `record_listing_card_decision`, `cancel_listing_card`, `create_listing_card_version`. Все они `SECURITY DEFINER` с `set search_path = ''`, явно проверяют право, `EXECUTE` отозван у `public` и `anon`.
- Граф статусов проверяет триггер при любом обновлении, в том числе из функций и от владельца базы.
- Файл версии шаблона: путь должен быть в папке своего шаблона, файл — загружен тем же пользователем. Размер и MIME-тип берутся из Storage, а не из запроса.
- Все изменения пишутся в `audit_log` триггером; скачивания шаблонов — сервером.

## 5. Ручная проверка

Подготовка: миграция применена; есть активный клиент (контрагент с ролью «клиент») и хотя бы один активный товар; есть пользователи с ролями `director`, `administrator`, `executive_director`, `commercial_director`, `logistics_specialist`.

**Шаблоны**

1. Войдите администратором → **Шаблоны** → «Новый шаблон». Тип «Прочий документ», язык «Русский», контрагент — ваш клиент, поля `product_name — Наименование` и `gtin — GTIN`, файл DOCX до 4 МБ. Ожидается: карточка шаблона, статус «Черновик», версия 1, в «Полях для подстановки» два поля.
2. Попробуйте загрузить `.exe` или файл больше 4 МБ — будет понятная ошибка, шаблон не создаётся.
3. На карточке нажмите «Скачать» — файл скачивается по ссылке, которая действует 60 секунд. В «Журнале действий» есть запись о скачивании.
4. Администратор не видит кнопки «Утвердить». Войдите исполнительным директором → «Утвердить версию 1». Статус «Утверждён», указан утвердивший.
5. Администратором загрузите новую версию с комментарием. Версия 2 актуальна, версия 1 в истории и скачивается, статус снова «Черновик».
6. Директором утвердите. Затем измените только название — статус остаётся «Утверждён»; измените список полей — статус «Черновик».
7. «Отключить» — шаблон пропадает из выбора в картах. «В архив» с причиной — шаблон и файлы видны, но изменить нельзя.
8. Войдите специалистом по логистике: каталог виден, кнопок изменения и скачивания нет; прямая ссылка `/templates/<id>/download` возвращает на карточку с сообщением об отсутствии прав.

**Карты ввода и вывода**

9. Администратором: **Карты ввода/вывода** → «Новая карта»: тип «Ввод товара», клиент, дата, шаблон (в списке только утверждённые и включённые). Черновик получил номер `LC-ГГГГ-NNNNN`, версия 1.
10. Добавьте две позиции: товар, требуемое количество (например, `120` коробов), артикул клиента, цену `1 500` в KZT. Попробуйте: количество `0`, цену без валюты, тот же товар повторно — будут ошибки.
11. Удалите одну позицию и добавьте снова. Отправьте карту клиенту («Отправить клиенту»). Формы изменения и кнопки удаления исчезают.
12. Администратор не может зафиксировать решение клиента. Войдите коммерческим директором: выберите «Клиент отклонил» без комментария — ошибка; с комментарием — карта «Отклонена клиентом».
13. Директором: «Создать новую версию». Открывается версия 2 — черновик с теми же позициями и ссылкой на версию 1. Измените количество, отправьте, коммерческим директором — «Клиент утвердил».
14. Создайте версию 3 из утверждённой версии 2, отправьте и утвердите: версия 2 становится «Заменена новой версией», утверждённая в цепочке одна — версия 3.
15. Создайте ещё одну карту и отмените её с причиной: статус «Отменена», из неё можно создать новую версию.
16. Специалистом по логистике: карты видны, кнопок изменения нет.

## 6. Откат кода

Откат кода не удаляет шаблоны, файлы и карты: они остаются в базе и в bucket.

1. Откатите коммиты ветки (`git revert`) или разверните предыдущий деплой.
2. Не удаляйте таблицы `document_templates*`, `product_listing_card*` и файлы в `nexus-documents/templates/`.
3. Чтобы временно закрыть доступ без отката, отзовите `templates.view` и `listing_cards.view` у ролей.

## 7. Известные ограничения и вопросы

- **Коммерческий директор не может создавать карты.** По матрице (раздел 3) у него «ОР» на создание и изменение, но «Р» на решение клиента и отправку. Чтобы КД вёл карты сам, администратор выдаёт ему `listing_cards.create` и `listing_cards.update` как отдельные разрешения. Стоит подтвердить у ARSEO, не нужно ли выдать их роли.
- Маркетолог по матрице загружает материалы для карт ввода, но в модели пока нет вложений к карте. Поле `document_id` (заполненная карта) есть в базе, но в интерфейсе ещё не выбирается.
- **Формирование документа из шаблона** (подстановка полей, AC-DOC-09) не реализовано: шаблон хранит файл и список полей, генерации нет.
- Изменение количества в позиции — через удаление и повторное добавление в черновике; отдельной формы редактирования строки нет.
- `scope` («О» в матрице) не применяется, поэтому специалист по логистике не скачивает файлы шаблонов.
- Строгую загрузку только через сервер база обеспечить не может: см. «Известные ограничения» в `docs/documents-module.md`.
- Экрана ведения справочника типов документов нет; тип шаблона выбирается из `document_types`.
