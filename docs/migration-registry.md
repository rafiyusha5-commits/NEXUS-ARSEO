# Реестр миграций рабочей базы и сверка схемы

К3 аудита 11.11.2026: в рабочей базе не было записи о том, какие миграции она получила, — только журнал работ.
С 21.11.2026 запись ведётся в `private.applied_migrations` (миграция `202611210600_migration_registry.sql`), а
состояние схемы проверяется сверкой с эталоном, собранным из миграций.

Таблица закрыта для всех ролей API: читать и писать её можно только учётными данными владельца базы. Применение
миграций к рабочей базе по-прежнему за людьми (AGENTS.md); инструменты ниже ничего сами не применяют.

## Инструменты

| Что | Файл | Что делает |
| --- | --- | --- |
| Снимок схемы | `scripts/schema-fingerprint.sql` | только чтение: по строке на объект — функции и процедуры (полное определение и права), таблицы, столбцы, ограничения, индексы, триггеры, политики, перечисления, коды прав, бакеты Storage; два отпечатка — точный и без пробелов. Данные таблиц не читаются |
| Эталон | `scripts/schema-reference.sh` | временная PostgreSQL с `supabase_stub.sql`, все миграции по одному разу по порядку имён (до `UNTIL`, если задан), затем снимок |
| Сравнение | `scripts/schema-diff.mts` | чего нет, что лишнее, что отличается; отдельно — объекты, отличающиеся только пробелами. Печатает только имена |
| Реестр | `scripts/migration-registry.mts` | `record` — SQL записи миграций (`applied` или `reconciled`); `pending` — какие миграции репозитория не записаны или записаны с другим содержимым |

Снимок нормализован, чтобы рабочий проект Supabase и локальная PostgreSQL совпадали, когда миграции одни и те же:
схемы `public` и `private` (и политики `storage.objects`), права только ролей API, столбцы по имени. Не учитываются
функции расширений (`pgcrypto` в Supabase лежит в `extensions`), право `MAINTAIN` (только PostgreSQL 17) и символы
CR в телах функций.

## Порядок

Сверка (один раз и после любых сомнений):

```bash
UNTIL=<последняя применённая миграция> bash scripts/schema-reference.sh > reference.tsv
psql "<рабочая база>" -X -q -At -F $'\t' -f scripts/schema-fingerprint.sql > production.tsv
node --disable-warning=ExperimentalWarning scripts/schema-diff.mts reference.tsv production.tsv
```

Если схемы совпадают (или различия разобраны и записаны в журнал), миграции до `UNTIL` записываются как сверенные:

```bash
node --disable-warning=ExperimentalWarning scripts/migration-registry.mts record --method reconciled \
  --by "<кто>" --until <последняя применённая миграция> --note "<сверка от даты>" > record.sql
```

Применение новых миграций: перед ним свежая резервная копия и `pending` по выгрузке реестра; после — `record
--method applied --from <первая> --until <последняя>` в том же сеансе.

## Сверка 21.11.2026

Рабочая база сравнена с эталоном до `202611190200_calculator_price_blocks.sql` (4751 объект). Различия:

- `private.drive_access_cleanup`: в рабочей базе на таблице включён RLS, миграции его не включают. Вероятно, его
  включила служебная функция Supabase `public.rls_auto_enable()` — единственный лишний объект рабочей базы. Доступ
  от этого строже, не шире;
- 11 функций (складские документы, проверки поставщика, строка плана закупок) отличаются только пробелами и
  переносами строк — применены из файла с другим форматированием;
- остальные объекты совпадают.
