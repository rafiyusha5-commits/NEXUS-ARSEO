# Безопасное подтверждение финансового импорта

Основа: `0569ff0c2d81825ac024cfbed1952db0e926d976`. Ветка `fix/receivables-import-idempotency`.
Миграция: `202609279600_receivables_import_safety.sql`. Применять только после независимой проверки владельцем.
Никакие рабочие/учебные базы и внешние финансовые сервисы при разработке не используются.

## Воспроизведённые дефекты исходной версии

| Сценарий | Исходное поведение | Новое поведение |
| --- | --- | --- |
| Пробелы/текст назначения в пересекающейся выписке | Новая оплата, поскольку назначение входит в ключ | Идентичность по счёту, валюте и устойчивому ID операции; назначение не является ключом |
| Другая валюта при прежних реквизитах | Ложный дубль: валюта отсутствовала в ключе | Валюта входит в идентичность |
| Итог покупателя + строки договоров | Суммы складываются | Неоднозначная структура блокирует весь импорт |
| Сальдо того же покупателя и даты | Безусловная замена | Предпросмотр прежнего сальдо, явная замена с причиной и проверкой прежнего ID |
| БИН и заказ разных покупателей | Автоматическое разнесение по БИН | Конфликт блокирует пакет |
| Нет имени покупателя, но есть сумма | Строка незаметно исчезает | Ошибка чтения, подтверждение запрещено |
| Несколько неразмеченных пар дебет/кредит | Выбирается последняя | Не угадывается конец периода |
| Незакрытая CSV-кавычка / один маркер обмена | Принимаются повреждённые/пустые данные | Понятный отказ |

SQL-доказательства старого поведения запускаются **до** миграции (`supabase/tests/before/202609279600_receivables_import_safety.sql`).
Пять новых тестов `import-safety.test.ts` были запущены до исправлений: 5/5 падали.

## Один учёт, два этапа

`preview_receivables_import` только читает. Он возвращает все строки, покупателя и основание сопоставления,
ошибки, дубли, старое сальдо, суммы/число строк отдельно по валютам и отпечаток плана.
`confirm_receivables_import` заново строит этот же план после блокировок. При изменении плана просит обновить просмотр.
До явного подтверждения ни финансовые записи, ни пакеты импорта не создаются.

Повторно используются **существующие** `import_bank_statement` и `import_opening_balances` как закрытые серверные писатели
тех же таблиц. EXECUTE старых RPC отозван у authenticated/anon/service_role/PUBLIC; клиент не может обойти новый путь.
В банковском писателе изменён только приём проверенного ключа. Правила задолженности, отсрочки, FIFO,
границы даты сальдо, ручного разнесения и замещения старой записи не изменены.
Старый тест арифметики дебиторки использует явно помеченные **тестовые** адаптеры писателей;
новые публичные права проверяются отдельно, без этих адаптеров.

### Три разных идентичности

- Пакет: SHA-256 исходных байтов + вид импорта. Имя файла не участвует.
- Запрос подтверждения: UUID + хеш содержимого. Потерянный ответ возвращается повторным запросом без повторной записи.
- Банковская операция: нормализованный счёт получателя + валюта + устойчивый ID банка. Дата, сумма,
  покупатель, номер платёжного поручения и назначение **не заменяют** такой ID.

Если ID отсутствует, сотрудник обязан найти его в банковском источнике, ввести и объяснить решение.
Нельзя придумывать новый ID для повторной выписки. Два разных настоящих ID сохраняют две оплаты даже при одинаковых остальных полях.
Совпавший ID с изменившимися датой, суммой или счётом плательщика блокируется.
Для прежних записей без ID показываются кандидаты по счёту/дате/сумме/валюте: сотрудник указывает
«тот же платёж» либо «отдельная операция» с причиной. Это не автоматическое признание дубля.

В базе есть уникальные ограничения пакета и операции. Общая транзакционная advisory-блокировка сериализует импорты;
табличные блокировки фиксируют справочник покупателей/заказы и финансовые записи перед повторной сверкой.
Это намеренно консервативная реализация: большой импорт временно задерживает изменение покупателей/заказов.
Нет фонового задания, удаления или автоматического переразнесения уже учтённых денег.

## Форматы и ограничения

- Банк: текст `1CClientBankExchange`, UTF-8/UTF-8 BOM/Windows-1251, завершённые секции, один счёт и одна валюта.
  Поддерживаются прежние варианты БИН/ИИН/ИНН и счётов; необязательный `ИдентификаторОперации` принимается как ID.
  Совместимость этого поля с конкретным банком не подтверждена. Без него обязательно ручное решение.
  Многосчётные/многовалютные файлы блокируются в интерфейсе: нужны отдельные выгрузки.
- Сальдо: плоский XLSX (первый лист) или CSV UTF-8/Windows-1251, `;`, табуляция или `,`, десятичная точка/запятая,
  пробелы в разрядах. Одна строка на покупателя/валюту. Явные «Итого/Всего» исключаются с указанием причины.
  Иерархические отчёты, повторные покупатели/валюты и неопределённые колонки сумм **не поддерживаются**, а не угадываются.
  Дату сальдо сотрудник указывает явно по отчёту; она не подставляется сегодняшней датой.
- Максимум подтверждения — 2000 строк. Все строки плана видны; скрытого частичного импорта нет.
- Ошибки и неоднозначные совпадения блокируют весь пакет. Неизвестный плательщик банковской операции может быть сохранён
  только как **неразнесённый**; применяется существующее ручное разнесение. Сальдо неизвестного покупателя блокируется.
- Полное исходное содержимое строк, решения, пакет, автор/время и ссылки на записи хранятся под RLS `receivables.view`.
  RPC требуют одновременно view/manage, включая личные запреты. service_role новых прав не получает.
- Безопасной отмены пакета нет. Кнопка удаления/отмены не добавлена; связи используют RESTRICT, каскадного удаления денег нет.
- React выводит пользовательские значения текстом (браузерный тест с HTML-подобным названием). XLSX-чтение не исполняет формулы.
  Экспорт банковских импортов/сальдо в Excel в текущем Nexus отсутствует; безопасность будущего такого экспорта не подтверждается
  этим PR. При его добавлении обязательны текстовые ячейки (не формулы) и защита CSV от `=`, `+`, `-`, `@`.

**Совместимость с реальными файлами компании остаётся неподтверждённой до проверки образцов.**
Ни реальные документы, ни Google, ни банковские/1С API для этой работы не использовались.

## Проверки

```sh
corepack pnpm typecheck
corepack pnpm lint
corepack pnpm test
corepack pnpm build
corepack pnpm test:db
node scripts/test-receivables-ui.mjs /path/to/playwright /tmp/nexus-import-screenshots
```

`test:db` создаёт одноразовый PostgreSQL (CI: 16), применяет миграции, проверяет их повторное применение,
права/RLS и SQL-регрессии; затем запускает два настоящих psql-соединения для одновременного импорта:
один/переименованный файл, перекрывающаяся операция с повтором после обновления просмотра,
два разных равных платежа, конфликт сальдо. Ожидание блокировки проверяется фактически, не таймингом результата.
Локальные SQL-проверки на Windows дополнительно выполнялись в изолированном PGlite, **не вместо** конкурентного PostgreSQL CI.
Браузерная проверка — реальный React-компонент с подменными серверными действиями, 1440/390 px,
запрещёнными внешними запросами; не проверяет живой Supabase/авторизацию браузера.

Зависимостей от других открытых PR нет. Миграция подготовлена, но нигде вне одноразовых тестов не применяется.
