Статус документа: черновик. План делит реализацию на последовательные фазы. Номера вопросов (М, И, П) — из [`open-questions.md`](./open-questions.md).

## Принципы реализации

- **Уже реализованное не ломаем.** Авторизация (вход, восстановление пароля, `/auth/callback`, `src/proxy.ts`) и миграция `202609260001_identity_and_access.sql` остаются как есть. Новые миграции только добавляют таблицы, колонки, функции и политики.
- **Одна фаза — свои миграции.** Таблица создаётся вместе с RLS-политиками, правами (`permissions`, `role_permissions`) и триггерами аудита. Таблица без RLS в `public` не допускается.
- **Проверки RLS — автоматические.** Для каждой роли есть тестовый пользователь; тесты проверяют разрешённые и запрещённые действия (сценарии из `mvp-acceptance-criteria.md`).
- **Секреты только на сервере.** Ключ `service_role` и ключи Google, WhatsApp, 1С не попадают в браузер (как сейчас в `supabase/README.md`).
- **Процесс мягкий до подтверждения.** Шаблон процесса работает в режиме `advisory`: предупреждение + причина вместо запрета.
- **Интерфейс — на русском.** Строки выносятся в словари с первой фазы, чтобы добавить казахский и английский без переделки (П20).
- **Тестовые данные — вымышленные.** Реальные договоры, реквизиты, персональные данные, цены и коды маркировки в репозиторий не попадают.

## Фаза 0 — доступ, профили, роли и аудит

| | |
|---|---|
| **Результат для пользователя** | Сотрудник входит по корпоративной почте (уже работает), видит свой профиль и роль. Администратор в интерфейсе приглашает и отключает пользователей, назначает роли, настраивает права ролей, выдаёт отдельные разрешения. Руководители видят журнал действий |
| **Таблицы** | Существующие: `profiles` (расширение: `user_type`, `counterparty_id`, телефоны, настройки уведомлений, основной склад), `app_roles` (+ `audience`), `permissions` (+ коды разделов), `role_permissions` (+ `scope`, заполнение матрицы), `user_roles`, `audit_log`. Новая: `user_permission_overrides`. Функции: `private.has_permission`, `private.is_employee`. Представление справочника сотрудников (включая отключённых — для истории) |
| **Экраны** | Вход и восстановление пароля (есть); «Мой профиль» (язык `ru`/`kk`/`en`, телефон, каналы уведомлений, все свои роли); «Пользователи» (список, приглашение, отключение, роли); «Роли и права» (матрица с Р / О / ОР / З); «Отдельные разрешения»; «Журнал действий» (фильтры по пользователю, объекту, дате) |
| **Основные действия** | Пригласить пользователя; назначить и снять роль; изменить право роли и `scope`; выдать и отозвать отдельное разрешение; отключить пользователя; найти действие в журнале |
| **Права доступа** | Разделы 1, 2, 19, 20 матрицы. Целевое управление — `administrator` и `director`; в текущей миграции доступ есть только у `administrator` |
| **Интеграции** | Supabase Auth; встроенная почта Supabase работает с лимитами, корпоративный SMTP Mail.ru подключается до промышленной эксплуатации (И19) |
| **Критерии готовности** | AC-AUTH, AC-ROLE, AC-AUDIT выполнены; у каждой из 9 ролей есть тестовый пользователь; тесты RLS для таблиц доступа проходят; политики чтения профилей и ролей ограничены сотрудниками |
| **Зависимости** | Миграция `202609260001` (есть) |
| **Риски** | Администратор может лишить доступа сам себя — нужен запрет снимать роль с последнего администратора. Встроенная почта Supabase ограничивает отправку писем. Журнал, который пишет клиент, неполный — нужны триггеры |
| **Решения ARSEO** | Для начала фазы блокирующих решений нет. И19 (SMTP) закрывается до промышленной эксплуатации; П21–П23 уточняются без остановки разработки |
