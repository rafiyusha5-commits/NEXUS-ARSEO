# AI-ассистент Nexus: веб, первый релиз

Статус: реализовано в ветке `feature/agent-web-mvp`, по умолчанию **выключено**. Миграция `202609275200_agent_web_mvp.sql` не применялась ни к одному рабочему проекту.

## Что делает

Раздел «Ассистент» (`/assistant`) отвечает на вопросы внутренних сотрудников на русском языке по данным Nexus:
- поставки;
- автомобили;
- документы поставки;
- результаты распознавания;
- задержки;
- остатки;
- свои задачи;
- справка.

Ограничения первого релиза:
- Ассистент только читает. Инструментов записи, произвольного SQL и произвольных HTTP-запросов нет.
- Каждый вопрос самостоятелен: памяти между вопросами нет.
- Нет Telegram, голоса, финансового профиля, отправки отчётов, NVIDIA и RAG. Telegram — см. `docs/telegram-architecture.md`.

## Устройство

```
Браузер ──POST /api/assistant (тот же Origin, JSON ≤ 8 КБ)──▶ маршрут
  маршрут: AGENT_ENABLED + подтверждение передачи → сессия → сотрудник → agent.use
  └─ runAgent (src/lib/agent/runner.ts, не зависит от канала)
       ├─ маскирование вопроса (до любого внешнего вызова)
       ├─ agent_reserve_run (серверный ключ): атомарно запрос дня + резерв бюджета месяца
       ├─ цикл: модель ⇄ инструменты (права проверяются перед каждым вызовом)
       ├─ факты собирает код из выбранных моделью записи и полей
       └─ agent_finish_run (серверный ключ): статус, токены, стоимость, безопасная трасса, возврат запроса при сбое
```

Как устроены зависимости:
- **Данные** читаются только серверным Supabase-клиентом из cookies текущего запроса, то есть сессией сотрудника. Действуют RLS и права на колонки (`src/lib/agent/server/supabase-data.ts`).
- **Учёт лимитов и бюджета — только сервер.** `agent_reserve_run` и `agent_finish_run` может выполнять только `service_role`, то есть сервер Nexus с ключом `SUPABASE_SECRET_KEY` (или устаревшим `SUPABASE_SERVICE_ROLE_KEY`). Сессия сотрудника эти функции вызвать не может. Иначе сотрудник получил бы токен завершения и повторял бы «резерв → завершение с выдуманным расходом и возвратом запроса», исчерпав общий бюджет без единого обращения к модели. По той же схеме уже работают `start_synchronization_run` / `finish_synchronization_run`.
  - Серверный ключ используется только для этих двух вызовов (`src/lib/agent/server/supabase-ledger.ts`). Бизнес-данные, права и инструменты — только сессией сотрудника.
  - Сотрудника для учёта сервер берёт из `auth.getUser()` текущей сессии и передаёт в `p_user_id`. База сама проверяет, что это активный внутренний сотрудник с `agent.use` (`private.user_has_permission`, с учётом персональных запретов). Закрыть запуск можно только для того же сотрудника и с токеном этого запуска.
  - Свой расход сотрудник читает своей сессией через `my_agent_usage()`; эта функция ничего не меняет.
- **Модель** вызывается через интерфейс `AgentModelProvider` (`src/lib/agent/types.ts`). Реализация — OpenAI Responses API на `fetch` (`providers/openai.ts`) с `store: false` и строгими схемами. Новый провайдер или канал добавляется без изменения бизнес-логики: канал передаёт в `runAgent` источник данных, проверку прав и журнал.
- **Поток ответа:** маршрут отдаёт NDJSON. Сначала идут только этапы («Ищу поставки», «Проверяю факты»), затем один ответ после проверки: факты, собранные кодом, и отдельно помеченные пояснения модели. Промежуточный текст модели в поток не попадает.

## Включение

1. Владелец согласует передачу данных провайдеру модели.
2. Применить миграцию `202609275200_agent_web_mvp.sql`.
3. Задать месячный бюджет и предел на один запрос в долларах × 10⁶. Пример: 20 USD в месяц и 0,50 USD на запрос:
   ```sql
   update public.agent_settings set monthly_budget_usd_micros = 20000000, max_run_reserve_usd_micros = 500000;
   ```
   Пока бюджет равен 0, вопросы не принимаются.
4. Переменные окружения сервера. Значения не коммитить:

## Инструменты

Общие правила для всех инструментов:
- Строгие схемы параметров: лишние поля, неверные типы и значения вне диапазона отклоняются.
- Явный список выходных полей.
- Не больше 20 записей.
- Таймаут 8 секунд.
- Права проверяются сервером перед **каждым** вызовом. Модель видит только инструменты, на которые у сотрудника есть права.

| Инструмент | Права | Возвращает | Не возвращает никогда |
|---|---|---|---|
| `find_shipments` | shipments.view | номер, проект, тип, статус, плановые даты, поставщик, клиент | цены |
| `get_shipment` | shipments.view | карточку; текущие и заблокированные этапы; товары с количествами | цены; причины приостановки и отмены (если статус не тот) |
| `get_shipment_vehicles` | shipments.view | номер, статус, госномера, марки, перевозчика, даты, температуру | ФИО, телефон и документ водителя; примечания |
| `get_shipment_documents` | shipments.view, documents.view | тип, название, номер, статус, даты, привязку к автомобилю; отсутствующие обязательные документы | суммы, содержимое файлов, имена файлов; название и номер документов водителя и автомобиля |
| `get_document_extraction` | shipments.view, documents.view | статус; только поля из `EXTRACTION_ALLOWED_FIELDS`: номера документов, даты, госномера, перевозчик, пломбы, температура, паллеты, вес, Incoterms, города и страны, категория | позиции и цены ЭСФ, данные водителя, телефоны, адреса, реквизиты, условия оплаты, подписантов, «доказательства» распознавания, текст документа |
| `list_delayed_shipments` | shipments.view | поставки и автомобили с прошедшей плановой датой прибытия, дни задержки, общее количество | — |
| `get_stock_status` | inventory.view, products.view, warehouses.view | количества по товару, складу и единице; ближайший срок годности; худшее состояние срока | себестоимость |
| `get_my_tasks` | tasks.view | свои задачи: название, статус, приоритет, срок, поставка. Исполнитель — пользователь сессии, а не параметр модели | описание задачи |
| `get_help` | — | отобранную справку `src/lib/agent/help.ts` | настройки, секреты, технические инструкции |

Определения в инструментах:
- **Задержка.** Поставка не закрыта и не отменена, плановая дата прибытия раньше сегодняшней по Asia/Aqtobe. Для автомобиля: нет фактического прибытия, статус не «Прибыл», «Разгружен» или «Отменён», поставка не закрыта и не отменена.

  Сравнение с разделом «Аналитика» (`src/app/analytics/page.tsx:28-29`):
  - **Совпадает:** условие для поставки — статус не `closed` и не `cancelled`, `planned_arrival_date < сегодня`.
  - **Другой часовой пояс:** аналитика считает «сегодня» по `Asia/Almaty`, ассистент — по `Asia/Aqtobe`. С 1 марта 2024 года весь Казахстан живёт по UTC+5, и в базе часовых поясов (tzdata 2025b в Node и в PostgreSQL 16) оба пояса сейчас дают UTC+5. Сегодняшняя дата совпадает; расхождение появилось бы только для дат до марта 2024 года (Almaty тогда был UTC+6) или при новом изменении tzdata. Рекомендация: перевести аналитику на `Asia/Aqtobe` отдельным изменением; в этой ветке аналитика не менялась.
  - **Только в ассистенте:** задержанные автомобили (по плановой дате прибытия автомобиля). Аналитика считает только поставки.
  - **Только в аналитике:** просроченные этапы (`due_at` у этапов не заполняется ни одной функцией, поэтому этот показатель всегда 0), заказы клиентов и задачи.
  - **Разный объём:** аналитика читает строки поставок без ограничения и считает их в браузере (не больше лимита строк API, обычно 1000). Ассистент получает точное количество от базы (`count: exact`) и показывает первые 20.
- **Минимальный остаток в Nexus не задан.** `purchase_plan_lines.safety_stock` — это ручной параметр строки плана закупки, а не порог товара. Поэтому инструмент не определяет, что товар «заканчивается», и прямо сообщает об этом.

## Маскирование и передача данных

Код `src/lib/agent/masking.ts` скрывает до передачи модели:
- номера удостоверений;
- ИИН и БИН (12 цифр);
- паспортные номера;
- телефоны;
- ключи и токены: API, Bearer, JWT, PEM;
- пароли и адреса подключения с паролем.

Где применяется:
- вопрос;
- параметры инструментов;
- результаты инструментов;
- запрос к модели;
- трасса;
- сообщения об ошибках.

Номера, разбитые пробелами или дефисами в любой группировке («0456 78912», «04-567-8912», «04 56 78 912»), а также с неразрывным пробелом, типографским тире или полноширинными цифрами, скрываются, если в цепочке 9 и больше цифр. Цепочки, приклеенные к буквам, — идентификаторы Nexus и не скрываются: номер поставки `NAR-2026-0007`, госномер `123ABC02`. Идентификаторы записей (UUID) тоже не трогаются.

Дополнительные правила:
- В свободном тексте из Nexus (названия, причины, комментарии) скрываются денежные суммы.
- Свободный текст из Nexus, в котором после маскирования осталась длинная последовательность цифр (7+ подряд, в том числе через точку, подчёркивание, косую черту или скобки), не передаётся вовсе.
- Вопрос, который нельзя безопасно очистить, отклоняется до резервирования и до обращения к модели: больше 5 скрытых фрагментов, приватный ключ или номер из 9+ цифр в форме, которую правила не распознают («0456.78912», «0456_78912», «0456/78912»). Даты и время в вопросе разрешены.
- Ходы самой модели (аргументы вызовов и текст), которые отправляются ей обратно на следующем шаге, и параметры в трассе проходят то же маскирование; длинный номер в любой форме заменяется на «[скрыто]».
- Исходный вопрос нигде не хранится; в трассу попадает замаскированная выдержка не длиннее 120 символов.

Модели никогда не передаются:
- закупочные цены и себестоимость (финансовых инструментов нет);
- суммы документов и позиции ЭСФ;
- данные водителей;
- исходные файлы и полный текст OCR;
- реквизиты и адреса;
- ключи и секреты Nexus.

Продажные цены прайса в этом этапе тоже не передаются: инструментов для них нет.

**Политика Nexus и правила ассистента — разные вещи.** Согласованная политика Nexus:
- сотрудники видят загруженные документы, включая инвойсы с ценами;
- продажные цены прайса доступны всем сотрудникам;
- закупочные цены и себестоимость — по отдельным правам.

Ассистент эту политику не меняет и новых ограничений в Nexus не вводит. Ограничения выше — это минимизация данных, уходящих внешнему провайдеру модели: доступ к документу в Nexus не означает, что его содержимое передаётся модели. Предложения изменить политику доступа в самом Nexus (данные водителей, позиции ЭСФ) вынесены отдельно и требуют решения владельца.

## Подмена инструкций

- Тексты документов, OCR, названия и комментарии передаются модели как данные с пометкой «недоверенный текст».
- Решения модели не расширяют полномочия:
  - неизвестные инструменты и инструменты без прав отклоняются сервером;
  - параметры проверяются строгой схемой;
  - исполнитель задач берётся из сессии;
  - ссылки на карточки строит сервер по идентификаторам из результатов. Ссылки и URL от модели удаляются.

## Достоверность ответа

Модель не пишет проверенные утверждения. Её окончательный ответ — JSON (`src/lib/agent/facts.ts`):
- `facts` — только выбор данных: `{ call, row, fields }` — вызов инструмента, номер записи и ключи полей этой записи;
- `commentary` — пояснения (`explanation`) и предположения (`assumption`) своими словами;
- `limitations` — ограничения ответа без цифр.

Как собирается факт:
- Объект факта (`subject`) строит инструмент из данных записи: «Поставка NAR-2026-0007», «Поставка NAR-2026-0007 · автомобиль № 1», «Инвойс № INV-55», «Задача «…»». Модель его не задаёт и не может приписать значение другому объекту.
- Значения подставляет код из этой записи: подпись поля, форматированное значение (даты дд.мм.гггг, время по Asia/Aqtobe), источник (инструмент и номер записи) и ссылка на карточку.
- Плановая и фактическая дата — разные поля с разными подписями. Если модель выбрала плановую дату, пользователь видит «Плановое прибытие — 05.10.2026», а не «прибыла».
- Отказ: несуществующий вызов, запись вне результата, поле не из списка инструмента или пустое значение. Отказ попадает в раздел «Отклонено при проверке» и фактом не становится. Остальные поля той же записи показываются.
- Количество записей — только `$count` (показано) и `$total` (всего по данным базы), отдельно от полей записи.

Что видит пользователь:
- «Проверенные данные Nexus» — факты, собранные кодом.
- «Пояснения модели» — свободный текст с пометкой «Пояснение модели · не проверено» или «Предположение · не проверено». Текст маскируется, ссылки и URL удаляются. Утверждение вроде «машина прибыла без повреждений» может появиться только здесь и никогда не выдаётся за факт.
- «Отклонено при проверке» — что модель выбрала неверно.
- «Ограничения ответа» — от сервера: неполный список «N из M», отсутствующая в Nexus функция, скрытые данные, отсутствие проверенных данных.

Что эта схема не делает: она не проверяет смысл пояснений модели. Неверный вывод в пояснении возможен, но он всегда показан отдельно как непроверенный.

## Лимиты и бюджет

- **Лимит пользователя:** 20 вопросов в сутки (`agent_settings.daily_request_limit`).
  - Сутки — по Asia/Aqtobe (UTC+5).
  - Счётчик общий для всех каналов: `channel` = web или telegram.
  - Резервирование атомарное: блокировка строки дня пользователя. Тест: из 30 параллельных запросов проходят ровно 20.
- **При сбое** провайдера, таймауте или неверном формате ответа запрос возвращается пользователю. Фактически потраченные токены и деньги всё равно учитываются в `agent_budget_months`.
- **Ограничения одного запроса:** шаги, вызовы инструментов, входные и выходные токены, таймаут вызова и общий срок 55 секунд. Перед каждым обращением к модели проверяется остаток бюджета запроса.
- **Месячный бюджет** (`monthly_budget_usd_micros`). Резерв на запрос считается консервативно: все лимиты токенов × цены. Учитываются фактические расходы и резервы всех открытых запусков, независимо от их возраста.
- **Зависший запуск** (сервер упал или не смог закрыть запуск) никогда не освобождает деньги сам по себе:
  - Запуск, открытый дольше `reservation_ttl_seconds` (600 с; срок обработки запроса 55 с), закрывает следующий `agent_reserve_run`: статус `failed`, код `AGENT_ABANDONED`, `cost_status = 'estimated'`, в расход месяца списывается весь резерв — провайдер мог выставить счёт до этой суммы.
  - Запрос сотрудника при этом не возвращается: возврат запроса и учёт денег разделены.
  - Позднее завершение того же запуска (`agent_finish_run` с его токеном) заменяет оценку на сообщённый расход: в бюджет добавляется только разница (обычно отрицательная), `cost_status = 'reconciled'`. Запрос возвращается, только если позднее завершение явно просит возврат.
  - Повторное завершение отклоняется (`AGENT_RUN_NOT_FOUND`), поэтому расход не учитывается дважды. Параллельное закрытие и позднее завершение не конфликтуют: запуск, который сейчас завершается, заблокирован и пропускается (`skip locked`), а порядок блокировок исключает взаимоблокировку.
  - `cost_status`: `reserved` — идёт; `actual` — закрыт сервером; `estimated` — списан резерв; `reconciled` — сверен после позднего завершения. Виден в трассах.
  - **Это лимит ассистента Nexus, а не гарантированный предел счёта облачного проекта.** Лимит расходов нужно отдельно настроить у провайдера.
- **Изменить лимиты можно только из SQL Editor** (таблица `agent_settings`). Аргументы RPC лимиты не меняют.
- **Токен завершения** выдаётся только серверу (резервирование доступно лишь `service_role`), его хэш через API не читается. Он защищает от закрытия чужого запуска по ошибке, но не считается доказательством подлинности значений: `agent_finish_run` в любом случае проверяет и очищает все сохраняемые поля (см. «Трасса»).
- **Резерв делается с запасом:** входные токены оцениваются до вызова, поэтому резерв на запрос — 1,5 × лимит входных токенов × цена + лимит выходных × цена.
- **Записанный расход ограничен резервом запуска** (`agent_finish_run`), токены и счётчики — разумными пределами. Иначе сотрудник мог бы прямым вызовом функции записать огромный расход и исчерпать общий бюджет.
- **Вызов модели с неизвестным результатом** (обрыв, таймаут, 5xx, нечитаемый ответ) не считается бесплатным: учитывается оценка входа и весь лимит вывода этого вызова. Отказ провайдера (4xx, кроме 408) не учитывается.
- **Ответ модели без достоверного `usage`** (нет поля, нет одного из счётчиков, некорректное значение) не превращается в нулевой расход: сообщённые счётчики учитываются, недостающий вход — по оценке, недостающий вывод — по лимиту вывода вызова. Те же оценки входят в лимиты запуска (`maxInputTokensTotal`, `maxOutputTokensTotal`): отдельный счётчик складывает достоверные токены и оценки неизвестных, поэтому ответы без `usage` не обходят лимит — следующий вызов блокируется, когда он исчерпан. В трассу пишутся только достоверные токены, оценки — только в денежный расход, который остаётся в пределах резерва.
- **Непредвиденная ошибка после резервирования** всё равно закрывает запуск: фактические токены записываются, запрос возвращается.
- **Параллельные запросы** не обходят ни дневной лимит, ни месячный бюджет: в `scripts/test-db.sh` 30 одновременных запросов дают ровно 20 по лимиту и ровно столько, сколько помещается в остаток бюджета.
- **Что учитывается приблизительно:** если сервер аварийно завершился и запуск так и не был закрыт, в расход месяца попадает весь резерв (оценка сверху), а фактические токены неизвестны. Запуски прошлых месяцев закрываются только поздним завершением: резервирование трогает лишь текущий месяц.

## Трасса

`agent_runs` хранит:
- сотрудника, канал, статус, код ошибки;
- замаскированную выдержку вопроса;
- имена инструментов и безопасные параметры (идентификаторы, перечисления, замаскированный поиск);
- число записей и признак неполного результата;
- шаги, токены и стоимость.

Проверка на стороне базы (`private.agent_clean_text`, `private.agent_clean_tools`), независимо от того, кто вызвал RPC:
- выдержка вопроса: удаляются управляющие и невидимые символы, скрываются секреты (пароли, Bearer, JWT, ключи, длинные токены) и любая цепочка из 7+ цифр, в том числе через пробел, дефис, точку, косую черту или скобки;
- `p_tools`: массив не длиннее 30; у записи только ключи `name, params, rows, truncated, ms, error`; имя — из списка инструментов; `rows` 0–100, `ms` 0–120000, код ошибки — из списка; параметры — только известные ключи со своими правилами (UUID, перечисление, код склада, `limit` 1–20), текст поиска очищается как выдержка. Сохраняется значение, собранное заново из проверенных частей;
- `p_model`, `p_provider`, `p_error_code` — строгий формат или список, без длинных цифровых последовательностей;
- нарушение формы — отказ `AGENT_BAD_REQUEST`, ничего не сохраняется.

Полные вопросы, ответы, документы и результаты инструментов не хранятся, поэтому трасса объясняет ход обработки, но восстановить по ней ответ нельзя. Доступ: сотрудник видит свои записи, держатель `agent.view_traces` — все.

## Откат без потери истории

1. Мгновенно: `AGENT_ENABLED` снять или поставить `false` — маршрут вернёт 503, страница покажет «выключен».
2. Запретить использование:
   ```sql
   delete from public.role_permissions where permission_id in (select id from public.permissions where code like 'agent.%');
   ```
   История запусков сохраняется.
3. Таблицы `agent_runs`, `agent_usage_days`, `agent_budget_months` и `agent_settings` не удалять: в них учёт расходов. Удаление таблиц — необратимая потеря истории, а не откат.
4. Код ассистента не используется остальным Nexus. Пункт меню и страницы можно убрать отдельным изменением.

## Подключение Terra

Для GPT-5.6 Terra используется Responses API и reasoning low. Запрос задаёт store=false: ответ не сохраняется как объект Responses для последующего получения через API. Это не отменяет правила хранения данных провайдера. Зашифрованный контекст рассуждения хранится в памяти одного запуска. Текст и аргументы инструментов на следующих шагах берутся из очищенной истории runtime, а не из исходного ответа модели. Отказ и незавершённый ответ возвращают известный расход токенов в учёт; при обрыве до получения usage точный расход неизвестен.

Пилот: месячный бюджет 5 USD, максимальный резерв одного вопроса 0,30 USD. При стандартных ограничениях резерв Terra составляет 0,252 USD; фактический расход обычно меньше. Production включается после применения миграции 5200 и проверки пользовательской сессии.


## Каталог и контекст диалога

`find_products` читает справочник `products` с сессией сотрудника и правом `products.view`. Цены не выбираются. Поиск по бренду, артикулу и названиям ru/en/kk; до 20 товаров на страницу, точное количество из базы, стабильная сортировка и offset. Список страницы формируется кодом целиком, даже если модель выбрала только часть полей. Нулевые складские остатки не означают отсутствия товаров в справочнике. Неполный результат явно обозначается и сопровождается ссылкой на справочник.

Обязательно применить миграцию `202609275500_agent_catalog.sql` **после** 5200/5300/5400: она разрешает новый инструмент и offset в проверке трассы. Иначе учёт запуска отклонит результат нового инструмента. Существующие миграции не изменяются.

Короткий контекст хранится только в памяти процесса, до 4 успешных вопросов, 30 минут бездействия, не более 500 бесед. Ключ включает сотрудника, канал и идентификатор беседы (в вебе отдельный для каждой вкладки; в Telegram — личный чат). Сохраняются маскированные вопросы и параметры выполненного поиска, без ответов, результатов инструментов, файлов и цен из базы. Старые вопросы — недоверенные подсказки для поиска, а не источник фактов: инструменты заново проверяют права и читают данные. В вебе кнопка «Новая беседа», в Telegram команда `/new` сбрасывают контекст. Перезапуск процесса очищает память; между несколькими серверными процессами она не общая. Постоянная история потребует отдельной реализации.


### Полный каталог в Telegram

При первой странице с limit=20 каталог автоматически читается страницами до 200 товаров в пределах таймаута инструмента. Остальные случаи сохраняют явно выбранную страницу. Для большого каталога остаётся предупреждение о неполноте. Стабильное число записей проверяется на всех страницах; при изменении каталога результат не объявляется полным.

Переносы строк в каталоге сохраняются. Ответ длиннее 3900 символов доставляется одним UTF-8 текстовым файлом с короткой подписью вместо обрезанного сообщения. Отправка файла проходит ту же проверку доступа, deadline и однократную отметку доставки; после неизвестного исхода повторной отправки нет. Файл формируется в памяти, в Nexus не хранится. Маленькие ответы остаются обычными сообщениями.

Голосовые ошибки различают скачивание, формат/длительность, доступ к аудио-API, ограничение запросов, таймаут и пустой текст. В учёте сохраняется прежний AGENT_SPEECH_ERROR; безопасный серверный журнал содержит только тип сбоя и HTTP-статус, без текста, записи, токена или URL.
