# Мониторинг Nexus

Основа: `codex/admin-order-date-correction-20261110`, `602931d62931a2570312d76446d0ab33b2fbf2f5` (PR №92). Миграция: `202611100200_system_monitoring.sql`. Выпуск, рабочие ключи, получатели и расписания требуют отдельного решения владельца. Этот PR их не включает.

## Что проверяется

`GET /api/health/live` отвечает только `{"status":"ok"}` и не обращается к Supabase/Auth. `GET /api/health/ready` отвечает таким же минимальным JSON или `{"status":"unavailable"}` с 503. Проверка готовности действительно читает RPC `system_health_ping` и заранее созданный маленький файл в закрытом Storage, сверяя SHA-256. Общий бюджет — 4 секунды, включая тело ответа, максимум 4 КиБ; зависшие чтения прерываются. Перенаправления запрещены. Параллельные запросы одного процесса используют один результат с кешем 5 секунд; кеша CDN нет. Несколько процессов имеют отдельные лимиты.

Только эти два точных пути обходят проверку сессии; диагностический экран `/admin/health` требует активного сотрудника и `system.health.view`. RPC повторно проверяют право. Миграция не выдаёт это право ролям или людям. Новое техническое право исключено из требования «все рабочие права» старого архива: мониторинг не содержит архивируемых рабочих данных; остальные ограничения архива сохранены.

В базе сохраняются только среда, компонент, код из закрытого набора, время и случайный UUID обращения. Нет запросов пользователей, сумм, документов, ФИО, email, SQL, исходных исключений, ключей или URL. `onRequestError` вообще не читает аргументы ошибки/запроса. Журнал на диске использует тот же белый список; максимум 12 сегментов по примерно 64 КиБ, срок 7 дней, очередь записи до 128 событий. Ошибка диска не падает в бизнес-код. Каталог должен быть закрыт ACL владельца ОС; POSIX mode сам по себе не заменяет Windows ACL. Проверяющий процесс имеет доступ только к своему каталогу, его родительские каталоги должны быть недоступны другим пользователям.

Инцидент уникален по среде/компоненту/коду среди открытых. Повторы того же наблюдения и ответы старее последнего не повторяют эффект; счётчик отражает принятые новые наблюдения, а не все HTTP-попытки. Только `OK` закрывает инцидент: выключение или отсутствие настройки не выдают восстановление. Новый сбой после восстановления — новый инцидент. Уведомления Nexus получают активные сотрудники с правом диагностики.

## Задания и доказательства резервирования

Источники состояний — уже существующие записи Drive, OCR и Telegram. Диагностика не запускает, не повторяет и не подтверждает обработку. Ручной режим без запусков показывается как ручной; истёкшая аренда — как требующее сотрудника задание. Успех и последняя попытка считаются отдельно. Для реально периодического задания режим `scheduled` использует согласованный интервал плюс 120 секунд; пустая очередь ручного обработчика не объявляется просроченной. Текущие таблицы не имеют отдельной надёжной очереди автоматических повторов: её наличие не выдумывается.

Отчёт резервирования — JSON `{"payload":"<точная JSON-строка>","signature":"<base64 Ed25519>"}`. Payload содержит ровно:

```json
{"environment":"test","copiedAt":"2026-11-10T00:00:00.000Z","integrityAt":null,"restoredAt":null,"restorePassed":false,"archiveSha256":"<64 lowercase hex>"}
```

Приватный ключ подписи принадлежит процессу проверенного резервирования и не передаётся приложению. Приложение только проверяет подпись, среду, порядок дат и структуру. Нельзя подписывать `restorePassed=true` по одному факту создания архива: нужны успешное независимое восстановление БД/Auth/Storage, проверки прав и документов. Результат CI на синтетике нельзя подписывать как production. Порог возраста 24 часа — тестовый, не утверждённый RPO компании. Неверный/чужой/отсутствующий отчёт означает «Не подтверждено». Источник выдачи подписанных production-отчётов ещё должен быть выбран владельцем.

## Запуск и независимый наблюдатель

Переменные перечислены без секретов в `.env.example`. CLI не читает `.env` автоматически, не принимает URL базы в аргументах и не включает сервисы. Для коллектора нужен отдельный серверный секрет Supabase; он обладает полномочиями service_role, поэтому хранится только в доверенной серверной среде, не в браузере/репозитории/аргументах команд. Код клиента допускает только четыре технических RPC. Это программный белый список, а не сужение прав самого service_role.

```text
node --disable-warning=ExperimentalWarning scripts/monitor-system.mts collect
node --disable-warning=ExperimentalWarning scripts/monitor-system.mts observe
```

`collect` проверяет зависимости, существующие задания и подписанный отчёт, сохраняет события. Внешняя доставка включается отдельно `MONITORING_EXTERNAL_ENABLED=true`: один элемент очереди за вызов, одна аренда на среду, до 5 попыток с задержкой, HTTP-таймаут 3 секунды. При ошибке событие остаётся; новый инцидент о сбое доставки не создаётся. Технический HTTPS-получатель должен обрабатывать `Idempotency-Key`: гарантия exactly-once для произвольного внешнего HTTP невозможна при потере ответа после отправки. Отправляются только разрешённые технические поля. Реальные Telegram/WhatsApp в этой разработке не подключаются.

`observe` запускается отдельно от Nexus; ему не нужен доступ к БД или серверный ключ. Он проверяет liveness, хранит своё состояние и повторы в частном каталоге. На том же компьютере обнаружит остановку процесса; выключение всего компьютера сможет обнаружить только наблюдатель на другом доступном узле. Для этого нужен отдельно согласованный сетевой адрес. PR не создаёт туннель, публичный сервер или правило брандмауэра. Получатели и способ размещения ещё не выбраны.

Обязательный JSON-файл окна (`MONITORING_WINDOW_FILE`), пример только для тестов:

```json
{"timeZone":"Asia/Almaty","weekdays":[1,2,3,4,5],"startHour":9,"endHour":18,"maintenanceUntil":null,"reason":"Согласованное тестовое окно"}
```

Часы не переходят через полночь. Для круглосуточного окна — 0–24 и все дни 0–6 (воскресенье=0). Обслуживание задаётся сроком ISO UTC и причиной. Вне окна наблюдатель не объявляет недоступность. Локальная история хранит отпечатки последних 100 редакций, время и настройки без секретов. Изменение файла делает оператор; приложение не меняет расписание. Одновременный запуск одного режима исключается lock-файлом. После аварийного завершения оператор проверяет отсутствие процесса и удаляет только соответствующий `observe.lock`/`collect.lock`; автоматического захвата чужой блокировки нет.

## Проверка и эксплуатационные ограничения

`tests/monitoring/policy.test.ts`: настоящие stream timeout/abort, single-flight 100 запросов, проверка canary, закрытый набор полей, ротация/отказ диска, подписи и среды, режимы и окно, повторы доставки. `system_monitoring.test.sql`: права, личный запрет, неактивность, повтор/восстановление/поздний ответ, предел попыток/аренда, неизменность рабочих таблиц. `test-monitoring-concurrency.mjs`: 100 одновременных повторов и 10 конкурирующих доставщиков на PostgreSQL. `monitoring-forms.mjs` включён в существующий historical-readiness: реальные Auth/Storage, экран 1440/390 и клавиатура, отказ/зависание backend, остановка настоящего тестового Next и отдельный процесс наблюдения. Все внешние вызовы тестов ограничены локальным стендом/подменами.

Шесть обязательных jobs CI сохраняются. Политика хранения технических инцидентов в БД в первом выпуске — без автоматического удаления; перед рабочим включением владелец должен утвердить срок и обслуживание. На диске старые сегменты ограничены автоматически. Записи рабочего Supabase и бизнес-таблиц в испытаниях не используются.

Отключение: прекратить внешнее расписание коллектора/наблюдателя и установить `MONITORING_ENABLED=false`, отключить технический внешний канал. Откат кода не требует удаления таблиц. Миграция аддитивна; не удалять журнал и не откатывать бизнес-данные ради отключения мониторинга. Перед отдельно разрешённым выпуском нужна проверенная копия БД/Auth/Storage.

Ожидают решения владельца: получатели, внешний канал, узел наблюдения, рабочее окно, частота/пороги, срок хранения БД и доверенный подписывающий процесс резервирования. До этого демонстрация и CI используют только тестовые значения.
