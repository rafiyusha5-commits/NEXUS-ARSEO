## Запуск

Нужны Node 24, зависимости lockfile, Docker, локальный образ `postgres:16`
и Playwright 1.62.1 с Chromium. База создаётся автоматически: UUID-контейнер,
`--network=none`, tmpfs, никаких портов, URL баз или env-файлов.

```sh
corepack pnpm install --frozen-lockfile
docker pull postgres:16
# После подготовки инструментов — одна команда:
NEXUS_TEST_PLAYWRIGHT=/absolute/path/to/playwright node scripts/test-historical-shipment.mjs
```

PowerShell: задайте `$env:NEXUS_TEST_PLAYWRIGHT` и выполните тот же `node ...`.
Если Playwright установлен в доступном module path, переменная не нужна.
В CI инструменты устанавливаются во временный каталог; рабочие сервисы,
Google, OCR, LLM, Telegram и ключи не используются.

Результаты: `test-results/historical/capture.json`, `readiness.json`,
снимки 1440/390 px. Снимки только синтетические, каталог исключён из Git.
Код выхода **2** означает невыполненный исторический контракт, не успешный E2E.
Код 1/другой ненулевой до формирования отчёта — сбой инфраструктуры/проверки.

| Две вкладки/обновление/ограничения | Идемпотентность существующих SQL-операций | Только чтение отчёта; скрытие цены — UI-тест, не доказательство RLS |

Таким образом отсутствуют полноценный изолированный HTTP-стенд
Auth/PostgREST/Storage, выполнение server actions через формы и проверка
двух одновременных записей из вкладок. Существующая Supabase SQL-заглушка
не является таким стендом. Это незавершённая часть работы, не утверждение,
что пользовательские формы проверены. Реальные документы не использовались.

Браузерный clock также фиксирован; системная дата и правила RPC не меняются.

## Подтверждённый дефект: оплаченное распределяется на полученное

Файл `supabase/migrations/202609279100_reviewed_customs_costing.sql`,
функция `calculate_shipment_cost`: цикл выбирает `received_quantity` как
количество, затем весь распределённый `goods_cost` делится на это количество.

Воспроизведение: `supabase/tests/diagnostics/historical_paid_shortfall.sql`.
Синтетическая позиция 100 шт. по 10 EUR, получено 98; через существующие RPC
создать goods_cost 1000 EUR, подтвердить, распределить, отметить оплаченным,
рассчитать себестоимость. Получено: goods=1000, quantity=98,
unit_landed_cost=**10.2041**, тогда как правило владельца запрещает
автоматическое перераспределение и предполагает **10** до отдельных операций
по повреждению/возврату/списанию.

Последствие: автоматическое увеличение удельной себестоимости оставшегося товара.
Предложение: отдельно согласовать и реализовать учёт оплаченной стоимости
и количественной базы вместе с отдельными операциями потерь; не заменять
одну формулу другой в этом тестовом PR. Утверждение расчёта переносит цену
в партии, поэтому менять правило без ревью нельзя.

Диагностический SQL возвращает факт, не утверждает, что 10.2041 правильно;
команда исторического контракта и отдельный CI завершаются неуспехом.
Старый пилотный assert про goods_total=346 описывает старый сценарий без
оплаченного goods_cost; он не проверяет и не отменяет правило владельца.

## После независимой проверки 20.10.2026

Описанный выше результат **10.2041 относится к исходной версии**.
Миграция `202610200500_purchase_cost_quantity.sql` в интеграционной ветке
исправляет его: диагностический сценарий возвращает **10**, а отдельный
`purchase_cost_quantity.test.sql` требует это значение и сохранность приёмки.
Повторённый SQL-пилот сохранил итог 396 EUR и движения склада.

Адаптер fenced OCR из #55 сохранён. Общие SQL и тесты приложения проверены
на совместном дереве. Полный браузерный поток остаётся незавершённым;
Draft и неуспешный `historical-readiness` сохраняются именно по этой причине.
Рабочие базы не менялись.
