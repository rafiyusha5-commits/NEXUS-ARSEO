# Историческая поставка: полный браузерный сценарий

Работа #56 продолжена в интеграционной ветке `integration/documents-costing-pilot-20261020`,
PR #57, вместе с #53–55 и исправлением правила закупочной стоимости.
Рабочие базы и сервисы не используются. Готовность определяется отдельным
заданием `historical-readiness`, а не успехом обычных SQL/TypeScript проверок.

## Изоляция и запуск

Нужны Node 24, зависимости lockfile, Docker, Supabase CLI 2.121.0,
образ `postgres:16` и Playwright 1.62.1 с Chromium.

```sh
corepack pnpm install --frozen-lockfile
docker pull postgres:16
NEXUS_TEST_PLAYWRIGHT=/absolute/path/to/playwright node scripts/test-historical-shipment.mjs
```

Команда не принимает URL базы или внешние endpoints. SQL-пилот создаёт свой
контейнер PostgreSQL 16 без сети. Браузерный сценарий создаёт ещё один отдельный
локальный Supabase с уникальным project_id: настоящий Auth, PostgREST, Storage
и PostgreSQL (версия записывается в результат; у CLI 2.121.0 — PostgreSQL 17.11).
После выполнения этот стек останавливается без сохранения резервной копии.
Общие SQL-проверки и конкурентные тесты отдельно продолжают выполняться на PostgreSQL 16.

Временная копия приложения получает только отслеживаемые Git файлы, без `.env*`.
Ключи создаются самим одноразовым Supabase. Служебный ключ используется только
для создания тестовых пользователей, в приложение он не передаётся.
SQL до входа создаёт только справочники и права; затем SQL используется только
для чтения контрольных снимков. Все бизнес-изменения выполняет браузер через
обычные формы и серверные действия Nexus с JWT сотрудника.

Drive и OCR подменены только на внешней HTTP-границе тестового процесса.
Drive-адаптер отклоняет любую запись. Приложение действительно скачивает байты,
проверяет версии и SHA-256, загружает их в настоящий тестовый Storage,
вызывает OCR и сохраняет предложение в базе. Ответ OCR — синтетический текст;
PNG — синтетические изображения, а не документы компании. Обычная production-сборка
проверяет реальные шрифты, функциональный стенд использует тестовый hook next/font,
чтобы загрузка шрифтов из CDN не блокировала проверку форм.

## Сценарий через формы

- Вход пользователя «Директор» через настоящий Auth.
- Создание исторической импортной поставки напрямую, два товара и два автомобиля,
  распределение 60/90 единиц. Предварительный прогноз и план закупок здесь не вводятся.
- Привязка синтетической папки; импорт инвойса, двух CMR, упаковочного листа и декларации.
- OCR с видимым индикатором; чтение товарных строк инвойса, упаковочного листа и ДТ.
- Явное назначение транспортного контекста с причиной; ручное исправление реквизита
  инвойса, подтверждение всех пяти источников, повторное чтение без потери подтверждений.
- Отдельная проверка отсутствующего CMR второй машины; добавление связи через форму
  документа и повторная проверка отчёта.
- Приёмка двух машин: 150 заказано, 147 годных, 1 повреждённая и 2 недостающие единицы.
  Обновление страницы не создаёт повторный приход.
- Заказ на 7 коробов по 10 штук, FEFO-резерв, повтор резервирования.
  Подтверждение без гарантийного письма отклоняется; после оформления и утверждения
  письма заказ подтверждается.
- Перемещение 10 штук между своими складами без нового прихода.
- Отгрузка из двух вкладок одновременно: одна выдача 70 штук, нулевой активный резерв.
- Возврат одного короба, карантин и решение о возврате в продажу.
- Фактический расход 50 EUR, распределение, расчёт и утверждение себестоимости 396 EUR.
- Завершение этапов, закрытие, повторное открытие с причиной и повторное закрытие.
- Итоговый отчёт на 1440/390 px и обновление страницы без изменения остатков.
- Вторая настоящая сессия с личными запретами: закрытые документы и закупочная
  стоимость недоступны.
- Отдельная поставка для правила 100/98: оплачено 1000 EUR за 100 единиц,
  принято 98; расчётная база 100, себестоимость единицы 10, приёмка остаётся 98.

## Контрольные точки

| Этап | Остаток | Резерв, шт. | Движений | Приёмок |
|---|---:|---:|---:|---:|
| Приёмка | 147 шт. | 0 | 3 | 2 |
| Резерв | 147 шт. | 70 | 3 | 2 |
| Перемещение | 147 шт. | 70 | 5 | 2 |
| Отгрузка | 77 шт. | 0 | 7 | 2 |
| Возврат | 77 шт. + 1 короб | 0 | 8 | 2 |
| Закрытие | 77 шт. + 1 короб | 0 | 8 | 2 |

В основном сценарии 1 короб = 10 шт.; разные единицы не суммируются как «78».
Партии сохраняют происхождение от поставки и автомобиля. Отдельная проверка
100/98 использует другой товар и не входит в эти контрольные суммы.
Браузерные даты задаются относительно дня запуска; SQL-пилот сохраняет свои
фиксированные даты. Системное время и функции бизнес-даты не подменяются.

## Доказательства и критерий готовности

`test-results/historical/` содержит SQL `capture.json`, фактический
`browser-result.json`, итоговый `readiness.json`, журнал внешних запросов,
журналы сборки/сервера и снимки экрана. При ошибке сохраняются шаги,
текст страницы, URL и снимок. Все данные синтетические, каталог исключён из Git.

`browserEvidenceProblems` требует полный набор контрольных точек, утверждённый
расчёт, доказательства OCR, ручных подтверждений, двух вкладок, комплектности CMR,
ограниченного доступа и правила 100/98. Неполный результат или отклонение чисел
даёт ненулевой код. Регрессии проверяют, что пропуск доказательства и лишнее
складское движение не превращаются в успешную готовность.

Зелёный результат доказывает этот синтетический сценарий. Он не доказывает
качество распознавания настоящего OCR, совместимость всех оригиналов HS-39,
работу реального Google Drive, нагрузочную устойчивость или отсутствие всех
предупреждений в произвольной поставке. Перенос в рабочую базу — отдельный шаг.
