# Автоматические проверки (GitHub Actions)

Workflow [checks.yml](../.github/workflows/checks.yml) проверяет каждый открытый или
обновлённый Pull Request, включая Draft и интеграционные ветки, и отдельно итоговый
`main` после push. Push рабочей ветки не создаёт второй прогон. Для ветки без PR
автоматического прогона нет: открыть Draft PR до передачи работы.

## Полный набор проверок

| Check | Содержимое | Таймаут |
|---|---|---|
| `app` | Frozen install, typecheck, lint, все unit-тесты, production build | 30 минут |
| `database` | PostgreSQL 16: все миграции, повторное применение, SQL/RLS и конкурентные проверки | 25 минут |
| `audit` | Frozen install и актуальный `audit:ci`, без пропуска ошибок реестра | 10 минут |
| `pilot-docker` | Docker PostgreSQL 16, полный SQL-набор и повторяемый пилот | 20 минут |
| `historical-readiness` | SQL-контракт, компонентные проверки и полный авторизованный браузерный цикл с настоящими локальными Auth/PostgREST/Storage | 45 минут |
| `recovery-drill` | Создание синтетических данных, копирование БД и Storage, уничтожение исходного стенда, восстановление в пустой экземпляр, сравнение данных/файлов/прав и вход через приложение | 45 минут |

Все шесть заданий выполняются параллельно, без `paths`, условий по Draft/labels,
`continue-on-error` или пропуска тестов при cache hit. Имена checks сохраняются.
Группа `checks-${{ github.event.pull_request.number || github.ref }}` и
`cancel-in-progress: true` отменяют устаревшую попытку того же PR/ветки, не затрагивая
другие PR. Для будущего разделения на несколько workflow группы потребуется
развести по имени workflow; в первом этапе такого разделения нет.

Node.js 24; pnpm определяется полем `packageManager` в `package.json`.
SQL-проверка `security_audit` сверяет разрешённые `SECURITY DEFINER` RPC, RLS и гранты.
В браузерном/восстановительном стенде используется реальный локальный Supabase;
его версия PostgreSQL отдельно фиксируется в доказательствах и не заменяет PG16 SQL-набор.

## Безопасность и внешние сервисы

- `permissions: contents: read`; `persist-credentials: false` у всех checkout.
- Нет `pull_request_target`, выдачи write-разрешений, обращений к `secrets`,
  автоматического merge или deployment. У `pull_request` из того же репозитория
  секреты в принципе могут быть доступны при явной передаче; workflow их не передаёт.
- Только одноразовые синтетические БД и файлы. Приложение браузерного стенда читает
  документы через подменённые Drive/OCR HTTP-границы. Рабочие Google, OCR, LLM и
  Telegram не используются. Это не утверждение о полной сетевой изоляции раннера:
  ему нужны реестры пакетов, образы и Actions.
- Восстановление включает права, ручные подтверждения, Auth и реальные файлы Storage.
  В артефакты восстановления выходят только JSON-результат и скриншоты, не резервные
  копии, пароли или ключи. Существующие ограничения артефактов не меняются.

## План защиты main — пока НЕ применён

На 21.10.2026 API показывает `main.protected=false`; API защиты и rulesets отвечает
403: `Upgrade to GitHub Pro or make this repository public to enable this feature`.
Добавление карты и бюджета Actions $5 не включает защиту приватной ветки.
Репозиторий должен оставаться приватным. Этот PR не меняет тариф, расходы, доступы
или настройки GitHub.

1. Владелец отдельно согласовывает подходящий тариф: для текущего личного приватного
   репозитория — GitHub Pro; перенос в организацию с GitHub Team является другим
   вариантом и не нужен для этого этапа. Стоимость тарифа отделена от бюджета Actions.
2. После согласования включить protection для точного имени `main`: обязательный PR,
   минимум одно независимое одобрение, сброс устаревших одобрений после push,
   разрешение всех обсуждений, запрет force push и удаления, без обхода администраторами.
3. Требовать все шесть checks из таблицы от GitHub Actions и актуальность ветки
   относительно main. Включать имена после появления этих checks на соответствующей
   основе; не требовать несуществующее имя. Переименование обычно блокирует merge,
   а не автоматически заменяет старое требование.
4. Подготовить CODEOWNERS для `.github/` (включая сам CODEOWNERS), `scripts/`,
   SQL/миграций и тестовой инфраструктуры, включить обязательное ревью владельцев.
   Назначить реальных независимых проверяющих с write-доступом: автор не может
   одобрить собственный PR; один владелец на его собственных PR создаст тупик.
   ИИ под тем же GitHub-аккаунтом не является независимым reviewer.
5. Проверить на отдельной тестовой ветке/PR: красный обязательный check блокирует
   merge, старый зелёный SHA не разрешает новый коммит, обновление базы требует
   актуальной проверки; правила не обходятся администратором. Main для этих проб не менять.
6. Слияние остаётся ручным и только по разрешению владельца. Merge queue пока не
   включать: для неё отдельно потребуется событие `merge_group` и проверка доступности
   на выбранном тарифе. Автоматическое слияние не включать.

До доступной защиты действует только процесс: основной проверяющий сверяет текущие
head/base и все шесть результатов перед ручным merge, остальные разработчики работают
через PR. Это НЕ технический запрет прямого push и не равно branch protection.
Даже администратор защищённого репозитория может изменить сами настройки защиты;
доступ к настройкам и учётным данным владельца нужно ограничивать отдельно.

## Проверка первого этапа и учёт расходов

Сравнивать с эталонным №260: app 231 с, database 103 с, pilot-docker 243 с,
audit 20 с, historical-readiness 462 с, recovery-drill 530 с.
Итого 1589 с (26:29); округление каждого job вверх даёт 29 минут.
При тарифе Linux x64 $0.006/мин это $0.174 до включённой квоты и других расходов.

Зафиксировать для нового head: один PR-прогон без push-дубля, шесть успешных checks,
cache hit/miss каждого устанавливающего зависимости задания, время jobs и сумму
округлённых минут. Для холодного и тёплого кеша можно повторить тот же SHA без
изменения кода. Не заявлять статистически доказанную экономию по одному прогону:
время загрузки образов, реестров и shared runners меняется. Фактические результаты
и ссылки на Actions фиксируются в описании PR, чтобы их запись не запускала новый CI.

Снятие push-дубля в прежней схеме даёт почти половину расхода на обновление PR;
относительно №260 эта экономия уже получена. Первый этап кеширования даёт небольшую
дополнительную экономию и может не пересечь порог округления jobs. Полные тесты
сохраняются даже при отсутствии измеримого ускорения.

## Локальное воспроизведение

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm typecheck
corepack pnpm lint
corepack pnpm test
corepack pnpm build
corepack pnpm run audit:ci
corepack pnpm run test:db       # PostgreSQL 16 и bash
corepack pnpm run test:db:docker
```

Полный браузерный цикл и восстановление требуют Docker, Supabase CLI 2.121.0 и
Playwright 1.62.1 с Chromium. Их штатные команды и доказательства описаны в
[historical-shipment-browser-e2e.md](historical-shipment-browser-e2e.md) и
[recovery-drill.md](recovery-drill.md). Использовать только одноразовые тестовые стенды.
