# Автоматические проверки (GitHub Actions)

Workflow [`.github/workflows/checks.yml`](../.github/workflows/checks.yml) запускается на каждый push в любую ветку и на каждый Pull Request. До его появления все проверки выполнялись вручную, а модель безопасности проекта опирается на `test:db`: `supabase/tests/security_audit.test.sql` сверяет список `tests.sec_exec_allow` с фактическими правами `EXECUTE`, и забытая функция роняет прогон только при запуске тестов.

## Что выполняется

| Проверка | Что внутри | Таймаут |
|---|---|---|
| `app` | `pnpm install --frozen-lockfile`, `typecheck`, `lint`, полный `test`, production `build` | 30 минут |
| `database` | серверные программы PostgreSQL 16, затем `pnpm run test:db` | 25 минут |
| `audit` | `pnpm install --frozen-lockfile`, затем `pnpm run audit:ci` | 10 минут |

Node.js 24, pnpm берётся из поля `packageManager` файла `package.json` через `corepack enable`, то есть версия пакетного менеджера задаётся проектом, а не настройками CI.

**Названия `app`, `database` и `audit` менять не следует.** На них будет ссылаться настройка защиты ветки «Require status checks to pass»: переименование проверки сделает требование недействительным, и защита пропустит непроверенный код. Эта настройка выполняется владельцем в интерфейсе GitHub; workflow её не меняет.

## Безопасность прогона

- Права сведены к `contents: read` на уровне workflow. Запись в репозиторий, выпуск пакетов и развёртывание недоступны.
- `pull_request_target` не используется. Код из Pull Request исполняется только в контексте `pull_request`, где у задания нет доступа к секретам репозитория.
- `actions/checkout` выгружается с `persist-credentials: false`, поэтому токен прогона не остаётся в `.git/config`.
- Устаревшие прогоны отменяются: группа `concurrency` считается по номеру Pull Request или по ветке.
- Кеш зависимостей привязан к точному хешу `pnpm-lock.yaml`, без общих префиксов (`restore-keys`). При изменении lockfile зависимости собираются заново, а не берутся из кеша другой версии.

## Только синтетические данные

CI не обращается ни к одному рабочему сервису. В workflow нет ни одного обращения к `secrets`, поэтому рабочих ключей в прогоне нет вовсе:

- проект Supabase и рабочая база не используются; SQL-тесты поднимают собственный одноразовый кластер PostgreSQL 16 в каталоге задания, применяют к нему все миграции, проверяют их повторное применение и удаляют кластер вместе с заданием;
- Google Drive и Google Sheets не читаются и тем более не изменяются;
- OpenAI, движок OCR и бот Telegram недостижимы;
- ассистент, OCR и Telegram остаются выключенными, потому что включающие их переменные (`AGENT_ENABLED`, `OCR_PROVIDER`, `TELEGRAM_ENABLED` и признания передачи данных) в прогоне отсутствуют;
- сборка проходит без переменных окружения. Если когда-нибудь потребуются значения, допустимы только очевидно фиктивные; рабочие настройки в CI не добавляются.

CI не выполняет развёртывание, не применяет миграции к рабочей базе и не объединяет Pull Request.

## Проверка зависимостей

`pnpm run audit:ci` запускает [`scripts/audit-prod.mjs`](../scripts/audit-prod.mjs): он получает `pnpm audit --prod --json` и отклоняет **любую** находку, которая не разобрана заранее. Уровень серьёзности поводом для пропуска не является: умеренная находка блокирует прогон так же, как высокая, и целые уровни не игнорируются.

Единственное действующее исключение — `GHSA-w5hq-g745-h8pq` для `uuid`, который приходит путём `.>exceljs>uuid`. Обоснование разобрано в [`security-audit.md`](./security-audit.md), раздел «Зависимости». Исключение привязано не только к пакету, но и к пути: если `uuid` придёт другим путём, обоснование перестанет действовать и проверка упадёт. Когда находка исчезнет, скрипт напомнит удалить исключение.

Чтобы добавить новое исключение, нужны три вещи: невозможность обновиться, разобранная причина недостижимости уязвимого кода и запись в `docs/security-audit.md`. Иначе зависимость обновляется.

## Как повторить локально

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm typecheck
corepack pnpm lint
corepack pnpm test
corepack pnpm build
corepack pnpm run audit:ci
corepack pnpm run test:db   # нужны initdb, pg_ctl и psql от PostgreSQL 15+
```

На Windows серверных программ PostgreSQL обычно нет, поэтому `test:db` удобнее выполнять в одноразовом контейнере:

```bash
docker run --rm -e LC_ALL=C.UTF-8 \
  -v "$PWD/supabase:/src/supabase:ro" -v "$PWD/scripts:/src/scripts:ro" -v "$PWD/docs:/src/docs:ro" \
  postgres:16 bash -c 'mkdir /tmp/repo && cp -r /src/supabase /src/scripts /src/docs /tmp/repo/ \
    && cd /tmp/repo && PGBIN=/usr/lib/postgresql/16/bin bash scripts/test-db.sh'
```

## Известные ограничения

- Для Pull Request из этого же репозитория прогон запускается дважды: по событию `push` в ветку и по событию `pull_request`. Это следствие требования проверять оба события. Если понадобится экономить минуты, `push` можно сузить до `main` и интеграционных ветвей, не меняя названий проверок.
- Действия закреплены мажорными тегами (`actions/checkout@v4`, `actions/setup-node@v4`, `actions/cache@v4`). Для более строгого режима их закрепляют хешем коммита; это меняет порядок обновления, поэтому решение за владельцем.
- Задание `database` рассчитывает на серверные программы PostgreSQL 16 в образе раннера и устанавливает пакет `postgresql-16`, только если их нет. Смена образа раннера может повлиять на время прогона, но не на результат.
- Приватный репозиторий расходует минуты GitHub Actions. Платные настройки и лимиты workflow не изменяет.
