# Агент «Сверка»

Агент сверяет документы активной поставки с её карточкой и сообщает о проблемах до того, как они всплывут на таможне.

- Миграция: `supabase/migrations/202609276400_document_check_agent.sql`. Применяется после `202609276300_telegram_delivery_authorization.sql`, повторное применение безопасно.
- Тесты: `supabase/tests/document_check_agent.test.sql`, `tests/document-check/rules.test.ts`, ссылка уведомления — `tests/notifications/rules.test.ts`.
- Экран: карточка поставки → вкладка «Документы» → блок «Сверка документов с карточкой» (`src/components/documents/shipment-document-check-panel.tsx`).

## Принципы

- Только правила в коде и базе. Языковая модель не используется, данные никуда не отправляются.
- Агент ничего не исправляет и не пишет в поставку, автомобили, документы и результаты распознавания. Его записи — собственное состояние проверки (`shipment_document_checks`) и уведомления.
- Задачу создаёт только сотрудник кнопкой «Создать задачу» у замечания. Задача назначается тому, кто нажал; текст берётся из текущей проверки в базе, а не из формы.
- Действуют права сотрудника: проверку видят и запускают только с правами `shipments.view` и `documents.view`. Названия сгенерированных документов с ценами скрываются от тех, кому эти документы недоступны (как в журнале документов). Закупочные цены в проверке не участвуют.
- Google Drive и Google Sheets агент не использует.

## Что проверяется

| Проверка | Как | Уровень |
|---|---|---|
| Госномер автомобиля и прицепа | значение из документа сравнивается с карточкой автомобиля, к которому привязан документ (или с единственным автомобилем поставки). Пробелы, дефисы и регистр не учитываются | расхождение — ошибка; номер есть только в документе — предупреждение |
| Госномер в документе без привязки при нескольких автомобилях | номер должен быть у одного из автомобилей поставки | не найден — ошибка |
| Вес брутто и нетто | сравнивается с расчётом по позициям и упаковке товаров (как во вкладке «Загрузка»). Документ автомобиля — с этим автомобилем, остальные — со всей поставкой. **Допуск: 2 % или 50 кг, что больше** | выход за допуск — ошибка; расчёт невозможен (нет упаковки, товары не распределены) — предупреждение |
| Количество паллет | должно лежать между округлениями расчёта вниз и вверх | предупреждение |
| Номер договора | в инвойсе, спецификации и договоре — с договором поставки из карточки | предупреждение |
| Номер инвойса | текст документа — с номером, под которым инвойс зарегистрирован | предупреждение |
| Обязательные документы | по правилам `document_requirements`: для поставки и для **каждого автомобиля** (`applies_to = shipment_transport`). Документ поставки засчитывается автомобилю, если автомобиль один | до таможни — предупреждение «нужен до таможенного оформления»; после начала таможни или этапа требования — ошибка |
| Сроки действия | документы с `valid_until` и договор поставки (`valid_to`): истёк или истечёт до планового прибытия (автомобиля, иначе поставки). Проверяется, пока груз не прибыл | ошибка |
| Состояние распознавания | документ не прочитан или документы расходятся между собой и ждут сотрудника | предупреждение |

Таможня считается начатой, если поставка в статусе «Таможня» или дальше, автомобиль на таможне или прибыл, либо этап категории `customs` в работе или завершён.

Закрытые и отменённые поставки не проверяются.

## Когда запускается

- **После каждого распознавания**, повторного распознавания, подтверждения данных и привязки документа к автомобилю — функция `run_shipment_document_check(p_shipment_id, 'recognition')` с сессией сотрудника. Ошибка проверки не мешает распознаванию.
- **По кнопке «Проверить сейчас»** в блоке — то же с источником `manual`.
- **Раз в день** для всех активных поставок — `run_document_checks()`, только `service_role`. Пример для pg_cron (расширение включается в Dashboard → Database → Extensions, миграция его не включает):

  ```sql
  select cron.schedule('nexus-document-checks', '40 1 * * *', $$select public.run_document_checks()$$);
  ```

  `40 1 * * *` — 06:40 по времени Казахстана (UTC+5). Задание выполняется внутри базы, секретный ключ не нужен.

Карточка всегда показывает результат, посчитанный в момент открытия (`shipment_document_check`, только чтение). Хранимое состояние нужно только для уведомлений.

## Уведомления

- Только в Nexus (раздел «Уведомления» и счётчик). В Telegram не отправляются.
- Получатели: активные сотрудники с ролями **«Администратор системы», «Директор», «Директор по логистике», «Старший менеджер по логистике», «Специалист по логистике»**, у которых есть `shipments.view` и `documents.view`. Список ролей — `private.document_check_recipient_roles()`; модульный тест сверяет его с `src/lib/document-check/rules.ts`.
- Тип `discrepancy` («Расхождение»), ссылка ведёт в блок проверки карточки.
- О проблеме сообщается **один раз**. Повторные запуски с теми же проблемами ничего не присылают. Если проблему исправили, а потом она появилась снова, придёт новое уведомление.
- В тексте только число ошибок и предупреждений и вид проблем (например, «Госномер прицепа в документе не совпадает с карточкой автомобиля»). Номера, вес и названия документов видны только в карточке.

## Функции

| Функция | Кто | Назначение |
|---|---|---|
| `shipment_document_check(p_shipment_id)` | сотрудник с `shipments.view` и `documents.view` | текущие замечания для карточки, только чтение |
| `run_shipment_document_check(p_shipment_id, p_source)` | то же | проверить сейчас и уведомить о новых проблемах; `p_source` — `recognition` или `manual` |
| `run_document_checks(p_today)` | `service_role` | ежедневная проверка всех активных поставок |

Таблица `shipment_document_checks` закрыта для прямого чтения и записи.

## Что можно настроить позже

- Получатели — `private.document_check_recipient_roles` и `DOCUMENT_CHECK_RECIPIENT_ROLES`.
