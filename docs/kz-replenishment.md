# Автозаказ для Казахстана

Первая интеграция в Nexus, отдельная тестовая ветка от
`8ff0835e6ac358644579629a0cb5187699a4134a` (`codex/document-actions-across-nexus`).
Рабочие базы, установленное приложение, Google Drive и Google Sheets этой работой
не изменяются. Выпуск и миграция требуют отдельного решения владельца.

## Как пользоваться

Раздел «Закупки → Автозаказ Казахстан», адрес `/replenishment`.

1. Выбрать поставщика, три разных склада — Актобе, Астана и Алматы — и сроки
   подготовки, международной доставки с таможней, доставки в город и пересмотра.
   Сохранить настройки с основанием. Все числа по умолчанию — предложения,
   их необходимо проверить. Настройки сохраняются отдельными версиями.
2. Подтвердить полноту истории продаж. Для нового товара или неполной истории
   задать средний дневной спрос отдельно по городу, с причиной. Ноль тоже требует
   явного решения. Товар без истории не исчезает из расчёта.
3. Разметить свободный запас и ожидаемые приходы: сколько предназначено для KZ,
   сколько — под экспортный заказ. Одна партия может делиться количественно.
   Неразмеченный остаток блокирует подготовку плана. Указать город и известные
   даты партии/прибытия для ожидаемого прихода. Это сведения планирования, они
   не изменяют партии склада или подтверждённые документы поставки.
4. Посмотреть расчёт по двум городам, предложения перемещения и риски ОСГ.
   Сохранить версию расчёта. Изменившиеся исходные данные требуют нового расчёта.
5. Подготовить черновик прогноза и пройти существующее согласование прогноза.
   Затем подготовить черновик плана закупки. Если учитывается запас другого
   города/Актобе, явно подтвердить это; складские документы оформляются отдельно.
   Изменение количества в согласованном прогнозе требует нового расчёта с
   соответствующим ручным спросом. Автоматического утверждения нет.
6. Скачать XLSX. WhatsApp открывает подготовленный текст. Для Telegram —
   скопировать показанный текст, открыть Telegram и выбрать чат; при запрете
   буфера браузером текст доступен для ручного копирования. Файл прикладывает
   сотрудник. На устройствах с Web Share файл можно передать
   через системный выбор приложения. Получатель и отправка всегда выбираются
   сотрудником; автоматических сообщений нет.

## Что считает код

- Только исполненные продажи клиентам KZ со складов Астаны и Алматы, каждый
  город отдельно. Продажи российским покупателям, Актобе и внутренние перемещения
  не входят в историю спроса. Возврат не создаёт новую продажу; валовая история
  продаж не уменьшается на возврат, возвращённый доступный запас учитывается
  обычным складским источником.
- Окно истории заканчивается вчера по рабочему дню Казахстана. Средний спрос
  — количество / число календарных дней. Неполный месяц не считается полным.
  При дефиците или неполной загрузке истории сотрудник задаёт ручную оценку.
- Горизонт — подготовка + международная доставка/таможня + доставка в город +
  период пересмотра. Страховой запас: коэффициент × стандартное отклонение
  дневных продаж × корень из горизонта. Это не одинаковая надбавка в процентах.
- Подтверждённые/зарезервированные заказы в пределах горизонта задают нижнюю
  границу спроса. Уже зарезервированные количества исключаются одновременно
  из спроса и свободного запаса. ОСГ новых клиентов в открытых заказах также
  учитывается, даже если они ещё отсутствуют в истории.
- Запас моделируется по дням и FEFO, с отдельными требованиями клиентов.
  Учитываются доступность партии, дата прихода, срок и единица; неизвестный
  ОСГ не становится пригодным автоматически. Формула процента и округление
  соответствуют `private.sale_shelf_life_pct`.
- Товар для российского экспортного заказа не уменьшает закупку для KZ.
  Назначение свободного товара в Актобе требуется подтвердить отдельно.
- Перемещение предлагается только из излишка после спроса и страхового запаса
  донора, с учётом времени доставки и ОСГ. Один источник расходуется в расчёте
  один раз; складской короб не предлагается перемещать дробной частью.
  Предложение не создаёт движение и не скрывает риск ОСГ.
- Закупка округляется вверх до короба. В таблице видны оба результата:
  без неподтверждённых перемещений и после их подтверждения. План закупки
  использует второй только с явным согласием учесть существующий запас KZ.

## Доступ, история и защита от повторов

Миграция `202611080300_kz_replenishment.sql` добавляет четыре таблицы истории
и пять публичных RPC. RLS включена; прямой доступ к новым таблицам не выдаётся.
RPC требуют действующих прав на товары, остатки, продажи, клиентов, поставки,
склады, поставщиков и подробности планов. Для записи дополнительно нужны
права создания/изменения, для прогноза — штатные права прогноза. Личный запрет
сохраняет приоритет. После ожидания блокировки права проверяются повторно.

Снимок сохраняет исходные данные, настройки, версию формулы и сотрудника.
Одинаковые исходные данные повторно возвращают тот же расчёт. Изменённые данные
и новый рабочий день делают прежний снимок историческим. Повтор решения
возвращает первоначальный черновик; изменённый повтор отклоняется. Подготовка
планов одного поставщика сериализована между версиями настроек. Незавершённый
план по тем же товарам блокирует повторную закупку, в том числе если он был
подготовлен обычным способом.

Это механизм подготовки, а не резервирования. RPC плана принимает предложение
уполномоченного сотрудника; обычный интерфейс рассчитывает его на сервере,
а база проверяет структуру, источники, повтор, упаковку и прогноз. Штатное
согласование сохраняется; SQL не выдаёт клиентский JSON за утверждённый расчёт.

Новые таблицы не получают общих прав service_role. ИИ использует серверный
ключ только для существующих учётных RPC бюджета. Бизнес-снимок читается
сессионным клиентом с текущими правами сотрудника.

## Объяснение ИИ и экспорт

ИИ вызывается только кнопкой, при включённом штатном провайдере и праве
`agent.use`, с лимитами и учётом бюджета. В модель поступают обезличенные
числовые итоги, без названий клиентов, документов, артикулов, цен и свободных
причин. Маскирование выполняется до отправки и перед показом. Неизвестное
использование токенов учитывается консервативно, автоматического повтора нет.
После ответа повторно проверяется актуальность и доступ.

Числа в таблице и XLSX производит код. Пояснение модели явно помечено как
требующее проверки; оно не меняет расчёт. Четыре листа XLSX: предложение,
перемещения, риски ОСГ и основания. Текст записывается как текст, не формулы.

## Проверки и границы первой версии

- `corepack pnpm typecheck`, `lint`, `test`, `build`.
- `corepack pnpm test:db`: новая схема, повтор миграции, права, личные запреты,
  отсутствие изменений остатков/продаж, история, повтор, упаковка, согласование.
  `scripts/test-replenishment-concurrency.mjs` проверяет настоящие конкурентные
  транзакции, конкурирующие версии настроек и отзыв доступа при ожидании.
- `node scripts/test-replenishment-ui.mjs <path-to-playwright>`: реальные React
  формы на синтетическом HTTP-стенде, 1440/390 px, причины, блокировки, отсутствие
  автоматической отправки, видимость скачивания. Встроен в существующее задание
  historical-readiness; все шесть проверок CI сохранены.
- `tests/pilot/replenishment-forms.mjs` дополнительно включён в существующий
  полный браузерный прогон historical-readiness: настоящие Next Server Actions,
  Supabase Auth и PostgREST; создание настроек, ручной спрос, назначение запаса,
  снимок, штатное согласование прогноза, черновик закупки и XLSX. Проверяются
  неизменность рабочих таблиц, устаревший снимок и личный запрет.
- Тесты ядра покрывают города, экспорт, назначения, повторы, резервы, новый SKU,
  поздний приход, ОСГ, истечение срока, перемещения и страховой запас. XLSX
  дополнительно открывается ExcelJS. ИИ проверяется подставным провайдером,
  без платного обращения к модели.

Локальные данные — синтетические, PostgreSQL 16. Локальный компонентный стенд
не подменяет полный браузерный проход; последний требует Docker/Supabase и
выполняется отдельным существующим заданием CI.
Реальные документы, историю KZ, рабочие Google-источники и доставку сообщения
получателю эта задача не использует. Перед выпуском нужен приёмочный проход
на отдельном Supabase с данными, разрешёнными владельцем.

Границы алгоритма: дневная средняя и изменчивость, без сезонной модели и
промо-прогноза; спрос распределяется внутри горизонта равномерно. Поле первого
дефицита — оценка модели, не обещание исполнения конкретного заказа. Для истории
используются текущие требования клиентов; будущие изменения договоров не
прогнозируются. Неполные/поздние приходы требуют уточнения. Минимальная партия
производителя и ограничения целой машины пока проверяются при согласовании;
автоматически используется только кратность короба. До 500 товаров и 50 000
строк истории, превышение вызывает явную ошибку, не усечение до 1000.

Риски видны при пересчёте. Существующий «Контроль ОСГ» и его уведомления остаются;
нового расписания и фоновой рассылки автозаказ не добавляет. Изменение настроек
создаёт отдельную версию и требует повторного подтверждения назначения запасов.
Для выпуска: проверить PR → миграция в согласованную тестовую среду → приёмка
владельцем → отдельное разрешение на объединение и обновление основной версии.
