# Проверенные изменения PR 45–49

Основа: `0569ff0c2d81825ac024cfbed1952db0e926d976`. В интеграционную ветку включены
45 (`5117957`), 46 (`9953099`), 47 (`1988c18`), 48 (`1029f4f`), 49 (`3facd22`).
Рабочие базы и сервисы при подготовке не используются.

## Исправления по итогам проверки

- Декларация: база проверяет структуру реквизитов, полную последовательность номеров
  строк, десятизначный ТН ВЭД, известные единицы, числа и предупреждения. Ограничение
  действует и при повторном подтверждении, и через прежние пути записи.
- Новая редакция текстовой декларации создаётся отдельной кнопкой с причиной.
  Файл читается на сервере; перед сохранением повторно проверяются права, версия,
  действующая привязка и время изменения. Предыдущие результат и сверка остаются
  в аудите. Ручные реквизиты сохраняются, подтверждение декларации снимается.
  После повторной ручной сверки статус вновь становится подтверждённым. Запоздалый
  повтор того же запроса не снимает новое подтверждение. Количества, расходы и
  склад эта операция не меняет. Для сканов остаётся отдельный штатный путь OCR.
- Итог разделяет чтение, согласованность и готовность. Отступление от заказанного
  количества сохраняется после подтверждения и не называется складской недостачей.
  Учитываются лишние строки инвойса, неполное чтение и предупреждения товарных строк.
  Информационное сообщение о необходимости ручной сверки не заменяет ошибку чтения.
- Despatch/Dispatch Note: известный английский формат OCR читает штуки из явной
  колонки `boxes (pieces)` и сверяет их сумму с итогом. Строки партий суммируются по
  артикулу и единице, связь берётся из графы 44 ДТ (04131). Две копии одного номера
  не суммируются; конфликт количеств между ними блокирует совпадение. Неподдержанный
  формат, отсутствие ссылки или неполный итог дают «недостаточно данных».
  Реальные файлы и сохранённый OCR в репозиторий не включены.
- Готовность использует один результат `buildShipmentDocumentReadiness` для обоих
  блоков. Это общая предварительная проверка; окончательный контроль выбранного
  шаблона и автомобиля перед формированием остаётся обязательным.
- Импорт сальдо выбирает однозначный конечный остаток. Начальный остаток не выдаётся
  за конечный. Неоднозначные колонки блокируют импорт.
- Исправление даты/данных сальдо из того же файла требует явной замены каждой строки
  с причиной. Создаётся новая квитанция импорта, прежние сальдо и источник сохраняются.
  Повтор старой или новой редакции возвращает сохранённый результат и не пишет деньги.
  Защита от повторных банковских платежей не меняется.
- Пилот отдельно проверяет отсутствие CMR второй машины и добавляет его перед
  успешным закрытием. Пустой список «известных дефектов» больше не выдаётся за
  заключение о полной готовности системы. Прежний PR 9 отдельно включать не нужно.

## Проверка

На объединённом коде: 699 модульных тестов, 81 SQL-файл на PostgreSQL 16.15,
повторное применение миграций, typecheck, lint и production build. Проверены
10 конкурентных сценариев резервов; повторный и пересекающийся импорт, конфликтующие
исправления сальдо; конкурентные изменения себестоимости и актуальности документов.
Два одинаковых пилотных прогона: 147 принято, 70 отгружено, остаток 77 шт. и
1 короб по 10 шт., резерв 0; себестоимость 396 EUR. Это синтетические данные.
Формы импорта и итог сверки проверяются headless-браузером на 1440 и 390 px.

Docker-проверка теперь требует Node 24 вместе с PostgreSQL 16, потому что SQL runner
запускает JavaScript-проверки гонок. Подготовка образов выполняется отдельно:

```sh
docker pull postgres:16
docker build -f scripts/Dockerfile.db-test -t nexus-db-test:pg16-node24 scripts
node scripts/test-db-docker.mjs
node scripts/test-shipment-pilot.mjs
node scripts/test-shipment-pilot.mjs --all-sql
```

Сами контейнеры одноразовые, `--network=none`, без опубликованных портов и рабочих
переменных. Новый CI job `pilot-docker` проверяет все три команды. Локально Windows
Docker отсутствует; нативный SQL-прогон не подменяет результат Docker CI.

Для развёртывания нужны миграции 9500, 9600 исходных PR и исправления 9700, 9800,
9900 в порядке файлов. Их применение к рабочей или учебной базе — отдельный шаг.
Обновление чтения существующей подтверждённой декларации выполняется явно через
новую редакцию. Совместимость импорта с реальными банковскими файлами компании
остаётся непроверенной до получения образцов.
