# Управляемые сбои документов

PR №64 расширяет существующий historical-readiness: настоящее приложение Next,
две авторизованные браузерные сессии и одноразовые Supabase Auth/PostgREST/Storage.
Внешние документы полностью синтетические. Google, рабочие базы и OCR-провайдер
компании не используются. Новых миграций и бизнес-изменений нет.

## Матрица — десять сценариев

| Сценарий | Что доказывает сквозная проверка |
|---|---|
| После скачивания, до Storage | Ошибка загрузки не создаёт документ или объект; явный повтор создаёт одну версию с проверенными байтами |
| После Storage, до регистрации | Файл физически сохранён, регистрация отсутствует; повтор регистрирует один документ, неопределённый staging сохраняется. Дополнительно теряется ответ уже выполненного RPC: квитанция предотвращает повторную загрузку |
| Timeout OCR и повтор | Истекает настоящий клиентский AbortSignal, запись становится failed; явный повтор проходит, документ и версия не удваиваются |
| Поздний ответ после нового успеха | Старая HTTP-попытка удерживается барьером, новая завершается первой; поздний ответ не меняет полную строку нового результата |
| Поздний ответ после ручного подтверждения | Новый результат подтверждается через форму, затем отпускается старый HTTP-ответ; вся строка, включая автора, дату и ручные поля, неизменна |
| Версия источника изменилась при скачивании | Новая metadata-версия блокирует регистрацию старого чтения; после явного повторного сканирования импорт проходит |
| Отзыв доступа | Выход синтетического Drive-файла из разрешённой папки останавливает импорт; личный deny в настоящей БД во время OCR запрещает сохранение результата |
| Две авторизованные вкладки | Параллельный импорт создаёт один документ/версию/связь; параллельное OCR отправляет один запрос провайдеру |
| Аварийный перезапуск Nexus | Процесс действительно завершается SIGKILL после записи OCR lease; файл и lease сохраняются, активная lease остаётся busy, после истечения появляется явное действие и повтор проходит |
| Один отказ среди успешных файлов | Из трёх файлов два прочитаны, один failed; повтор завершает третий, не переписывая успешные строки |

После каждого сценария сравниваются существующие ручные подтверждения и прежние
строки журнала. Позиции поставок, остатки, движения, продажи, расходы и расчёты
себестоимости остаются прежними. Физические файлы скачиваются из тестового Storage
и сверяются по SHA-256 с зарегистрированными версиями.

## Как устроены отказы

`tests/pilot/fault-http.mjs` — отдельный HTTP-сервер только на loopback. Тестовый
fetch-boundary перенаправляет туда синтетические Drive/OCR-запросы и запросы
к локальному Supabase. Успешные Auth/REST/Storage-запросы действительно доходят
до Supabase. Барьеры имеют подтверждение достижения и ограниченное время ожидания;
нет угадывания порядка запросов по фиксированной паузе. Другие адреса и любые
операции записи в Drive отклоняются. Заголовки, токены и тела запросов не журналируются.

Приложение использует штатную сессию сотрудника. Привилегированное соединение теста
только читает доказательства, временно вводит personal deny и сдвигает временные
поля уже созданной lease. Это ускорение тестовых часов, **не** проверка ожидания
двух часов по настоящему времени. Бизнес-операции и ручное подтверждение выполняются
через формы; привилегированные RPC не подменяют эти действия.

Сбой регистрации с неопределённым результатом намеренно сохраняет приватный
staging-объект: отсутствие дублей документов не означает отсутствие временного
файла. Автоматическая очистка таких объектов в эту задачу не входит.

## Запуск и обязательный результат

```sh
node --test tests/pilot/fault-http.test.ts
NEXUS_TEST_PLAYWRIGHT=/absolute/path/to/playwright node scripts/test-historical-shipment.mjs
corepack pnpm test:recovery
corepack pnpm test:db
```

Нужны Docker, Supabase CLI и Chromium. Runner сам создаёт одноразовый проект;
передавать URL существующей базы нельзя. Обычный historical-readiness дополнительно
выполняет матрицу, recovery-drill сохраняет свой независимый полный сценарий.
Ни одно из шести обязательных заданий CI не удалено и не стало условным.

`test-results/historical/document-faults.json` содержит каждый реально пройденный
сценарий. При отказе сохраняются частичный JSON, страница и снимок. Итоговая readiness
проверяет полный перечень и статусы; отсутствие сценария даёт ненулевой код.
Факт прохождения конкретного коммита устанавливается журналом CI и артефактом,
а не этой инструкцией. До зелёного полного прогона PR остаётся Draft.

Дополнительно сохранены unit-тесты action, SQL-регрессии и конкурентные проверки
на PostgreSQL 16. В браузерном Supabase используется версия PostgreSQL из закреплённого
CLI (в предыдущих прогонах — 17.11); она не заменяет обязательный PostgreSQL 16.

## Границы доказательства

Реальные документы HS-39, внешний Drive, производственный OCR, межсетевые отказы,
длительный простой, полный диск и авария самого PostgreSQL этой матрицей не проверены.
Восстановление из копии проверяет отдельный recovery-drill. Приложение после
SIGKILL перезапускается на том же локальном backend: это не failover кластера.
Никаких изменений main, рабочей БД, прав пользователей компании или расписаний.
