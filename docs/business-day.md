# Рабочий день Казахстана

Находка Н10 аудита 13.10.2026, миграция `202609278300_kazakhstan_business_date.sql`.

База Supabase работает в UTC. Казахстан живёт в UTC+5, поэтому с 00:00 до 05:00 по местному времени «сегодня» по UTC — ещё вчера. Раньше в эти часы база ставила вчерашние фактические даты погрузки и прибытия, прошлый год в номерах в новогоднюю ночь и считала годной партию, срок которой истёк вчера (FEFO-выдача, отгрузка заказа, остатки). Отклонялся и курс, датированный сегодняшним днём.

## Правило

- **База.** Каждая функция, которая берёт текущую дату (`current_date`, `now()::date`, `localtimestamp`), работает с настройкой `set timezone to 'Asia/Almaty'`. Миграция 8300 проставила её всем существующим функциям, не меняя их тела. Новую или переопределённую функцию нужно объявлять так же:

  ```sql
  create or replace function public.example() returns void
  language plpgsql security definer set search_path = '' set timezone to 'Asia/Almaty' as $$ ... $$;
  ```

  Явное `at time zone 'UTC'` для рабочих дат запрещено. В представлениях и значениях по умолчанию дата пишется явно: `(now() at time zone 'Asia/Almaty')::date`.
- **Проверка.** `supabase/tests/business_date.test.sql` падает и называет функцию, если она читает текущую дату без этой настройки. Он же проверяет поведение в двух крайних часовых поясах сессии (UTC−12 и UTC+14): в любой момент хотя бы один из них живёт в другом дне, чем Казахстан.
- **Тесты.** SQL-тесты работают в поясе `Asia/Almaty` (`PGOPTIONS` в `scripts/test-db.sh`). Их собственное `current_date` — тот же рабочий день, что у функций, в любое время суток.
- **Приложение.** Дата «сегодня» для полей ввода и сравнений — `businessToday()` из `src/lib/dates/business-day.ts`, а не `new Date().toISOString().slice(0, 10)` (это дата по UTC).

Казахстан с 1 марта 2024 года живёт в одном поясе UTC+5. Помощники агентов, где указаны `Asia/Qyzylorda` или `Asia/Aqtobe`, дают тот же день.
