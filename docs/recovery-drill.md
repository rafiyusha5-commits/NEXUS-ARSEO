# Воспроизводимая тренировка восстановления Nexus

Основа: `fix/supplier-quantity-baseline-20261021`, `009a0bedd3a371ceaeee66228e1dae4ca0b040d5`.
Только синтетические данные и новые одноразовые локальные контейнеры. Это не утилита подключения к рабочей базе.

## Одна команда

```sh
corepack pnpm test:recovery
```

Предварительные условия: Node 24, pnpm из packageManager, Docker с локальным socket,
Supabase CLI **2.121.0**, образ `postgres:16`, Chromium/Playwright **1.62.1**.
Установить зависимости `corepack pnpm install --frozen-lockfile`; подготовить образ `docker pull postgres:16`.
Playwright можно установить во временный каталог и задать `NEXUS_TEST_PLAYWRIGHT` его абсолютным путём,
как в задании `recovery-drill` файла `.github/workflows/checks.yml`. Порты 54321/54322/3100 должны быть свободны.
Рекомендуемая воспроизводимая среда — Ubuntu 24.04, как CI. Не запускать на машине с владельческим локальным Supabase на этих портах.

Аргументы, пути к готовой копии, URL базы и выбор существующего контейнера **не принимаются**.
Файлы `.env` владельца не читаются и не копируются; окружение процессов составляется по узкому списку.
Удалённый Docker endpoint запрещён. Контейнеры проверяются по случайному имени и ID;
перед очисткой целевой БД проверяются пустота приложения и маркер текущего запуска.

## Что выполняется

1. Существующий `runHistoricalForms` создаёт полный синтетический цикл через Nexus, настоящий локальный Auth/PostgREST/Storage,
   подменные Drive/OCR HTTP-границы: два автомобиля, документы, ручные подтверждения, приёмка,
   перемещение, отгрузка, возврат, расходы и утверждённая себестоимость.
2. Через те же операции добавляются отдельный подтверждённый заказ с активным резервом и документ с двумя различными версиями файлов.
   Это дополняет, а не переписывает пилот. История исполненных резервов остаётся в копии.
3. Приложение и записывающие сервисы останавливаются. Сначала исключаются активные cron и очередь HTTP.
   Создаются `pg_dump --format=custom` и **отдельный** архив физического тома локального Storage.
   До/после копирования сравниваются контрольные суммы всех строк таблиц.
4. Исходный тестовый проект удаляется. Новый проект запускается без миграций приложения; подтверждается пустота.
   Собственная пустая БД пересоздаётся и восстанавливается `pg_restore` с владельцами/ACL.
   В другой пустой том возвращаются файлы Storage. Использование исходного тома запрещено проверкой.
5. Сверяются таблицы, схема, ограничения, RLS, права функций, default privileges, последовательности, личные запреты.
   Через настоящий Auth выполняется новый вход обоих синтетических сотрудников.
   Каждая версия скачивается через Storage API, SHA-256 сравнивается с сохранённой версией документа.
   Сотруднику с личным запретом скачивание запрещено.
6. Приложение собирается с конфигурацией нового экземпляра, без ключей Google/OCR/Telegram/LLM.
   Браузер входит в восстановленный Nexus, открывает реестр и отчёт; проверяются директор и ограниченный сотрудник,
   desktop/mobile. Исходящие fetch-запросы, кроме локальных API, блокируются и делают тест красным.
   После запуска не должны измениться бизнес-таблицы, подтверждения, резервы, движения, состояния и очереди.
7. Тестовый восстановленный проект удаляется. Результат записывается в `test-results/recovery/recovery-result.json`.

## Доказательства и границы

JSON содержит фактические длительности копирования, восстановления БД/файлов и проверки приложения,
SHA-256 обоих архивов, каждого файла/версии, таблиц и схемы, исходный/итоговый commit и версию PostgreSQL.
В CI публикуются только этот отчёт и синтетические снимки — не дамп, Auth-токены, пароли или ключи.
Сами тестовые архивы находятся в новом временном каталоге запуска (`nexus-historical-*/recovery-backup`), вне Git.
После локальной проверки их можно удалить вместе с этим конкретным временным каталогом; никогда не применять широкую очистку домашней папки.

Полный SQL-набор приложения проверяется отдельными заданиями на **PostgreSQL 16**.
Настоящий локальный Supabase выбранной версии CLI использует свою версию PostgreSQL (фиксируется в отчёте);
сценарий требует одинаковую версию движка источника и цели. Не выдавать его за проверку перехода между версиями.

SQL-копия не содержит физические файлы Storage и сборку приложения.
Физический архив локального тома — работающий адаптер **для этой тренировки**, не команда резервирования управляемого облачного Storage.
В облаке нужен отдельный согласованный экспорт всех объектов/версий с checksum-manifest и проверкой восстановления через API.
Маленькая тестовая база не определяет production RTO/RPO, полосу канала, пределы объёма, PITR или время восстановления индексов большой базы.

## Auth, роли и секреты

В тренировке восстанавливаются реальные локальные таблицы Auth с синтетическими пользователями/хешами паролей;
вход проверяется заново. Bootstrap-роли создаёт тот же CLI; schema/ACL должны совпасть.
Приложение не получает service_role. Существующий пилот использует локальный административный ключ только для создания тестовых пользователей.

Для production отдельно потребуются: совместимая версия Auth/Storage, роли и гранты, настройки JWT/signing keys,
redirect/site URLs, SMTP, OAuth/SAML/MFA, политики сессий, ключи шифрования/Vault и защищённое хранилище секретов.
Решение о сохранении либо отзыве прежних сессий и ротации ключей принимает владелец.
Внешние провайдеры, SMTP, MFA и production-ротация здесь **не проверяются**; реальные ключи не нужны и не запрашиваются.
Не переносить производственные секреты в Git, дамп-артефакты CI или диагностические журналы.

## План восстановления для владельца (не выполняется сценарием в production)

1. Определить согласованную точку восстановления, зафиксировать версию приложения/БД, остановить запись и автоматические исполнители.
2. Проверить целостность копий и соответствие единому срезу БД/Storage. Сохранить текущий экземпляр для расследования.
3. Восстановить совместимую схему, роли и данные в **новый** закрытый экземпляр. Проверить RLS/ACL и личные запреты.
4. Восстановить файлы независимо от SQL, проверить каждую доступную версию и отсутствие потерянных объектов.
5. Настроить Auth и секреты через защищённый канал. Собрать приложение под новую public-конфигурацию.
6. При выключенных OCR/Telegram/интеграциях выполнить проверки связности, истории, финансовых состояний и остатков.
7. Переключение трафика и последующее включение каждого исполнителя — только по отдельному решению владельца.
   Не воспроизводить вслепую старые задания: сначала проверить квитанции и идемпотентность.

## Откат версии приложения

Сохранить SHA/артефакт текущей и предыдущей сборки, manifest миграций и настройки запуска.
До переключения подтвердить совместимость старого приложения с текущей схемой на копии.
Если совместима — владелец возвращает предыдущий проверенный артефакт и его конфигурацию, не меняя историю Git/main.
Если несовместима — не выполнять автоматические down-migrations: подготовить отдельное восстановление согласованной точки БД **и** файлов,
с явным решением о данных, записанных после неё. Прогнать эту тренировку на выбранной паре версий.
Текущий тест доказывает восстановление той же версии, **не** универсальный downgrade и не автоматический production-rollback.

Миграций приложения в этом PR нет. Пересечения: общий браузерный runner, package.json и CI workflow;
точное сопоставление с открытыми PR и фактический CI приводятся в описании PR.
